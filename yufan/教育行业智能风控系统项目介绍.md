# 教育行业智能风控系统项目介绍

## 一、项目概述

本项目是一个面向教育行业的智能风控系统，主要解决在线教育平台在课程报名、课程退费、学习行为和直播打赏等业务场景中可能出现的风险问题。

系统在老师原有通用风控项目的基础上完成了教育行业适配，将原来的电商订单风控扩展为教育业务风控，并接入业务规则、XGBoost 模型和大语言模型（LLM），形成“业务规则 + 机器学习 + LLM 智能协作”的综合风控体系。

系统主要包含以下功能：

- 风控仪表盘
- 风控规则管理
- 风险案件管理
- 评估历史查询
- 在线风险检查
- 黑名单管理
- AI 风控助手

## 二、业务说明

### 1. 课程报名风险

课程报名是教育平台最常见的业务场景，可能存在以下风险：

- 短时间内连续报名多门高价课程
- 新注册账号立即购买高价课程
- 多个账号使用同一个设备批量报名
- 夜间进行异常大额课程消费
- 使用异常支付账号集中报名

系统会结合课程金额、用户历史订单、设备关联数量和报名时间等信息进行风险判断。

### 2. 课程退费风险

课程退费是教育行业中非常重要的风控场景，主要风险包括：

- 购买课程后立即申请退费
- 学习时长很短却多次退费
- 用户退费比例明显过高
- 累计退费金额异常
- 同一个身份或支付账号连续申请退费

系统会结合用户退费次数、退费率、学习进度、累计退费金额和历史订单情况进行判断。

### 3. 学习行为风险

学习行为场景主要关注账号共享和代理学习问题，例如：

- 多个用户共用同一台设备
- 同一用户频繁更换设备
- 多个身份使用相同设备学习
- 学习时间和课程进度明显异常
- 疑似代学、刷课或批量学习

系统通过设备指纹、用户关联数量、学习时长和课程进度等特征识别异常行为。

### 4. 直播打赏风险

教育直播场景中可能存在未成年人消费或异常打赏风险，例如：

- 短时间内连续大额打赏
- 新账号立即进行高额消费
- 存在投诉记录的用户再次大额打赏
- 多个账号使用相同设备打赏
- 命中异常直播账号或设备黑名单

系统会在打赏发生时进行实时检查，并根据风险结果决定通过、标记、人工审核或拒绝。

## 三、系统风控流程

一次教育业务事件进入系统后，会经过以下处理流程：

```text
业务事件
   ↓
参数和业务数据校验
   ↓
用户、课程、订单、设备数据补全
   ↓
黑名单检查
   ↓
25 维风险特征计算
   ↓
业务规则匹配
   ↓
XGBoost 模型预测
   ↓
规则分与模型分融合
   ↓
生成风险等级和决策
   ↓
保存评估、案件及用户画像
```

系统最终输出四种决策：

- **通过**：风险较低，业务正常执行。
- **标记**：允许业务继续，但保留风险标记。
- **人工审核**：创建待审核案件，由风控人员处理。
- **拒绝**：风险极高，系统自动拒绝并生成已拒绝案件。

## 四、业务规则讲解

业务规则用于识别明确、可解释的风险行为。每条规则包含规则名称、适用事件、判断条件、风险等级、风险分和处置动作。

### 1. 单笔超高额课程报名

当单笔课程报名金额达到 10000 元及以上时，系统认为该交易存在极高风险。

- 风险等级：极高
- 风险分：95
- 处理动作：拒绝

### 2. 七日短时大额连报

当用户最近七天报名次数达到一定数量，并且累计报名金额超过阈值时，系统判断可能存在批量报名、盗刷或异常营销行为。

- 风险等级：极高
- 风险分：90
- 处理动作：拒绝

### 3. 高比例频繁退费

当用户退费次数较多，并且退费率达到 75% 以上时，可能存在恶意退费行为。

- 风险等级：极高
- 风险分：92
- 处理动作：拒绝

### 4. 低学习时长反复退费

当用户多次申请退费，同时实际学习时长很低时，系统会认为该用户存在异常退费风险。

- 风险等级：高
- 风险分：75
- 处理动作：人工审核

### 5. 累计退费金额异常

当用户累计退费金额达到 20000 元以上时，系统会将该事件提交人工审核。

- 风险等级：高
- 风险分：70
- 处理动作：人工审核

### 6. 设备关联多账号

当同一设备关联多个用户账号时，可能存在批量注册、账号共享或代理学习。

- 风险等级：极高
- 风险分：88
- 处理动作：拒绝

### 7. 夜间高额教育消费

当用户在夜间购买高价课程时，系统会结合金额、用户历史和设备情况判断是否需要人工审核。

- 风险等级：高
- 风险分：65
- 处理动作：人工审核

### 8. 一票否决机制

如果事件命中“极高”风险规则，即使 XGBoost 模型给出的风险概率较低，系统仍会执行拒绝。

这样可以防止模型评分将明确的高风险业务错误地降级放行。

## 五、XGBoost 风险评估

### 1. 为什么使用 XGBoost

业务规则适合判断已知风险，但难以覆盖所有复杂情况。

XGBoost 可以从历史数据中学习不同特征之间的组合关系，发现单条规则无法识别的潜在风险。例如，某一项特征看起来正常，但多项特征组合后可能表现出明显的风险模式。

### 2. 模型使用的风险特征

项目使用了 25 个风险特征，主要分为三类。

用户特征包括：

- 用户历史订单数
- 最近 7 天订单数
- 最近 30 天订单数
- 用户平均订单金额
- 用户最大订单金额
- 用户退费次数
- 用户退费率
- 用户累计退费金额
- 用户投诉次数

订单及课程特征包括：

- 当前订单金额
- 课程数量
- 优惠金额
- 优惠比例
- 支付时间间隔
- 是否属于夜间消费

设备及关联特征包括：

- 用户关联设备数量
- 设备关联账号数量
- 设备关联身份数量
- 是否为新设备
- 关联地区数量

### 3. 模型输出

XGBoost 输出当前事件的拒绝概率，例如：

```text
P（拒绝）= 0.72
```

系统不会简单地把 `0.72` 直接当作 72 分，而是通过校准函数将概率转换为风险分，使模型分数与规则分数处于相同范围。

### 4. 双轨融合

系统将规则风险分和 XGBoost 模型风险分进行加权融合：

```text
最终风险分 = 规则风险分 × 规则权重
           + 模型风险分 × 模型权重
```

当前默认配置中：

```text
规则权重 = 0.5
模型权重 = 0.5
```

最终风险分对应的决策区间为：

| 最终分数 | 风险等级 | 处理决策 |
| ---: | --- | --- |
| 0～29 | 低 | 通过 |
| 30～59 | 中 | 标记 |
| 60～79 | 高 | 人工审核 |
| 80～100 | 极高 | 拒绝 |

这种方式既保留了业务规则的可解释性，又利用机器学习提升了复杂风险的识别能力。

## 六、案件管理机制

并不是所有评估都会进入案件管理。

- “通过”和“标记”只保存在评估历史中。
- “人工审核”会生成“待审核”案件。
- “拒绝”会生成“已拒绝”案件，并记录系统自动拒绝日志。

风控人员可以在案件管理中查看：

- 用户信息
- 业务事件
- 风险评分
- 命中规则
- XGBoost 评分
- 风险详情
- 案件处理状态
- 审核人与审核意见

这样既保留了完整评估记录，又避免正常业务大量进入人工案件列表。

## 七、如何使用 LLM 协作

### 1. 自然语言查询

传统系统需要用户手动选择多个筛选条件。接入 LLM 后，风控人员可以直接使用自然语言提问，例如：

```text
查询最近一周所有高风险退费事件。
```

```text
帮我查看用户 RISK_REFUND_001 的风险记录。
```

```text
统计最近七天被拒绝最多的业务类型。
```

LLM 会理解用户意图，并调用对应的查询工具获取真实数据库结果。

### 2. 风险结果解释

对于一条风险评估，LLM 可以把技术字段转换成容易理解的业务说明。

例如：

```text
该用户最近发生了 4 次课程退费，退费率达到 100%，
累计退费金额超过 20000 元，并且当前课程几乎没有学习记录，
因此系统将该申请判定为极高风险。
```

这可以帮助业务人员理解系统为什么作出该决策。

### 3. 辅助案件审核

LLM 可以汇总案件中的用户历史、命中规则、模型评分和业务数据，并给出审核建议，例如：

```text
建议维持拒绝。

理由：
1. 用户退费率明显高于正常用户；
2. 多次在学习进度较低时申请退费；
3. 同一身份关联多笔异常订单；
4. 规则引擎和 XGBoost 模型均判断为高风险。
```

最终审核决定仍由规则系统或人工审核人员完成，LLM 只负责辅助分析，不能绕过风控规则直接修改结果。

### 4. 辅助规则设计

风控人员还可以通过自然语言描述需求：

```text
如果用户最近 30 天退费超过 3 次，并且累计退费金额超过 15000 元，
就提交人工审核。
```

LLM 可以将需求整理为结构化规则草稿：

```json
{
  "and": [
    {
      "field": "user_refund_count",
      "op": ">=",
      "value": 3
    },
    {
      "field": "user_refund_amount",
      "op": ">=",
      "value": 15000
    }
  ]
}
```

规则仍需要经过人工确认后才能启用，避免大模型误解业务要求。

### 5. LLM 的安全边界

在本项目中，LLM 的主要职责是：

- 理解自然语言
- 调用经过授权的系统工具
- 查询和汇总业务数据
- 解释风险评估结果
- 提供案件审核建议
- 辅助生成规则草稿

LLM 不直接连接数据库执行任意 SQL，也不直接决定是否拒绝用户。最终风险决策仍由规则引擎、XGBoost 模型和人工审核共同完成。

## 八、项目特点

本项目具有以下特点：

- 将通用风控系统改造为教育行业风控系统
- 覆盖报名、退费、学习和直播打赏场景
- 使用 25 维特征进行风险评估
- 采用业务规则与 XGBoost 双轨融合
- 支持极高风险规则一票否决
- 支持评估、案件、黑名单和操作日志全流程追踪
- 使用 LLM 提供自然语言查询和风险解释
- 使用独立教育数据库保存项目数据
- 测试数据带有专属标记，可以安全清理

## 九、项目总结

本项目不是单独依赖某一种风控方法，而是把业务规则、机器学习和大语言模型结合起来：

```text
业务规则负责明确判断
        +
XGBoost 负责发现复杂风险
        +
LLM 负责理解、查询和解释
        =
教育行业智能风控系统
```

通过这种分工，系统既能保持决策的准确性和可解释性，又能降低风控人员使用系统的难度，实现从风险识别、自动决策到人工审核和智能辅助的完整业务闭环。
