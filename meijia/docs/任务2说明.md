# 任务 2：数据层与规则引擎

## 实现范围

- `app/models_business.py`：8 张核心业务表及 `user_device` 支撑表。
- `app/models_risk.py`：规则、事件、特征快照、评估结果和人工案件表。
- `app/engine/feature.py`：账号、报名交易、学习行为 3 个特征族，共固定 25 维。
- `app/engine/rule.py`：8 个兼容 `match_rXXX` 入口、通用 JSON 条件求值、数据库分值/动作和启用过滤。
- `scripts/gen_risky_users.py`：25 个教育高风险种子用户。
- `scripts/gen_risk_data.py`：默认生成 1000 条评估及 25,000 条特征快照。

## 必须告诉学生的三个坑

1. **ORM 与 Pydantic 必须同步**：修改 `app/models_business.py` 或 `app/models_risk.py` 后，要同步检查 `app/schemas.py` 的输入类型、必填性、枚举和响应字段。数据库允许 NULL 而 Pydantic 强制必填，会导致接口先于数据库报错；反过来则可能在提交事务时才失败。
2. **特征名和顺序不能漂移**：三个 `compute_*_features` 的合并结果必须与 `app/engine/ml_model.py::FEATURE_COLUMNS` 完全一致。当前固定为 25 维，新增、删除、改名或换序都要同步训练和推理代码，并重新训练旧模型，不能继续使用电商模型。
3. **规则必须启用**：规则 ORM 的 `enabled` 属性映射数据库列 `is_enabled`。只有 `enabled=True` 且 `deleted_at IS NULL` 的规则才会进入 `load_enabled_rules()`；只注册 `match` 函数但没有启用数据库规则，不会产生任何命中。

补充注意：数据库 `rule_condition`、`risk_score` 和 `action` 是唯一事实来源。条件字段必须来自 `FEATURE_COLUMNS`，保存前会执行结构与运算符校验。
