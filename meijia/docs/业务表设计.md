# 教育风控业务表设计

> 本阶段为概念设计，仅列核心字段。完整主键、外键、字段类型、索引和可空性将在确认后固化为 MySQL 8.0 DDL。

| 表名 | 核心字段（3-5 个） | 用途 |
|---|---|---|
| `UserInfo` | `user_id`, `role`, `student_id`, `real_name_status`, `register_at` | 保存学生、家长和老师的身份及注册信息，是账号类规则的主体。 |
| `Course` | `course_id`, `name`, `category`, `price`, `teacher_id` | 保存课程定价、分类及授课老师，用于报名和课程维度风险聚合。 |
| `OrderInfo` | `order_id`, `user_id`, `learner_user_id`, `course_id`, `total_amount` | 记录购买者为实际学员购买课程的报名交易，为集中报名、大额连报和退费分析提供事实。 |
| `LearningProgress` | `progress_id`, `user_id`, `course_id`, `total_minutes`, `completion_rate` | 记录课程学习投入和完成程度，为零学时退费等规则提供履约证据。 |
| `RefundRequest` | `refund_id`, `order_id`, `study_minutes_before_refund`, `requested_amount`, `refund_amount` | 记录申请金额、实际退款及申请时学习快照，用于识别低学习量和连续退费。 |
| `BlacklistExtra` | `entry_id`, `type`, `value`, `expire_at`, `reason` | 统一维护用户、学号、身份证、设备指纹及直播账号黑名单。 |
| `EducationCredential` | `credential_id`, `user_id`, `id_card_hash`, `submitted_education_level`, `verify_status` | 安全保存学历认证申请和权威源核验结果，用于识别身份与学历冲突。 |
| `LiveReward` | `reward_id`, `live_session_id`, `reward_account_id`, `amount`, `reward_status` | 记录单场直播打赏流水，用于聚合新账号的大额打赏行为。 |

### 设备关联支撑表（已确认启用）

首期核心业务表仍为上述 8 张；另增加 1 张多对多支撑表，不把设备历史压缩在用户主表中。

| 表名 | 核心字段 | 用途 |
|---|---|---|
| `UserDevice` | `relation_id`, `user_id`, `device_fingerprint`, `first_seen_at`, `last_seen_at` | 保存账号与设备的历史关联，支持同设备多账号和单账号多设备分析。 |

## 规则计算所需字段

概览表只展示 3-5 个字段，以下字段也应进入正式设计。这里先确定业务含义，数据类型、可空性和索引等待选项确认。

| 表名 | 需要补充或保留的字段 | 支撑的规则 |
|---|---|---|
| `UserInfo` | `name`, `register_at` | R001 新账号、R018 账号注册天数 |
| `UserDevice` | `relation_id`, `user_id`, `device_fingerprint`, `first_seen_at`, `last_seen_at` | R001 关联条件、R008 设备关联账号数 |
| `Course` | `total_hours`, `course_status` | 判断课程是否有效及学习完成度是否合理 |
| `OrderInfo` | `study_goal`, `expected_finish_days`, `payment_account_hash`, `created_at`, `paid_at`, `order_status` | R001 按学员、R005 按购买者计算；用支付主体摘要发现关联账号 |
| `LearningProgress` | `last_active_at`, `updated_at` | R002；确认学习数据在退费申请前已经更新 |
| `RefundRequest` | `requested_by_user_id`, `reason`, `requested_at`, `completed_at`, `refund_status` | R002、R012；区分申请人、申请退款与退款成功 |
| `BlacklistExtra` | `created_at`, `status`, `deleted_at` | R030；支持启停、过期、软删除和审计 |
| `EducationCredential` | `id_card_ciphertext`, `id_card_masked`, `authoritative_education_level`, `verify_source`, `verified_at` | R025；兼顾外部核验重试、精确匹配和脱敏展示 |
| `LiveReward` | `user_id`, `original_reward_id`, `transaction_type`, `rewarded_at`, `reward_status` | R018；按成功打赏及其调整流水计算净额 |

## 表间关系

```text
UserInfo 1 ── N OrderInfo N ── 1 Course
   │                 │
   │                 └── 1 ── N RefundRequest
   │
   ├── N UserDevice
   ├── N LearningProgress N ── 1 Course
   ├── N EducationCredential
   └── N LiveReward

BlacklistExtra 通过 (type, value) 与用户 ID、学号、身份证号、
设备指纹或直播账号进行逻辑匹配，不设置多目标物理外键。
```

## 数据一致性要求

- `OrderInfo.total_amount` 和 `LiveReward.amount` 不得为负数；退费申请金额必须大于 0，实际退款金额不得超过申请金额。
- `OrderInfo.user_id` 表示购买者，`learner_user_id` 表示实际学员；涉及资金的规则按购买者统计，涉及报名与学习的规则按学员统计。
- `LearningProgress.total_minutes` 不得为负，`completion_rate` 应限制在 0-100%。
- 同一用户与课程原则上只有一条累计进度记录；若需要逐次学习明细，应另建学习行为流水表。
- R002 优先使用 `RefundRequest.study_minutes_before_refund` 快照，避免后续学习导致历史规则结果变化。
- 学历、身份证等敏感数据应加密或脱敏展示；用于精确匹配时可额外保存不可逆摘要。
- 支付主体不保存银行卡号等原文，只保存经过统一规范化后的不可逆 `payment_account_hash`。
- 订单、退款和打赏聚合必须过滤取消、失败记录，具体有效状态值在字段确认阶段确定。
- `UserDevice` 同一用户与同一指纹只能保留一条关系，重复上报时更新 `last_seen_at`，不重复插入；规则仅使用最近 180 天活跃的设备关系。
- R005 使用事件发生时近 1 小时的支付成功订单毛额，后续退款不回改历史特征和评估结果。
- 直播打赏风险金额采用成功打赏减去退款、撤销及冲正后的净额。

## 设计边界

- 以上 8 张均为业务事实表；规则配置、评估结果、人工审核案件等风控平台表不计入本清单。
- 已确认采用 `UserDevice` 保存设备历史；它属于支撑关联表，不计入首期 8 张核心业务表。
- `BlacklistExtra` 实际属于风控基础数据表。保留该名称是为了对齐题目，落库时建议改为语义更明确的 `risk_blacklist`。

## 参考设计的取舍

本项目参考 `/home/major/AI_Risk` 的分层思想，但不沿用其电商表和字段：

- DDL 按“基础主表 → 关联表 → 交易与行为表”的外键依赖顺序执行。
- 外键列建立索引；窗口聚合再围绕“主体 + 状态 + 事件时间”设计联合索引。
- 黑名单采用“类型 + 规范化值”唯一约束，并同时支持到期和软删除，便于审计。
- 数据库 DDL 与后续 ORM 模型保持一一对应，并增加自动一致性检查。
