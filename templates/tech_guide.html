0. 先读：5 分钟掌握核心骨架

🧠 生活化类比（一图看懂双轨风控）
做风控就像 去医院看病：
① 规则引擎 (60% 权重) = 老中医「望闻问切」：发烧 38.5℃ → 规则命中 30 分；咳嗽喉咙痛 → 35 分；武汉旅行史 → +100 VETO，优点 100% 可解释。
② XGBoost (40% 权重) = CT 影像 / 验血报告：看过 10 万病例能发现隐性模式，优点查隐性风险，缺点黑盒。
③ fuse_score 融合 = 主任医生签字：0.6×中医 + 0.4×CT → 40 以下回家（通过）/ 40-60 观察（标记）/ 60-90 专家会诊（人工审核）/ 90 以上立刻住院（拒绝）。
④ VETO=90 一票否决 = 心脏骤停直接进抢救室，不用等 CT，省资源 + 不放过高危。
💼 业务小例子：VETO 90 分怎么触发？
USER_007 同时满足 3 条：L020 拒收率 30%（30）+ L007 实名失败（30）+ L012 刀具词（35）= 95 ≥ 90 → 直接 VETO，不再跑 XGBoost 模型，立刻返回「拒绝」。
道理：心脏骤停病人不等 CT；而且坏人可以伪装 100 单正常历史（骗 ML），但 3 条高危规则同时命中，信号比 ML 可靠得多。

新人先理解这 5 条，后面看代码就不迷路：

  1. 双轨风控 = 0.6 × 规则分 + 0.4 × ML 分，≥90 分触发 VETO 一票否决（直接拒绝，不再融合），代码在 app/engine/decision.py
  2. 规则引擎：app/engine/rule.py 实现 9 种 JSON op；app/engine/feature.py 输出 固定 25 维特征 dict（任何改动都要同步 3 处，测试卡住就看第 7 章）
  3. XGBoost：app/engine/ml_model.py import 时自动加载 app/engine/xgb_model.json；缺失时自动降级纯规则，不影响业务
  4. 数据库：9 张通用风控表（Rule/Event/Feature/Assessment/Case/Alert/Blacklist/ActionLog/Validator）+ 8 张物流业务表（Shipment/ShipmentItem/Address/Complaint/Declaration/Customs/Delivery/实人实名）严格分离，不跨域加 FK
  5. 调用入口：前端 /risk-check → POST /api/risk/evaluate → RiskService.evaluate() → 依次经过：黑名单 5 级短路 → 规则引擎加权 → XGBoost 预测 → decision 融合 → 写 Case/Alert/Assessment

(lifespan 的 APScheduler 会起两遍)

3.2 FastAPI lifespan

在 scripts/main.py 注册 @asynccontextmanager，两件事：

  1. startup：创建 app.scheduler = APScheduler(AsyncIOScheduler) → 加 2 个 cron（案件超时检查每分钟；告警轮询每 30s）→ scheduler.start()
  2. shutdown：scheduler.shutdown(wait=False)，防进程泄漏
🔴 陷阱：如果 6 步自检里 DB 端口写成 127.0.0.1 而 .env 里 DB_HOST 是远程主机，会出现「6 步自检挂但其实服务能起来」的假象——所有 host 都走 settings.DB_HOST。

4. 风险评估一次调用链 ⭐⭐⭐（面试必考）

💼 业务小例子：黑名单短路 = 性能 30× 提速
手机号 13800138000 被运营同事加进 黑名单_5 级（手机号） →
未短路前：查特征（10 次 JOIN=100ms）+ 30 条规则（700ms）+ XGB 前向（400ms）= 1200ms
有短路后：blacklist_service.match 查 6 张表任意命中 = 40ms 直接 return「拒绝+命中原因=黑名单命中」
设计原则：最便宜、最准的校验放最前，越贵的（ML/大 JOIN）越靠后。

# app/engine/decision.py
VETO_MIN_SCORE = 90               # 一票否决阈值 (规则分)
RULE_WEIGHT     = 0.6
ML_WEIGHT       = 0.4
THRESHOLDS = [
    (40,  "通过"),
    (60,  "标记"),
    (90,  "人工审核"),
    (101, "拒绝"),  # ≥90 会被 VETO 提前拦截, 这里兜底
]

def fuse_score(rule_score: int, ml_score: int) -> tuple[int, str]:
    if rule_score >= VETO_MIN_SCORE:              # ① 一票否决: 规则 ≥ 90 直接拒绝, 不融合
        return 100, "拒绝"
    final = int(round(RULE_WEIGHT * rule_score + ML_WEIGHT * ml_score))  # ② 加权融合 (0-100)
    for threshold, decision in THRESHOLDS:        # ③ 分段匹配决策
        if final < threshold: return final, decision
    return 100, "拒绝"

6.1 9 种 op 实现（无第三方依赖，自研 evaluate_condition）

📄 Python 代码 · 19 行python  
# app/engine/rule.py 核心 100 行, 支持 9 种 JSON op
SUPPORTED_OPS = {
    "==": lambda v,r: v == r,
    "!=": lambda v,r: v != r,
    ">":  lambda v,r: v is not None and v >  r,
    "<":  lambda v,r: v is not None and v <  r,
    ">=": lambda v,r: v is not None and v >= r,
    "<=": lambda v,r: v is not None and v <= r,
    "in":       lambda v,r: v in r,                                # r = list
    "contains": lambda v,r: isinstance(v,str) and str(r) in v,    # 字符串包含
    "between":  lambda v,r: r[0] <= v <= r[1],                    # r = [min, max]
}
def evaluate_condition(cond: dict, features: dict) -> bool:
    field, op, value = cond["field"], cond["op"], cond["value"]
    if field not in features: return False        # 特征缺失: 保守不命中
    # 支持嵌套 AND/OR: {"op":"and","conditions":[c1,c2,...]}
    if op == "and": return all(evaluate_condition(c, features) for c in cond["conditions"])
    if op == "or":  return any(evaluate_condition(c, features) for c in cond["conditions"])
    return SUPPORTED_OPS.get(op, lambda *_: False)(features[field], value)

        MODEL = xgb.XGBClassifier()

def predict_proba(features: dict) -> int:
    if MODEL is None: return features.get("user_risk_score", 0)   # ⭐ 降级纯规则, 不影响业务
    row = np.array([[features[k] for k in FEATURE_COLUMNS]], dtype=np.float32)
    return int(round(MODEL.predict_proba(row)[0][1] * 100))      # 正例概率 × 100 → 0-100 分

  3) 加 1 条集成测试：软删 → list → assert len == old_len - 1
① 软删约定（risk_rule / risk_blacklist）
DELETE 路由不执行 db.delete(obj)，而是 obj.deleted_at = now()；所有读接口都加 WHERE deleted_at IS NULL，少加一处就会显示已删数据。
② 案件状态机白名单
service/case.py::_ALLOWED_CASE_TRANSITIONS = {"待审核": ["审核中", "已关闭"], ...}，任何非法跳转（已通过→待审核）后端直接返回 400 「状态流转非法」，不允许绕过状态机。
③ 日志约定
所有业务模块 logger = logging.getLogger(__name__)，不准另起；统一走 logging_config.py：stdout + logs/app.log（50MB × 5 轮转，合规留痕）。

13. 🎯 面试高频 30 题（附标答要点，直接背）

项目里"双轨风控"具体怎么实现？为什么选 0.6/0.4？答：0.6 规则 + 0.4 ML 加权融合；规则可解释（运营改）+ ML 学隐性模式。权重 0.6/0.4 是上线初值（规则稳定优先），后续可按业务 AUC 回测调。≥90 分 VETO 一票否决跳过 ML，防止高危规则被 ML "稀释"。
如何保证特征工程和模型输入永远对齐？契约式：FEATURE_COLUMNS 常量 + feature.py 输出 dict + test_xgboost 对齐测试，3 层锁死；新增特征 3 步同步，否则对齐测试直接挂。
为什么黑名单放最前面短路？6 类优先级怎么定？省资源（后续 7 步不跑）+ 确定性最高（人工确认恶意）。6 类按"作恶影响面 + 确定性"排序：用户 > 身份证 > 手机 > 地址 > 运单 > 设备。
XGBoost 模型文件不存在怎么办？import 时 try/except，MODEL=None，predict_proba 退化成 user_risk_score（纯规则画像）。业务 0 感知，只有日志 WARNING。
为什么用 SQLAlchemy async？踩过什么坑？并发高（每评估要跑 20+ SQL），async 不占线程。坑：① aiomysql Event loop is closed（写 get_db_async 显式 close 不依赖 __aexit__）② 不要 db.refresh()（aiomysql 跨 loop 报 MissingGreenlet）→ 写入时 Python 端直接填 default，commit 后直接读内存值。
规则引擎 9 种 op 为什么自研不用库？① 9 种简单 op 没必要引入 json-logic/jmespath 额外依赖（面试加分：控制依赖数）② 嵌套 AND/OR 递归 50 行就实现，比第三方更可控 ③ 错误时返回的条件路径能定位到哪条规则。
前端「[object Object]」这个经典 Bug 你们怎么根治的？根因：直接 alert(err.detail) 把 list[dict] 当字符串。根治：① 写 formatHttpDetail() 递归格式化（Pydantic msg+loc → 中文 "[body.field] 错误信息"）② 原生 alert 全替换成 showToast() 右上角 Toast ③ 后端 422 异常处理器直接把 msg 翻译中文，前端 0 处理。
静态文件强缓存怎么解？FastAPI StaticFiles 默认 1 年，每次改 JS 加查询参数版本号 ?v=20260812vN，URL 变了浏览器强制重新下载（CDN 同理）。
17 张表为什么严格分 9 风控 + 8 物流？通用风控表（Rule/Event/Assessment/Case…）跨行业可复用；物流表替换成电商订单/金融交易/出行订单就是另一个行业版本——架构可迁移性高，面试强调"不是写死物流，而是场景 E 替换层"。
案件为什么要状态机？怎么防非法跳转？运营人员容易手滑（已通过→再拒绝会让下游困惑）。service/case.py 里写 _ALLOWED_CASE_TRANSITIONS 白名单，任何非法跳转 400「状态流转非法」，写操作全过 service 层，不让 router 直接 ORM 更新。
软删为什么还要 deleted_at 而不是物理删？合规留痕（风险规则改动要有审计）；还能一键恢复（UPDATE deleted_at=NULL）。注意：所有 SELECT 必须手动加 WHERE deleted_at IS NULL，少加一处就会显示脏数据。
训练数据正例不足怎么办？① scripts/gen_risk_data.py --balance-pos 造合成正例 ② scale_pos_weight=5 样本加权 ③ SMOTE 过采样（先试 ①+② 够了）。本项目合格线 AUC ≥ 0.82。
为什么用 Jinja2 SSR 不搞前后端分离？① 项目是教学用，0 构建（不用 Node/Vite），新人 clone 完 python run_app.py 直接看效果 ② 7 个管理后台页面交互简单，SSR 够了 ③ SEO/首屏更快。
Agent 为什么要做只读安全？怎么防 Prompt 注入？Agent 允许用户自然语言 → 如果让它写库，一句"把所有黑名单都删掉"就完了。防注入：① 6 个工具只暴露读/只读 SQL（正则黑名单 INSERT/UPDATE/DELETE/DROP）② DB 层配只读 DB 用户 ③ 工具输出最大 4000 chars 截断 ④ 系统 Prompt 禁止输出 SQL 原文。
调度器为什么要 lifespan 启停？APScheduler 是全局单例，lifespan 保证 FastAPI 进程启动时 scheduler.start() 一次，退出时 shutdown()。踩过的坑：uvicorn reload=True 会让 lifespan 跑两遍 → scheduler 两个实例同时跑 → 12h 超时被关 2 次，AGENTS.md 明确禁止 reload=True。
FK 归属越权链是啥？举例子。接口声明"给运单 X 提交审核"但用户 ID 是 Y，要验证 ensure_shipment_belongs_to_sender(shipment_id, user_id) → 运单 belong_to 不是 Y 就 403。放在 service/validator.py 中间件层，每个写操作必过 validator。
Pydantic 英文报错怎么翻译中文的？scripts/main.py 全局 @app.exception_handler(RequestValidationError)：遍历 err.detail，按 error.type 匹配（比按 msg 稳，Pydantic 版本变化不影响），再把 {ge}/{le}/{min_length} 模板参数填进中文句子。兜底还有前端 formatHttpDetail 字符串级替换，双保险。
决策融合 0.6/0.4 可以怎么优化？答 2 点：① 离线 GridSearchCV 搜最佳权重组合（按 AUC 最高）② 动态权重：冷启动时 0.9/0.1 ML 样本少；数据量上来后 0.5/0.5 回归。
为什么不直接规则 ≥ 某阈值就拒绝，还要搞 VETO=90？因为累加型分值：3 条 30 分规则加起来 90 就是多个弱信号叠加 → 确定为恶意，不再相信 ML（ML 是概率性的，可能被伪装样本拉低）。VETO 阈值 90 是"运营绝对不能放过"的红线。
pytest 为什么必须用 python -m pytest tests/，不能裸 pytest？裸 pytest 不把 cwd 加进 sys.path，import app 就报 ModuleNotFoundError。AGENTS.md 里写死了命令（很多 README 过期还是 pytest tests/，面试主动提你修过文档陷阱加分）。
Python 3.13 为什么禁用？uv/pyproject.toml 要求 requires-python = ">=3.11,<3.13"。XGBoost 1.7 的 py313 wheel 未稳定（报 unknown file type），aiomysql 部分 async 函数在 3.13 有新 GIL 坑 → 为稳定性禁用。
Action Log 怎么设计？risk_action_log 表：operator / action_type(CREATE_RULE/DELETE_BLACKLIST/REVIEW_CASE) / target_type / target_id / before_value(JSON) / after_value(JSON) / remark / create_time。所有写操作（rule/create, case/review, blacklist/add）统一过 service/action_log.record()，前端看不看无所谓，合规审计 100% 能追到人。
一条风险评估完整调用链要写多少 SQL？怎么优化？最坏：黑名单 6 次 SELECT + 25 维特征（用户画像 3 + 运单 3 + 实名 2 + 地址 3 + 跨境 2 + 设备 2 + 投诉 1 + 拒收 2 + 训练回填 3 + 规则 1）= 约 30 次。优化：① 黑名单短路直接 return，30 → 6 次 ② 特征工程里同一张表的 JOIN 合并成一条大 SQL ③ AsyncSession 开 pool_size=10 max_overflow=20 连接池。
为什么 XGBoost 用 JSON 存模型不用 pickle？pickle 跨版本（XGBoost 1.x→2.x）经常崩；JSON 是官方标准格式（save_model/load_model），跨语言也能读（后续换 Java 线上推理不用重训）。
XGBoost 为什么 predict_proba 要取 [0][1]？二分类 predict_proba 返回的是 (n, 2) 矩阵：第 0 列=负例概率，第 1 列=正例（高风险）概率，乘 100 才是 0-100 分的分数。
为什么要写 refreshDashboard / loadRules 这些显式函数不自动轮询？① 省资源（后端 RTT 高）② 操作型后台不需要实时，用户手动点"刷新"或新建后跳第一页足够；要实时可以 setInterval 1min 调一次。
为什么规则排序 priority 第一键而不是 update_time？列表展示 = 规则权重序（运营先看 100/99/98 的高权规则），同权组内按 update_time DESC 让最新修改的在同权组顶 —— 两全：权重大的在整库顶，同组内最新的在组顶。
为什么要区分「标记」和「人工审核」两种决策？阈值 40-60 = 标记（观察项，不给运营加工作量，只进评估历史）；60-90 = 人工审核（自动建案，要人处理）—— 运营人力有限，不能把模糊的都塞过来。
你们做过什么"工程稳定性改进"？① run_app.py 6 步自检（Python/.env/依赖/DB连通/表存在/静态文件），上线就知道卡哪 ② ML 模型缺失自动降级，不阻塞业务 ③ Pydantic 错误翻译中文减少 50% 客服工单 ④ formatHttpDetail 消灭 [object Object] 视觉 bug ⑤ 静态版本号破缓存避免改完代码用户看到旧 JS。
（开放题）如果你要加一个新业务场景（比如电商），要动哪些地方？4 步：① 新建 models_ecommerce.py（订单/支付/售后 8 表）② feature.py 里把物流 SQL 语义替换成电商对应字段（25 维 dict key 不变！契约不动）③ 种子规则 sql/seed_rules_ecommerce.sql 30 条电商规则 ④ 前端 4 种事件类型下拉 + 业务 ID placeholder 换电商。其他 9 张风控表、decision、ML、Agent、dashboard 都不动。
