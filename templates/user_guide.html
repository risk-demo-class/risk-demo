0. 快速上手（5 分钟）

第一次使用？按以下顺序做一遍就能上手系统 80% 功能：

  1. 进入 仪表盘，了解当前系统今日评估数、高风险数等整体概况。
  2. 打开 规则管理，浏览一遍已启用的 L001~L030 30 条规则（建立对规则引擎的直觉）。
  3. 跳去 风险检查，输入：
    • 事件类型 = 寄件下单，业务 ID = SHIP001，用户 ID = NORMAL001 → 点执行检查（应拿到「通过」或「标记」）
    • 再换用户 ID = RISK001 跑一次（命中高危规则，应进入「人工审核」）
  4. 如果上一步是人工审核，打开 案件管理，找到刚生成的案件，进入详情看用户画像，决定通过 / 拒绝。
  5. 确认是恶意用户，到 黑名单 把它加进「用户」黑名单 → 之后该用户任何寄件都会被直接拒绝（不再跑规则和 ML）。

3. 风险检查（核心入口） → 打开

系统 最常用 页面：输入一次业务事件参数 → 返回最终「通过 / 标记 / 人工审核 / 拒绝」决策与详细原因。

  1. 选事件类型（必须从 4 个中选一个，否则会被后端拦截报错）
  2. 填业务 ID（运单号 / 报关单号 / 投诉单号，见下表）
  3. 填用户 ID（可选，但推荐；不填时用户画像特征会全部置 0，规则命中会减少）
  4. 点「执行检查」（等待 1~3 秒，后台会跑：黑名单 5 级短路 → 规则引擎加权融合 → XGBoost ML 评分 → 422 校验）
  5. 下方会出现结果面板，包含每条命中规则的名称、分值、以及 ML 评分。

5. 规则管理（规则引擎 60% 权重） → 打开

30 条 L001~L030 物流规则都在这里维护。规则分 = 60% 权重，会直接左右最终决策。

5.1 新建规则字段详解

字段必填说明 + 合法取值示例
规则 ID✅全局唯一，建议 L001/L002/L031 递增（已有 ID 会报 409 冲突）L031
规则名称✅一句话说明"这条规则命中代表什么"新号+高价值报关=人工
分类✅8 大分类，见附录 9.2跨境异常
风险等级✅低 / 中 / 高 / 极高（仅标签展示，不参与计算，真正扣分看 risk_score）高
分值 0-100✅最重要字段！这条规则命中时给多少分（加权后 ≥90 会触发 VETO）60
动作✅通过 / 标记 / 人工审核 / 拒绝人工审核
优先级❌ 默认 0数字越大越先执行；相同分值时，优先级高的规则排在列表前90

🔴 字段名只能从附录 9.3 的 25 维特征里挑，比如写成 refund_rate 就会永远匹配不上（正确写法是 sender_recent_refund_rate）。

5.3 启用/禁用/删除

  • 启用/禁用（开关按钮）：禁用后规则引擎跳过它；可以随时再启用，适合活动后临时下架。
  • 删除：软删（deleted_at = 当前时间），列表不再显示，想恢复需要管理员改 DB 把 deleted_at 置回 NULL。
  • 排序：优先级 DESC → 修改时间 DESC → 规则 ID DESC（最新修改的会排在同优先级最前）

6. 黑名单管理（短路拦截） → 打开

6.1 6 类黑名单 + 优先级（从高到低）

命中**任何一级**都会直接返回「拒绝」决策，不再跑后面的规则和 ML（性能 + 安全双提升）：

  1. 用户 — 对 user_id 整体封禁（最严厉，建议只用于确认欺诈）
  2. 身份证号 — 身份证号匹配，适用实名欺诈
  3. 手机号 — 11 位手机号匹配
  4. 地址 — 高发退货/异常收货地址
  5. 运单号 — 特定运单隔离（异常流程）
  6. 设备指纹 — dev-xxx 格式，模拟器 / 多开设备共用

6.2 使用红线（团队要严格遵守）

⚠️ 黑名单不是垃圾桶！不要滥用：
  1. 只有人工核实 + 确认恶意才能加。如果只是"疑似"请走案件「人工审核」。
  2. 加黑名单时必须填原因，方便 6 个月后复盘。
  3. 加用户级黑名单会影响该用户所有合法运单收寄，能加手机号就别加用户级。

7.2 三步审核流程

  1. 打开详情：点表格「详情」按钮，查看完整命中规则 + 用户画像 + 历史评估
  2. 判定并填审核意见：
    • 🟢 通过：用户没问题，放行；如果是误命中可把相关规则调低分或禁用
    • 🔴 拒绝：确认有风险；建议同时勾选「拒绝时加入黑名单」一次性全封
    • ⚪ 关闭：数据不足无法判断 / 重复案件
  3. 填审核人（默认 admin），点对应按钮 → 案件流转到终态

10. 常见问题 FAQ

两种情况：
① 新建规则后系统自动跳回第 1 页（因为按 修改时间 DESC，最新的在第 1 页），如果你在第 2 页以后创建，列表会跳到第 1 页，这是正常行为。
② 如果规则 ID 与已存在的重复，右上角会弹红色 Toast「规则ID已存在」（409 冲突），并没有真的创建。

分值：50 ✅ / 85.5 ❌ / 空 ❌。
条件 JSON：3 个必填键 = field（从 25 维里挑）+ op（从 9 种里挑）+ value（类型匹配）。常见错误：引号写成中文「」、op 写成 >= 以外的符号、field 拼错（refund_rate → 正确是 sender_recent_refund_rate）。

app/engine/xgb_model.json 模型文件不存在或损坏。系统已自动降级为纯规则（业务照常运行，只是 ML 40% 权重没了）。让后端工程师执行 python scripts/train_xgb_model.py 重训生成文件即可。

可以。系统所有"删除"都是软删除（只写 deleted_at = 当前时间，不真删数据）。联系 DBA 执行： 
UPDATE risk_rule     SET deleted_at = NULL WHERE rule_id     = 'L031';
UPDATE risk_blacklist SET deleted_at = NULL WHERE blacklist_id = 123;

不会报错。当业务 ID 在数据库里找不到，业务级特征会填默认值（0/false/空），规则引擎只能匹配到用户画像级和全局级特征，结果依然可用，但可能漏掉了运单/报关单级的规则。建议填真实 ID 以获得完整评估。

修改"优先级"字段：给相同类别的规则设置相同的优先级数字（例如"危险品瞒报"类全部设为 90），同一类别内再按修改时间 DESC 排序。编辑规则后同类别最新的会排到同类最前面。

后台 app/scheduler.py 每 30 分钟扫一次表，对「待审核」超过 12h 的案件自动设为「已关闭」，并写操作日志避免漏案。审核人员请在工作时段及时处理。

11. 典型业务流程（按图索骥）

场景 A：客服接到用户投诉 → 复核该用户是否有风险

  1. 进入「风险检查」→ 事件 = 投诉申诉 / 业务 ID = 投诉单号 / 用户 ID = 被投诉用户
  2. 如果决策是「通过」→ 正常流程处理投诉。
  3. 如果决策是「人工审核」→ 记下 case_id → 转审核组处理。
  4. 如果决策是「拒绝」或「命中黑名单」→ 投诉升级，不做和解处理。

场景 B：大促前策略调整 → 新增 1 条规则并验证

  1. 「规则管理」→ 新建规则 L031：新号 + 高价值 → 人工审核。分值 55，优先级 80。
  2. 「风险检查」→ 手工构造 10 条新号高价值数据 → 都应进入人工审核；用 NORMAL 老号跑 → 不命中。
  3. 等大促结束 2 周 → 观察评估历史里 L031 的命中率 → 命中率 < 0.1% 考虑禁用。

场景 C：运营审核员处理一个高危案件

  1. 「案件管理」→ 状态筛选"待审核"→ 打开高风险案件。
  2. 详情里看：用户画像拒收率 45%、投诉 7 次 → 确定职业薅羊毛 → 勾选「拒绝+加黑名单用户+身份证号+手机号」。
  3. 审核意见填写「职业薅羊毛，投诉 7 次，拒收率 45%」→ 点红色「拒绝」按钮。自动生成 3 条黑名单，以后该用户任何寄件都被直接拒绝。
