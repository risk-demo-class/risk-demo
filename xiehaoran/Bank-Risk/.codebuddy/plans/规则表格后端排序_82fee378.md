## 用户需求

为规则管理模块的规则表格增加排序功能，支持对规则数据进行排序查看。

## 产品概述

在规则管理页的表格中，通过点击列头触发服务端排序，用户可按指定字段升序/降序查看规则列表，排序结果跨分页全量有效，并与现有分类筛选、分页交互保持一致。

## 核心功能

- 后端 `GET /api/rules` 新增排序参数 `sort_by` 与 `order`，支持按规则ID、分值、优先级、风险等级排序（等级按低/中/高/极高语义而非字典序）。
- 前端规则表格对「规则ID」「分值」「等级」「优先级」四列表头增加可点击排序，点击后向后端发起带排序参数的请求并刷新当前页数据。
- 排序状态与分页、分类筛选联动：切换分类或排序时回到第 1 页；表头箭头方向正确反映当前排序字段与方向。
- 无排序参数时保持现有优先级降序的默认行为，不破坏既有展示顺序。

## 技术栈

- 前端：React + TypeScript + Ant Design（Table 受控排序、sorter 配置）+ Tailwind CSS
- 后端：FastAPI + SQLAlchemy（异步） + SQLite/AsyncSession
- 现有模式：后端分页 `api.rules(category, page, page_size)`，前端 `RuleBoard.tsx` 中 `load()` 拉取数据并受控分页

## 实现方案

采用后端排序方案（已与用户确认），点击表头后由 Ant Design Table 的 `onChange` 回调拿到 `sorter.field` 与 `sorter.order`，写入前端状态 `sortBy/sortOrder`，重新调用 `api.rules` 携带排序参数，后端用 `order_by` 对全量数据排序后分页返回。该方案与现有分页、分类筛选同为后端驱动，行为一致、支持跨页全量排序。

关键技术决策：

1. 后端用 `case()` 表达式把 `risk_level` 字符串（低/中/高/极高）映射为数值 1/2/3/4 再 `order_by`，避免按汉字字典序/拼音错误排序。
2. 排序参数白名单校验：`sort_by` 仅允许 `rule_id/risk_score/priority/risk_level`，`order` 仅允许 `asc/desc`，非法值忽略并回退默认 `priority.desc()`，防止 SQL 注入与错误排序。
3. 前端 `sorter` 仅声明 `true`（数据来自后端，不需 AntD 本地排序），用受控 `sortOrder` 显示箭头；等级列 `sorter.field` 设为 `"risk_level"` 直接传给后端。

性能与可靠性：排序在数据库层 `order_by` + `limit/offset` 完成，沿用现有索引友好的整型/主键字段；`risk_level` 的 `case()` 为轻量表达式，数据量小无瓶颈。默认无排序参数保持原有 `priority.desc()`，向后兼容。

## 实现注意

- 复用现有 `api.rules` 签名风格，仅追加可选参数，不影响其他调用方（当前仅 RuleBoard 使用）。
- `load` 的 `useEffect` 依赖需加入 `sortBy`、`sortOrder`，避免排序变化后不刷新。
- 切换分类或排序时 `setPage(1)`，保持与现有「切换分类回第1页」一致，避免停留在越界页码。
- 后端 `order_by` 构建时使用白名单映射，杜绝用户可控字符串直接拼入查询。
- 改动后前端执行 `npm run build`（或 tsc）确保类型通过。

## 架构设计

现有数据流：UI 交互（点击表头）→ `setSortBy/setSortOrder` → `useEffect→load()` → `api.rules(params)` → `GET /api/rules?...&sort_by=&order=` → 后端 `api_list_rules` 构建 `order_by` → 返回排序后分页数据 → Table 渲染（受控 `sortOrder` 箭头）。

仅修改规则列表这条既有链路，不引入新架构模式。
