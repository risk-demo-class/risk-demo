# agent_design.md - Vibe Coding 协作复盘

## 1. 我们如何用 LLM 协作

本项目的业务层 (场景 A 旅游风控) 全部通过 LLM 协作产出, 流程对应任务书 4 个递进任务:

| 任务 | LLM 输入 | LLM 产出 | 人工验收 |
|---|---|---|---|
| 1 业务理解 | 任务书场景 A 描述 | `1-业务说明.md` | 欺诈场景/字段/事件/术语真实 |
| 2 数据层 | 业务说明 | 8 张表 ORM + DDL + 造数脚本 | init_db 跑通, ≥100 条数据 |
| 3 pipeline+训练 | 表结构 + 造数逻辑 | 25 维特征 + 12 规则 + 训练脚本 | val_auc≥0.7, ≥3 规则命中 |
| 4 演示文档 | 全项目代码 | README + 本复盘 | 5-8 分钟讲解 |

## 2. 关键提示词 (节选)

> "我要做旅游行业的风控系统, 业务层跟电商完全不同. 帮我设计 8 张业务表 schema,
> 字段/关联/索引要考虑后续风控特征计算的便利, 同时写一个 Python 造数脚本至少造 100 条."

> "这是旅游业务表 + 数据. 请帮我设计 3 大特征族 (用户/订单/行程), 字段映射到旅游行业,
> 调研 OTA 典型欺诈套路, 设计 12 条业务规则, 跑通 XGBoost 训练并用 val_auc/val_f1 评估."

## 3. 复用边界约束 (LLM 必须遵守)

- `process_event` 4 步 + `run_risk_check` 7 步流程与契约不能改
- 风控 9 张表结构复用, 只允许 ENUM 追加旅游值
- 黑名单: `risk_blacklist` 权威, `blacklist_extra` 业务镜像
- 第三特征族用 `trip_*` 前缀, 引擎 `_classify_feature_entity` 零改动

## 4. 踩过的坑

1. ENUM 硬编码: 电商枚举装不下旅游值 → 用 migration 追加 (ALTER TABLE MODIFY ENUM)
2. 双库隔离: 造数脚本必须指向 `tourism` 库, 防止误操作 `ecs` 基线数据
3. 特征-标签同源: 训练数据来自规则标签, AUC 高是"规则喂出来的", 讲解时主动说明
4. 前置拦截 vs 规则: 黑护照走 R030 规则 (留审计), 前置只拦 用户/设备/签证
