# 旅游行业风控系统业务说明

## 1. 业务定位

本系统面向 OTA 平台、旅行社、旅游交易平台及综合出行服务商，覆盖机票、酒店、签证、跟团游、投诉、售后等业务场景。

系统目标是在旅游交易的关键节点识别欺诈、倒卖、恶意退款、证件异常、账户团伙和合规风险，并形成完整闭环：

```text
业务事件接入 -> 业务实体校验 -> 黑名单拦截 -> 特征计算 -> 规则/模型评估
-> 风险决策 -> 案件审核 -> 黑名单/用户画像沉淀 -> 告警监控
```

系统不追求简单地“拦截所有异常”，而是通过分层风险等级与分档决策，在保障交易安全、平台资产安全、旅游者权益和监管合规之间取得平衡。

## 2. 典型欺诈与风险场景

| 场景 | 典型表现 | 风控关注点 |
|---|---|---|
| 黄牛囤票/占座倒卖 | 同一手机号、支付账号、设备或 IP 短时间大量预订机票、热门线路或热门酒店 | 高频、同航班/同线路、同支付账号聚集、短时间批量操作 |
| 大额跨境游欺诈 | 新注册用户提交高金额跨境游订单，且临近出行或目的地风险较高 | 订单金额、注册时间、目的地风险、出行日期 |
| 签证风险 | 用户 90 天内多次拒签，或 30 天内申请多个国家签证 | 拒签历史、申请国家数量、旅客证件一致性 |
| 黑护照/证件拦截 | 旅客护照号、身份证号、手机号、支付账号命中黑名单 | 黑名单类型、证件号、手机号、支付账号 |
| 恶意退改/退款 | 高频订退、临近出行退款、高额退款、投诉后申请补偿 | 退款率、取消率、退款金额、投诉次数 |
| 酒店预订欺诈 | 高价酒店临期预订、入住人异常、证件不一致、拒绝实名核验 | 入住人信息、酒店金额、入住日期、实名状态 |
| 投诉套利 | 同一用户多次投诉、重复索赔、同订单多渠道投诉 | 投诉次数、赔付金额、历史案件 |
| 账户团伙风险 | 多账号共用手机号、护照、支付账号、设备或 IP，批量下单和退改 | 账号关联网络、设备/IP、证件聚合 |

## 5. 风控事件类型

| 事件类型 | 触发时机 | 主要风险 |
|---|---|---|
| `旅游下单` | 跟团游、自由行订单提交 | 大额订单、临期出行、高风险目的地、新用户大单 |
| `机票预订` | 航班锁座、出票前、支付后出票 | 黄牛囤票、占座倒卖、同账号批量订票 |
| `酒店预订` | 酒店下单、确认入住前 | 临期高价酒店、入住人异常、证件异常 |
| `签证申请` | 签证资料提交、补充材料、出签/拒签 | 多国签证、拒签历史、证件异常 |
| `支付` | 支付发起、支付成功、支付失败 | 支付账号聚集、高频支付失败、盗刷风险 |
| `售后申请` | 退款、退改签、取消、补偿申请 | 恶意退款、临期退款、高额补偿 |
| `投诉` | 用户发起投诉、重复投诉、申请赔付 | 投诉套利、恶意索赔 |
| `出行前核验` | 出发前 T-7/T-1 自动复核 | 出行前状态变更、证件/黑名单复核 |

### 5.1 事件与 source_id 映射

为了贴合参考项目 `RiskCheckRequest(event_type, source_id, user_id, event_data)` 的统一入口，旅游版约定 `source_id` 按事件类型指向不同业务表。

| 事件类型 | source_id 指向 | 业务校验规则 |
|---|---|---|
| `旅游下单` | `OrderInfo.order_id` | 订单存在，且 `order.user_id == request.user_id` |
| `机票预订` | `BookingFlight.booking_id` | 机票预订存在，可反查订单，订单归属用户 |
| `酒店预订` | `BookingHotel.booking_id` | 酒店预订存在，可反查订单，订单归属用户 |
| `签证申请` | `VisaApplication.visa_id` | 签证申请存在，且 `visa.user_id == request.user_id` |
| `支付` | `OrderInfo.order_id` | 订单存在，订单归属用户，校验支付账号和设备信息 |
| `售后申请` | `TravelRefund.refund_id` | 售后单存在，可反查订单，订单归属用户 |
| `投诉` | `TravelComplaint.complaint_id` | 投诉记录存在，可反查订单，订单归属用户 |
| `出行前核验` | `OrderInfo.order_id` | 订单存在，订单归属用户，重新核验旅客证件和黑名单 |

### 5.2 黑名单类型

旅游版黑名单类型在参考项目 `用户 / 地址 / 手机号` 基础上扩展为：

```text
用户 / 手机号 / 护照号 / 身份证号 / 支付账号 / 设备指纹 / IP / 订单
```

前置拦截优先级建议：

```text
用户 -> 护照号/身份证号 -> 支付账号 -> 设备指纹 -> 手机号 -> IP -> 订单
```

命中任一强黑名单时直接返回 `decision=拒绝`，不进入完整 7 步决策流水线；普通观察名单则继续进入规则和模型评估。

## 6. 事件特征提取规则

旅游版继续沿用参考项目 `app/engine/feature.py` 的三大特征族命名方式：

```text
user_*   用户维度特征
order_*  订单/业务单据维度特征
addr_*   目的地/出行地址维度特征
```

其中 `addr_*` 在旅游行业不再表示收货地址，而是表示目的地、酒店城市、航线到达地等位置风险。

## 7. 评分规则与决策设计

系统采用四层风险等级：

```text
低 / 中 / 高 / 极高
```

对应四档决策：

```text
通过 / 标记 / 人工审核 / 拒绝
```

建议决策策略：

| 风险等级 | 决策 | 处理方式 |
|---|---|---|
| 低 | 通过 | 正常放行，记录评估结果 |
| 中 | 标记 | 允许交易，但进入用户画像和后续监控 |
| 高 | 人工审核 | 暂停关键动作，由运营/风控人员审核 |
| 极高 | 拒绝 | 拦截交易，必要时沉淀黑名单和案件 |

评分区间贴合参考项目 `app/engine/decision.py`：

| 分数区间 | 风险等级 | 决策 |
|---|---|---|
| `0 <= score < 30` | 低 | 通过 |
| `30 <= score < 60` | 中 | 标记 |
| `60 <= score < 80` | 高 | 人工审核 |
| `80 <= score <= 100` | 极高 | 拒绝 |

规则评分公式沿用参考项目：

```text
rule_score = min(max(命中规则分) + 3 * (额外命中规则数), 100)
```

若启用 XGBoost，则沿用双轨融合：

```text
final_score = 0.5 * rule_score + 0.5 * ml_score_100
```

一票否决规则不允许被模型低分拉低。只要命中 `risk_level=极高` 的规则，最终结果强制：

```text
final_score >= 90
risk_level = 极高
decision = 拒绝
```

极高规则应具备一票否决能力，例如：

- 护照、身份证、手机号或支付账号命中黑名单。
- 明确黄牛囤票行为。
- 严重证件异常或冒用嫌疑。
- 高风险目的地叠加超大额临期订单。

## 8. 初始规则方向

系统初始化规则建议先落 25 条，字段全部来自 `compute_all_features()` 返回的特征字典，方便直接写入 `risk_rule.rule_condition`。

| 编号 | 规则名 | 事件类型 | 条件特征 | 风险等级 | 分数 | 决策 |
|---|---|---|---|---|---:|---|
| R001 | 拒签历史拦截 | 签证申请 | `user_visa_reject_count_90d >= 2` | 极高 | 95 | 拒绝 |
| R002 | 短期多国签证 | 签证申请 | `user_visa_country_count_30d >= 3` | 高 | 75 | 人工审核 |
| R003 | 高风险目的地 | 通用 | `addr_destination_risk_score >= 85` | 高 | 70 | 人工审核 |
| R004 | 临期高风险目的地下单 | 旅游下单 | `order_days_to_departure <= 7 && order_destination_risk_score >= 70` | 高 | 78 | 人工审核 |
| R005 | 大额跨境游 | 旅游下单 | `order_is_cross_border == 1 && order_total_amount >= 50000` | 高 | 76 | 人工审核 |
| R006 | 超大额旅游订单 | 通用 | `order_total_amount >= 100000` | 极高 | 92 | 拒绝 |
| R007 | 多人团单异常 | 旅游下单 | `order_passenger_count >= 10 && order_total_amount >= 30000` | 高 | 72 | 人工审核 |

## 10. 合规与监管要求

系统设计应遵循以下原则：

1. 最小必要原则  
   仅采集和处理完成旅游服务、交易安全、实名核验、风控识别所必需的数据。

2. 目的限定原则  
   身份证、护照、手机号、支付账号、行踪轨迹等敏感信息，只能用于合同履行、实名核验、交易安全、反欺诈和法定义务履行，不得超范围使用。

3. 敏感个人信息保护  
   身份证、护照、金融账户、行踪轨迹、不满十四周岁未成年人信息等属于敏感个人信息，应采取加密存储、访问控制、脱敏展示、操作审计、授权留痕等措施。

4. 消费者权益保护  
   风控规则不得不合理限制消费者合法权利，不得以风控为由规避退改签、合同履行、投诉处理等法定义务。

5. 可解释与可申诉  
   对人工审核、拒绝、加黑等强影响决策，应保留命中规则、风险特征、评估时间、操作人和案件记录，并提供人工复核与申诉通道。

6. 住宿实名登记合规  
   酒店、住宿类业务涉及实名登记，应按照旅馆业治安管理要求查验旅客有效身份证件，并按规定登记或上传相关信息。

7. 在线旅游经营合规  
   在线旅游经营者应保障旅游者合法权益，规范产品展示、价格、退改、合同、售后和投诉处理，承担产品和服务质量责任。
