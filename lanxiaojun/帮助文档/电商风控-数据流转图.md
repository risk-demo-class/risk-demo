# 电商风控系统 — 数据流转全流程详解

> 本文档用最直白的方式，一步步展示 **一份用户数据** 从浏览器发请求到系统返回结果，经历了哪些函数、哪些表。

## 场景设定

用户 **U001** 在系统里**下单**，订单号 **ORD001**，一个接口请求从头走到尾：

```
POST http://localhost:8000/api/risk/check

Body:
{
  "event_type": "下单",
  "source_id": "ORD001",
  "user_id": "U001"
}
```

---

## 第 0 步：请求到达服务器

```
浏览器 ──HTTP POST──→ Uvicorn ──→ FastAPI
```

Uvicorn（Python Web 服务器）收到 HTTP 报文，解析后交给 FastAPI。

**代码位置：** `scripts/main.py`

```python
app = FastAPI(title="电商风控系统", ...)
app.include_router(risk_router)   # ← 注册风控检查路由
```

FastAPI 匹配 URL `/api/risk/check` + 方法 `POST`，找到对应的处理函数。

**详细匹配过程在下文中Fastapi调用过程**

## 第 1 步：Router 层 — 接客

**文件：** `app/routers/risk.py`

**函数：** `api_risk_check()`

```python
@risk_router.post("/check", response_model=RiskCheckResponse)
async def api_risk_check(request: RiskCheckRequest, db: AsyncSession = Depends(get_db_async)):
    return await process_event(db, request)
```

这一步做两件事：

### ① Pydantic 自动校验

FastAPI 自动把 JSON Body 转换成 `RiskCheckRequest` 对象，同时校验：
- `event_type` 必须是 `"下单"` / `"支付"` / `"售后申请"` / `"物流投诉"` 之一
- `source_id` 和 `user_id` 不能为空

### ② 拿数据库连接

`Depends(get_db_async)` 从连接池拿一个 `AsyncSession`，整个请求共用。

## 第 2 步：Service 层 — 事件处理管道

**文件：** `app/service/event.py`

**函数：** `process_event()` — 总调度员

```python
async def process_event(db: AsyncSession, request: RiskCheckRequest) -> RiskCheckResponse:
    # 1. 业务实体校验
    await validate_risk_check_request(db, request)

    # 2. 补全 order_id / receive_id
    request = await _enrich_request(db, request)

    # 3. 黑名单前置检查
    blocked = await _check_all_blacklists(db, request)
    if blocked is not None:
        return _blacklist_reject(request, blocked)

    # 4. 决策引擎 7 步
    return await run_risk_check(db, request)
```

### 2.1 校验数据合法性

**文件：** `app/service/validator.py`

**函数：** `validate_risk_check_request()`

```python
async def validate_risk_check_request(db, request):
    await ensure_user_exists(db, request.user_id)               # ①
    await ensure_source_matches_event_type(db, request)         # ②
    if request.event_type in ("下单", "支付"):
        await ensure_order_belongs_to_user(db, order_id, request.user_id)  # ③
```

| 检查项 | 用途 | 执行的 SQL |
|--------|------|-----------|
| ① 用户存在 | U001 是不是真用户 | `SELECT COUNT(*) FROM user_info WHERE user_id='U001'` |
| ② source_id 匹配 | "下单"事件应该传订单号 ORD001 | `SELECT COUNT(*) FROM order_info WHERE order_id='ORD001'` |
| ③ 防止越权 | 防止张三拿李四的订单查 | `SELECT user_id FROM order_info WHERE order_id='ORD001'` → 必须是 U001 |

> 任何一项失败 → 抛 `HTTPException`，返回 4xx 错误，**后面的都不跑了**。

### 2.3 黑名单拦截

**文件：** `app/service/event.py` + `app/service/case.py`

**函数：** `_check_all_blacklists()` → `check_blacklist()`

```python
async def _check_all_blacklists(db, request):
    # 优先级：用户 > 地址 > 手机号（短路）
    if await check_blacklist(db, "用户", request.user_id):     → 查用户黑名单
        return "用户"
    if request.receive_id and await check_blacklist(db, "地址", request.receive_id):
        return "地址"
    if request.receive_id:
        # 查手机号
        # SELECT receiver_phone FROM receive_info WHERE receive_id='REC001'
        if row and await check_blacklist(db, "手机号", row.receiver_phone):
            return "手机号"
    return None  # 没撞黑
```

**查黑名单函数：**

```python
async def check_blacklist(db, blacklist_type, value):
    # SELECT * FROM risk_blacklist
    # WHERE blacklist_type='用户' AND blacklist_value='U001'
    bl = await db.execute(select(RiskBlacklist)...)
    if not bl:
        return False                         # 不在黑名单
    if bl.expire_time and bl.expire_time < datetime.now():
        return False                         # 过期了
    return True                              # 命中黑名单
```

> 撞黑 → 直接返回拒绝（不进引擎，不写库）：
> ```python
> def _blacklist_reject(request, blocked_by):
>     return RiskCheckResponse(
>         final_score=100, decision="拒绝", blocked_by=blocked_by
>     )
> ```

> 没撞黑 → 进入核心决策引擎。

## 第 3 步：Engine 层 — 7 步决策流水线

**文件：** `app/engine/decision.py`

**函数：** `run_risk_check()` — 最核心函数

```python
async def run_risk_check(db, request):
    # Step 1: 准备上下文
    ctx = _build_context(request)
    await _enrich_receive_id(db, ctx)

    # Step 2: 创建事件记录
    event_id = _create_event_record(db, ctx)

    # Step 3-4: 计算特征 + 保存快照
    features = await _compute_features(db, ctx)
    _save_feature_snapshot(db, ctx, features)

    # Step 5: 加载 + 匹配规则
    rules = await _evaluate_rules(db, ctx, features)

    # Step 6: 算决策（评分 + 一票否决 + XGBoost）
    final_score, risk_level, decision, ml_score, ml_decision = \
        _calculate_decision(rules, features)

    # Step 7: 落库 + 响应
    await db.flush()
    assessment_id = await _save_assessment(db, ctx, rules, ...)
    await _maybe_create_case(db, assessment_id, ctx, rules, ...)
    await _update_user_profile(db, ctx, features, ...)
    await db.commit()

    return _build_response(ctx, features, rules, ...)
```

### Step 1：准备上下文

**函数：** `_build_context()` + `_enrich_receive_id()`

把数据打包成 `_RiskCheckContext` 对象，后面的步骤共用：

```
_RiskCheckContext {
    request:   原始请求
    user_id:   "U001"
    order_id:  "ORD001"
    receive_id:"REC001"
    event_id:  ""        ← 下一歩才生成
}
```

### Step 3：计算 25 维特征

**文件：** `app/engine/feature.py`

**函数：** `compute_all_features()` → 内部调 3 组子函数

```python
async def compute_all_features(db, user_id, order_id, receive_id):
    features = {}
    features.update(await compute_user_features(db, user_id))         # 14 个
    if order_id:
        features.update(await compute_order_features(db, order_id))   # 8 个
    if receive_id:
        features.update(await compute_address_features(db, receive_id)) # 3 个
    return features   # 共 25 个
```

#### 用户维度（14 个特征）

| 特征名 | 含义 | SQL 查询 |
|--------|------|---------|
| `user_total_orders` | 历史订单总数 | `SELECT COUNT(*) FROM order_info WHERE user_id='U001'` |
| `user_orders_30d` | 近 30 天订单数 | 同上 + 时间条件 |
| `user_orders_7d` | 近 7 天订单数 | 同上 + 时间条件 |
| `user_total_amount` | 历史总消费 | `SUM(OrderDetail.final_amount) JOIN OrderInfo` |
| `user_avg_order_amount` | 平均每单金额 | 总金额 / 总单数 |
| `user_max_order_amount` | 单笔最大金额 | `MAX(...)` |
| `user_refund_count` | 退款次数 | `SELECT COUNT(*) FROM postsale` |
| `user_postsale_count` | 售后次数 | 同上 |
| `user_refund_rate` | 退款率 | 退款次数 / 总订单数 |
| `user_postsale_rate` | 售后率 | 同上 |
| `user_refund_amount` | 累计退款金额 | `SUM(refund_amount)` |
| `user_cancel_count` | 取消订单次数 | `SELECT COUNT(*) FROM order_info WHERE status='取消'` |
| `user_complaint_count` | 投诉次数 | `SELECT COUNT(*) FROM logistics_complaints_record` |
| `user_address_count` | 使用过的地址数 | `SELECT COUNT(*) FROM receive_info` |

#### 订单维度（8 个特征）

| 特征名 | 含义 |
|--------|------|
| `order_total_amount` | 本单总金额 |
| `order_item_count` | 本单商品件数 |
| `order_sku_count` | 本单不同 SKU 数量 |
| `order_discount_amount` | 折扣金额 |
| `order_discount_rate` | 折扣率 |
| `order_pay_interval_sec` | 下单到支付的间隔（秒）— 太快可能是机器刷单 |
| `order_is_night` | 是否深夜下单（23:00-06:00）— 风险信号 |
| `order_category_count` | 本单涉及的商品品类数 |

#### 地址维度（3 个特征）

| 特征名 | 含义 |
|--------|------|
| `addr_total_count` | 这个地址被用过几次 |
| `addr_province_count` | 该用户换过几个省收货 |
| `addr_is_new` | 这个地址是不是第一次用（新地址风险高） |

### Step 5：加载并匹配规则

**文件：** `app/engine/rule.py`

**函数：** `load_enabled_rules()` + `match_rules()`

```python
# 从数据库加载启用的规则
rules = await load_enabled_rules(db, event_type="下单")
# → SELECT * FROM risk_rule WHERE is_enabled=1
#     AND (event_type='下单' OR event_type='通用')

# 逐条匹配
def match_rules(rules, features):
    hits = []
    for rule in rules:
        condition = rule.condition_dict   # 解析 JSON 条件
        if evaluate_condition(condition, features):   # 用特征值判断
            hits.append(RuleHitResult(rule))           # 命中就记录
    return hits
```

#### 数据库预置规则示例（共 30 条）

| 规则ID | 规则名 | 条件表达式 | 分值 | 级别 |
|--------|--------|-----------|------|------|
| R001 | 单笔大额 | `order_total_amount >= 10000` | 70 | 高 |
| R002 | 单笔超大额 | `order_total_amount >= 50000` | 95 | 极高 |
| R005 | 深夜下单 | `order_is_night == 1` | 30 | 中 |
| R008 | 短时多单 | `user_orders_7d >= 10` | 60 | 高 |
| R015 | 高退款率 | `user_refund_rate >= 0.8` | 95 | 极高 |

#### 规则条件求值引擎

```python
def evaluate_condition(condition, features):
    # 单条件
    # {"field": "order_total_amount", "op": ">=", "value": 10000}
    # → features["order_total_amount"]=588, 588>=10000 → False

    # 组合条件（AND/OR 递归）
    # {"and": [{条件1}, {条件2}]}
    # → 条件1 AND 条件2

    # 支持的运算符:
    # > >= < <= == != in not_in between
    actual = features.get(condition["field"])
    return _compare(actual, condition["op"], condition["value"])
```

> U001 这单 588 块 + 凌晨下单 → 命中 R005（30 分）+ 某个 20 分规则 = **命中 2 条**

### Step 6：计算评分与决策（核心算法）

**函数：** `_calculate_decision()` — 分 4 小步

#### ① 算规则分

```python
def calculate_final_score(hits):
    max_score = max(h.risk_score for h in hits)   # 最高分
    extra_count = len(hits) - 1                    # 额外命中
    bonus = 3 * extra_count                        # 每条额外 +3
    return min(max_score + bonus, 100)

# U001：最高分 30, 命中 2 条
# = 30 + 3×(2-1) = 33
```

#### ② 检查一票否决

```python
def check_veto(hits):
    return any(h.risk_level == "极高" for h in hits)

# U001 没有命中"极高"级别 → False
```

#### ③ 算 ML 分（XGBoost）

**文件：** `app/engine/ml_model.py`

**函数：** `predict()`

```python
# 25 个特征按固定顺序传给 XGBoost 模型
# 模型输出 P(拒绝) = 0.2（20%的概率会被拒绝）

ml_score_100 = _ml_prob_to_risk_score(0.2)
# 校准公式: 100 × (1 - e^(-3 × 0.2))
#         = 100 × (1 - 0.549)
#         = 45 分
```

校准曲线（把概率映射到 0-100 分）：

| P(拒绝) | 风险分 | 含义 |
|---------|-------|------|
| 0.0 | 0 | 无风险 |
| 0.1 | 26 | 低风险 |
| 0.3 | 59 | 中风险 |
| 0.5 | 78 | 中高风险 |
| 0.7 | 90 | 高风险 |
| 0.9 | 97 | 极高风险 |

#### ④ 双轨融合

```python
# 权重: 规则 0.5, ML 0.5（从 config.py 配置）
final_score = 0.5 × 规则分(33) + 0.5 × ML分(45)
            = 16.5 + 22.5
            = 39

risk_level = _score_to_level(39)
# < 30 → 低    [通过]
# < 60 → 中    [标记]   ← U001 是 39 分
# < 80 → 高    [人工审核]
# ≥ 80 → 极高  [拒绝]

decision = _score_to_decision(39)
# → "标记"（放行但系统标记一下）
```

**阈值配置**（`app/config.py`）：

```
RISK_PASS_THRESHOLD    = 30   # <30 → 通过
RISK_MARK_THRESHOLD    = 60   # <60 → 标记
RISK_REVIEW_THRESHOLD  = 80   # <80 → 人工审核
                             # ≥80 → 拒绝
```

> 如果有"极高"级别规则命中 → 强制 decision="拒绝"，分数抬到 ≥90，XGBoost 再低也没用。

# Fastapi调用过程

---
  匹配过程（用大白话讲）

  当请求 POST http://localhost:8000/api/risk/check 到达时，FastAPI 内部做了这件事：

1. 步骤 ①：拿到 URL 和方法

  	URL:    /api/risk/check
  	方法:   POST

2. 步骤 ②：看路由器前缀

  	FastAPI 把 prefix 当成"前缀匹配"。它去查所有已注册的路由器，发现：

  	risk_router 的前缀是 /api/risk

  	当前 URL /api/risk/check 以前缀 /api/risk 开头 → 匹配上了。

3. 步骤 ③：去掉前缀，匹配相对路径

  	去掉前缀 /api/risk 后，剩下 check。

  	FastAPI 在 risk_router 内部查找：
  - 有没有 POST 方法 + /check 路径 的处理函数？
  - 找到 api_risk_check 函数 → 就是它了！

4. 步骤 ④：自动解析参数

  	FastAPI 发现这个函数需要两个参数：

  ```
  async def api_risk_check(
        	request: RiskCheckRequest,      # 从 HTTP Body 解析 JSON
        	db: AsyncSession                # 从依赖注入拿数据库连接
    	):
  ```

  - request: RiskCheckRequest → FastAPI 自动把 JSON Body 转成 Pydantic 对象，顺便校验字段类型对不对
  - db: AsyncSession = Depends(get_db_async) → FastAPI 自动调用 get_db_async() 从连接池拿一个数据库 session

5. 步骤 ⑤：调用函数

  	所有参数都准备好了，FastAPI 调用：

​          api_risk_check(request=RiskCheckRequest对象, db=数据库session对象)

  	然后等着它返回结果，再自动把返回的 Python 对象转成 JSON 作为 HTTP 响应发回去。
