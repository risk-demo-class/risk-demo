## 一、一句话说清这个系统干什么

```
用户下单/支付/售后/投诉
         │
         ▼
   ┌─────────────┐
   │  风控系统    │  ← 几百毫秒算出风险分
   └──────┬──────┘
          │
    ┌─────┴─────┐
    │           │
  通过        拒绝
  (放行)      (拦截)
```

**核心回答一个问题：** "这笔交易是正常的，还是黑产/羊毛党/欺诈？"

---

## 二、特征 — 系统"看"什么

特征是系统判断风险的**原材料**。系统不会凭空判断，它先去数据库查一堆数据，算成**25 个数字**，这就是"特征"。

### 2.1 25 个特征分 3 组

#### 👤 用户特征（14 个）— 查这个人的历史行为

| 特征名 | 含义 | 业务直觉 |
|--------|------|---------|
| `user_total_orders` | 一共下过多少单 | 新用户 vs 老客户 |
| `user_orders_30d` | 最近 30 天下几单 | 是不是忽然密集下单 |
| `user_avg_order_amount` | 平均每单多少钱 | 平时花多少 |
| `user_refund_rate` | 退款率 | 是不是老退款 |
| `user_cancel_count` | 取消过几单 | 是不是下单又取消 |
| `user_complaint_count` | 投诉过几次 | 是不是刺头用户 |
| `user_address_count` | 用过几个地址 | 正常人就 1-2 个地址 |

**举例：**
```
用户 U001:  user_total_orders=15,  user_refund_rate=0.067,  user_address_count=2
用户 RISK01: user_total_orders=50,  user_refund_rate=0.85,   user_address_count=8
           ↑ 正常用户              ↑ 退款率 85%，严重异常    ↑ 8 个地址，异常
```

#### 📦 订单特征（8 个）— 查这笔订单本身

| 特征名 | 含义 | 业务直觉 |
|--------|------|---------|
| `order_total_amount` | 这单多少钱 | 大额订单风险高 |
| `order_item_count` | 几件商品 | 异常批量 |
| `order_discount_rate` | 折扣比例 | 是不是用了大额优惠券 |
| `order_pay_interval_sec` | 下单到支付隔几秒 | **机器刷单：3 秒付完，正常人：几分钟** |
| `order_is_night` | 是否凌晨下单（0/1） | 凌晨下单 = 高风险信号 |

**举例：**
```
正常用户下单: order_total_amount=256,  order_pay_interval_sec=380(6分钟),  order_is_night=0
机器刷单:     order_total_amount=9999, order_pay_interval_sec=3(3秒!),     order_is_night=1
           ↑ 金额大但正常          ↑ 3 秒付款（明显机器）            ↑ 凌晨 3 点
```

#### 📍 地址特征（3 个）— 查收货地址

| 特征名 | 含义 | 业务直觉 |
|--------|------|---------|
| `addr_total_count` | 这个地址被用过几次 | 新地址风险高 |
| `addr_province_count` | 这个用户换过几个省收货 | 正常人就 1 个省 |
| `addr_is_new` | 这个地址是不是第一次用（0/1） | 新地址 = 高风险 |

### 2.2 特征是怎么算出来的？

系统不靠猜，每个特征都是**真实去数据库查**出来的：

```sql
-- 比如算 "这个用户最近 30 天下几单"
SELECT COUNT(*)
FROM order_info
WHERE user_id = 'U001'
  AND create_time >= NOW() - INTERVAL 30 DAY;

-- 比如算 "这个用户退款率多少"
SELECT COUNT(*) FROM postsale WHERE user_id = 'U001'   -- 退款次数
/ 
SELECT COUNT(*) FROM order_info WHERE user_id = 'U001'  -- 总订单数

-- 比如算 "这笔是不是深夜下单"
SELECT HOUR(create_time) FROM order_info WHERE order_id = 'ORD001'
-- 如果在 23:00-06:00 之间 → order_is_night = 1
```

**一句话：** 25 个特征 = 系统对"这个人、这单、这个地址"的全面画像。

## 三、规则 — 系统怎么"判断"

特征算出来了，接下来需要用**规则**来判断"这个特征值是否异常"。

### 3.1 规则的写法

每条规则就是一个 **JSON 条件表达式**，存在数据库里：

```json
{
  "field": "order_total_amount",
  "op": ">=",
  "value": 10000
}
```

意思：**"如果这笔订单金额 >= 10000 元，这条规则就命中。"**

### 3.2 30 条预置规则

数据库里预置了 30 条规则，分 6 大类（你也可以通过 API 随便加）：

| 类别 | 规则数 | 举例 |
|------|:------:|------|
| **订单欺诈** | 5 条 | R001: 金额 ≥ 5000 → 标记（中风险）<br>R002: 金额 ≥ 10000 → 拒绝（极高风险）|
| **支付风险** | 4 条 | R006: 7 天 ≥ 10 单 → 人工审核<br>R007: 30 天 ≥ 30 单 → 拒绝（机器刷单）|
| **账户风险** | 4 条 | R010: 退款率 ≥ 30% → 人工审核<br>R015: 退款率 ≥ 80% → 拒绝（恶意退款）|
| **售后滥用** | 3 条 | R012: 退款次数 ≥ 5 → 人工审核 |
| **地址风险** | 4 条 | R017: 换过 ≥ 3 个省份 → 标记 |
| **物流风险** | 3 条 | R022: 投诉次数 ≥ 3 → 标记 |
| **通用规则** | 7 条 | 跨事件类型生效 |

### 3.3 规则引擎怎么工作

```python
# 拿一个用户的数据来举例：
features = {
    "user_total_orders": 15,      # 老客户，15 单
    "user_refund_rate": 0.067,    # 退款率 6.7%，正常
    "order_total_amount": 588.00, # 588 块，正常
    "order_is_night": 1,          # 凌晨下的单！
    "order_pay_interval_sec": 30, # 30 秒付完，很快
}

# 逐条规则判断（只展示部分）：
# R001: order_total_amount >= 5000  → 588 < 5000 → 未命中
# R002: order_total_amount >= 10000 → 588 < 10000 → 未命中
# R005: order_is_night == 1         → 1 == 1 → ✅ 命中！（凌晨下单，30 分）
# R006: user_orders_7d >= 10        → 假设 7 天 3 单 → 未命中
# R008: order_pay_interval_sec < 60 → 30 < 60 → ✅ 命中！（付款太快，20 分）

# 最终命中 2 条规则：
#   R005: 30 分（凌晨下单）
#   R008: 20 分（付款太快）
```

### 3.4 支持的条件运算符

| 运算符 | 示例 | 含义 |
|--------|------|------|
| `>` / `>=` | `">= 5000"` | 金额大于等于 5000 |
| `<` / `<=` | `"< 60"` | 秒数小于 60 |
| `==` / `!=` | `"== 1"` | 是否等于（比如是否深夜） |
| `in` | `"in [3,5,7]"` | 是否在列表里 |
| `between` | `"between [3000,8000]"` | 是否在区间内 |
| `and` / `or` | 嵌套组合 | 多个条件同时/任一满足 |

**复杂规则举例：**
```json
// R030：高退款 + 高消费 + 多地址 = 极高风险羊毛党
{
  "and": [
    {"field": "user_refund_rate", "op": ">=", "value": 0.5},
    {"field": "user_avg_order_amount", "op": ">=", "value": 2000},
    {"field": "user_address_count", "op": ">=", "value": 3}
  ]
}
// 三个条件都满足 → 命中，说明是高消费+高退款+多地址的"专业羊毛党"
```

## 四、决策 — 系统最终"决定"什么

规则命中后，系统进入**评分决策阶段**，这是最后一步。

### 4.1 评分公式

```python
规则分 = max(各命中规则的分值) + 3 × (额外命中数)
上限 100
```

**举例：**
```
命中 2 条规则，最高分 30：
规则分 = 30 + 3 × (2 - 1) = 33 分

命中 3 条规则，最高分 70：
规则分 = 70 + 3 × (3 - 1) = 76 分

命中 1 条规则，最高分 95（一票否决）：
规则分 = 95 + 3 × 0 = 95 分（直接拒绝）
```

### 4.2 双轨融合（规则 + AI）

系统不只用规则，**还加了一个 XGBoost AI 模型**：

```
规则引擎得分     ──┐
                 ├── 0.5 × 规则分 + 0.5 × AI分 = 最终分
XGBoost AI得分 ---┘
```

**为什么加 AI？**
- 规则是人写的，**总有没覆盖到的欺诈模式**
- AI 从历史数据里**自动学习"什么样的特征组合意味着高风险"**
- 规则 + AI 互补，比单独用任一更准

**AI 输出校准：**
```python
# XGBoost 输出 P(拒绝) ∈ [0,1]，比如 0.2 表示"20% 概率是高风险"
# 转成 0-100 分（sigmoid 校准）：
AI分 = 100 × (1 - e^(-3 × 0.2)) = 45 分
# 曲线：低概率压得更低（减少误报），高概率推得更高（强化拦截）
```

### 4.3 一票否决（最高优先级）

如果有任何一条规则的级别是 **"极高"**，强制拒绝，AI 再怎么说"没问题"也没用：

```python
# 场景：R002（单笔 ≥ 10000）命中，级别"极高"
规则分 = 95
AI 分  = 0.2  → 校准后 45
融合分 = 0.5 × 95 + 0.5 × 45 = 70   ← 原本是"人工审核"

# 一票否决触发：
decision = "拒绝"    # 强制改成拒绝
final_score = 90     # 强制抬到 90
# ← 不会被 AI 的低分拉低
```

**业务含义：** 某些红线规则一旦触发，不管 AI 怎么判断，必须拒绝。

### 4.4 四档决策

| 分数范围 | 决策 | 业务动作 | 是否建案 |
|---------|------|---------|:-------:|
| 0-29 | **通过** | 正常放行，不留底 | ❌ |
| 30-59 | **标记** | 放行但系统记录，下次再犯可能升级 | ❌ |
| 60-79 | **人工审核** | 不放行，等客服人工判断 | ✅ |
| 80-100 | **拒绝** | 直接拒绝，系统自动关案 | ✅ |

### 4.5 完整决策示例

```python
# 用户 U001 凌晨下单 588 元，30 秒付款
# 命中 2 条规则：
#   R005（凌晨下单）→ 30 分
#   R008（付款太快）→ 20 分

# 一票否决检查：无"极高"级别 → 不触发

# 规则分：30 + 3×1 = 33
# AI 分：0.2 → 校准后 45 分

# 双轨融合：0.5 × 33 + 0.5 × 45 = 39 分

# 最终决策：39 < 60 → "标记"
# 放行，但系统记录"这个用户有点可疑"
```

## 六、你能用这个系统做什么

| 你想干什么 | 怎么做 |
|-----------|--------|
| **加一条规则** | `curl -X POST /api/rules` 传一个 JSON 条件，立刻生效，不用重启 |
| **关掉一条规则** | `curl -X PUT /api/rules/R001/toggle` 一键关闭 |
| **训练 AI 模型** | `python scripts/train_xgb_model.py` |
| **查用户的画像** | `curl /api/profile/U001` 查看该用户的 25 维特征和风险等级 |
| **看哪些规则经常命中** | 打开仪表盘 `/` → 规则命中分布 |
| **查历史评估** | `curl /api/assessments?decision=拒绝` 找所有被拒记录 |

## 七、一句话总结

> **25 个特征描述这个人+这单+这个地址 → 30 条规则判断哪些特征异常 → XGBoost AI 模型做第二道判断 → 规则+AI 融合评分 → 最终决定"通过/标记/人工审核/拒绝"。**
>
> 整个过程几百毫秒，全靠规则和 AI 自动完成，不需要人参与。
