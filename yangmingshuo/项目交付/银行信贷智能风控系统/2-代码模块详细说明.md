# 银行信贷智能风控系统——代码模块详细说明

## 1. 项目概述

本项目是一个可运行的银行信贷风险控制教学系统，覆盖 **信用卡申请、贷款申请、转账、登录** 四类业务事件。系统使用 FastAPI 提供网页和接口，使用 SQLAlchemy 操作数据库，通过特征工程提取客户风险信号，再由规则引擎评分、产生风险决策；高风险结果自动进入案件管理。同时项目提供 XGBoost 模型训练脚本，用 AUC 和 F1 验证模型效果。

系统的核心链路是：

```text
业务数据 → 事件校验 → 事件分流 → 特征计算 → 黑名单检查
        → 规则匹配 → 风险评分 → 风险决策 → 评估落库 → 高风险建案
```

项目根目录为：

```text
E:\项目交付\银行信贷智能风控系统
```

## 3. 根目录文件说明

### 3.1 `run_app.py`——一键启动入口

这是项目的主启动文件。它首先检查 `data/bank_risk.db` 是否存在。如果数据库不存在，会依次执行建库脚本和造数脚本；随后通过 Uvicorn 启动 FastAPI 应用。

执行命令：


## 4. `app` 核心应用模块

### 4.1 `app/config.py`——全局配置

该文件集中定义三类配置：

- `DATABASE_URL`：默认值为 `sqlite:///./data/bank_risk.db`，也允许用同名环境变量覆盖。
- `BLACKLIST_TYPES`：设备指纹、IP、银行卡号、身份证号。
- `EVENT_TYPES`：信用卡申请、贷款申请、转账、登录。

集中配置可防止各模块分别写死相同常量，后续增加事件类型时也更容易维护。

### 4.2 `app/database.py`——数据库连接层

该文件负责创建 SQLAlchemy 的三个基础对象：

- `Base`：所有 ORM 模型的父类。
- `engine`：数据库连接引擎。
- `SessionLocal`：数据库会话工厂。

项目启动时自动创建 `data` 目录。SQLite 使用 `check_same_thread=False`，使数据库连接能在 FastAPI 的请求线程中正常使用。

### 4.3 `app/models_business.py`——8 张银行业务表

该模块使用 SQLAlchemy 2.0 类型化 ORM 描述银行业务数据。

#### `UserInfo` 客户信息表

保存客户号、姓名、身份证摘要、信用分、注册时间、KYC 等级和月收入。身份证只保存 SHA-256 摘要，不保存明文。信用分、KYC、注册时间和收入是贷款准入的重要基础信息。

#### `BankCard` 银行卡表

保存银行卡编号、所属客户、卡号摘要、银行代码、卡类型和授信额度。通过 `user_id` 关联客户。一个客户可以拥有多张银行卡。

#### `Transaction` 转账交易表

数据库表名为 `bank_transaction`，保存付款卡、收款卡、金额、渠道、设备、IP、地区和交易时间。它为大额交易、夜间交易、异地交易及交易频率特征提供数据。

#### `LoanApplication` 贷款申请表

保存申请号、客户号、申请金额、期限、用途、申报月收入、负债率和申请时间。该表是信贷风控和模型训练的核心业务表。

#### `LoginLog` 登录日志表

保存登录流水号、客户、设备、IP、地区、是否成功和登录时间。用于识别撞库、暴力破解、夜间登录和账户接管风险。

#### `DeviceFingerprint` 设备指纹表

保存设备与客户的绑定关系、指纹摘要、首次/最近出现时间、操作系统和浏览器。一个客户短期关联过多设备可能意味着群控、账号共享或账户被盗。

#### `IpGeolocation` IP 地理信息表

保存 IP 的国家、省、市、运营商，以及代理和 Tor 标记。后续可扩展代理 IP、Tor 出口、境外 IP 和登录地突变规则。

#### `BlacklistExtra` 扩展黑名单表

黑名单支持设备指纹、IP、银行卡号和身份证号四种类型，记录黑名单值、原因和失效时间。命中黑名单时，当前流水线直接叠加 100 风险分并拒绝。

### 4.4 `app/models_risk.py`——风险结果表

#### `RiskAssessment` 风险评估表

每执行一次风控检查，就写入一条评估记录，保存：

- 评估号、事件类型、业务流水号、客户号；
- 最终风险分、风险等级和决策；
- 命中规则 JSON；
- 特征快照 JSON；
- 创建时间。

保存规则与特征快照可以支持结果复现、风险解释、审计和申诉复核。

#### `RiskCase` 风险案件表

当决策为“人工审核”或“拒绝”时自动生成案件。案件记录包含案件号、关联评估号、状态、负责人和创建时间。当前默认状态为“待审核”，负责人为“未分配”。

## 5. 特征工程模块

文件：`app/engine/feature.py`

该模块按银行行业重新设计了三大特征族：**客户综合特征、信贷申请特征、交易/登录行为特征**。

### 5.1 `compute_user_features(db, user_id)`

计算客户层的通用特征，其他事件特征都以它为基础：

| 特征 | 计算方式 | 风险含义 |
|---|---|---|
| `credit_score` | 客户表信用分 | 分数越低，违约或欺诈风险越高 |
| `kyc_level` | 客户 KYC 等级 | 等级不足说明身份核验不充分 |
| `account_age_days` | 当前时间减注册时间 | 新账户缺少稳定历史，风险相对较高 |
| `loan_application_count` | 客户累计贷款申请数 | 多次申请可用于识别多头申请倾向 |
| `avg_debt_ratio` | 历史贷款平均负债率 | 衡量客户整体债务压力 |
| `login_fail_24h` | 最近 24 小时失败登录次数 | 识别撞库、暴力破解和账户接管 |
| `device_count` | 客户关联设备数量 | 设备过多可能是群控或账号共享 |
| `txn_count_24h` | 客户银行卡 24 小时交易笔数 | 识别短时高频资金活动 |
| `txn_amount_24h` | 24 小时交易金额合计 | 识别资金集中转出 |

函数首先查客户及其所有银行卡，再通过聚合 SQL 查询贷款、登录、设备和交易数据，最后返回统一的 Python 字典。

### 5.2 `compute_loan_features(db, source_id)`

贷款申请特征族。先通过贷款流水号查到贷款和客户号，再调用客户通用特征，并追加：

- `loan_amount`：贷款金额；
- `term_months`：贷款期限；
- `debt_ratio`：本次申请的负债率；
- `loan_income_multiple`：贷款金额 ÷ 月收入，用于衡量申请金额是否明显超过偿付能力。

函数返回 `(user_id, features)`，使业务层同时获得客户身份和特征字典。

### 5.3 `compute_transaction_features(db, source_id)`

交易特征族。通过交易流水找到付款卡，再由银行卡找到客户，追加：

- `txn_amount`：本次转账金额；
- `night_transaction`：交易发生在 0—6 点时为 1；
- `cross_region`：交易地区不在北京、上海、广东、浙江示例常用地区时为 1。

这些特征用于识别大额、夜间和异常地域转账。

### 5.4 `compute_login_features(db, source_id)`

登录行为特征族。通过登录流水获得客户号，在通用特征上追加：

- `login_success`：本次登录是否成功；
- `night_login`：是否为凌晨登录。

结合通用特征中的 `login_fail_24h` 和 `device_count`，可以识别连续失败、新设备群控和账户接管迹象。

## 6. 规则引擎

文件：`app/engine/rule.py`

`RULES` 中定义了 10 条银行行业规则。每条规则的结构是：

```text
(规则编号, 规则名称, 特征字段, 比较符, 阈值, 风险分)
```

| 编号 | 规则 | 条件 | 分数 |
|---|---|---|---:|
| R001 | 低信用评分 | `credit_score < 550` | 30 |
| R002 | KYC 等级不足 | `kyc_level < 2` | 35 |
| R003 | 高负债率 | `debt_ratio > 0.65` | 40 |
| R004 | 贷款金额超过月收入 12 倍 | `loan_income_multiple > 12` | 35 |
| R005 | 24 小时登录失败过多 | `login_fail_24h >= 5` | 35 |
| R006 | 设备数量异常 | `device_count > 4` | 25 |
| R007 | 大额转账 | `txn_amount > 50000` | 45 |
| R008 | 夜间交易 | `night_transaction == 1` | 20 |
| R009 | 异地交易 | `cross_region == 1` | 25 |
| R010 | 新账户申请信贷 | `account_age_days < 30` | 30 |

`match_rules(features)` 建立比较符到 Lambda 函数的映射，遍历全部规则；只有特征字典包含相应字段且条件为真时才记录命中。返回内容包含规则号、规则名和风险分。

规则是按事件自然适配的。例如贷款特征没有 `txn_amount`，因此不会错误命中大额转账规则；交易事件没有 `debt_ratio`，也不会命中贷款负债率规则。

## 7. 服务层与完整 Pipeline

### 7.1 `app/service/validator.py`

`validate_event(db, event_type, source_id)` 完成入口校验：

1. 判断事件是否属于系统支持的四类事件；
2. 对贷款、转账和登录事件，依据业务流水号查询对应 ORM 表；
3. 记录不存在时抛出 `ValueError`，阻止无效数据进入后续计算。

信用卡申请当前以客户号直接计算客户特征，所以不查询独立的信用卡申请表。

### 7.2 `app/service/event.py`

`process_event(db, event_type, source_id, user_id=None)` 是项目最重要的风控总入口，也就是完整 pipeline。

执行步骤如下：

1. 调用 `validate_event` 校验事件和流水号。
2. 根据事件类型分流：贷款调用 `compute_loan_features`，转账调用 `compute_transaction_features`，登录调用 `compute_login_features`，信用卡申请调用 `compute_user_features`。
3. 使用客户号和流水号查询扩展黑名单。
4. 调用 `match_rules` 获取命中规则。
5. 将规则分累加；命中黑名单额外加 100 分；最终分限制在 0—100。
6. 按阈值形成决策：

```text
score >= 80：拒绝
score >= 50：人工审核
score >= 25：关注
score < 25：通过
```

7. 同步产生风险等级：极高、高、中、低。
8. 生成唯一评估号，把结果、规则和特征写入 `risk_assessment`。
9. “人工审核”或“拒绝”结果自动写入 `risk_case`。
10. 提交事务并返回评估对象。

## 9. 数据初始化与生成脚本

### 9.1 `scripts/init_db.py`

导入业务和风险 ORM，使全部表注册到 SQLAlchemy 元数据，然后调用 `Base.metadata.create_all(engine)` 创建数据库表。当前共创建 10 张表：8 张业务表和 2 张风险表。

执行：

```powershell
python scripts/init_db.py
```

### 9.2 `scripts/gen_business_data.py`

该脚本使用固定随机种子 `20260812`，因此每次运行都能得到结构一致、可复现的数据。默认生成 160 个客户，其中前 35 个被设计为高风险样本。

高风险样本具有多个真实可解释的风险信号：

- 信用分 350—540；
- 注册仅 2—20 天；
- 部分客户 KYC 等级为 1；
- 负债率 0.68—0.95；
- 贷款金额为月收入 14—24 倍；
- 24 小时内有 6 次失败登录；
- 部分客户关联 5 台设备；
- 转账金额 6 万—16 万；
- 凌晨 2 点发生境外转账。

正常样本则使用较高信用分、较长账户年龄、较低负债率、正常申请金额和日间境内交易，形成清晰的训练与演示对照。

脚本还生成 60 个 IP、银行卡、设备、登录日志和 8 条扩展黑名单。运行前会清空 8 张业务表，保证重复执行不会因主键重复而失败。风险评估和案件表不会被清空，因此重复运行风险检查会累积历史记录。

执行：

```powershell
python scripts/gen_business_data.py
```

## 10. 风控验收脚本

文件：`scripts/run_risk_check.py`

该脚本不是训练模型，而是用固定样本验证规则风控完整链路。它调用与网页相同的 `process_event`，依次检查：

- `L0001`：高风险贷款；
- `T0001`：高风险转账；
- `LG00010`：高风险登录；
- `L0100`：正常贷款对照样本。

高风险样本会输出 `100 极高 拒绝` 和多个规则，正常样本输出 `0 低 通过`。每次执行也会新增风险评估和风险案件，所以随后打开网页即可看到相应记录。

执行：

```powershell
python scripts/run_risk_check.py
```

## 11. XGBoost 模型训练

文件：`scripts/train_xgb_model.py`

### 11.1 训练数据

脚本 JOIN `loan_application` 和 `user_info`，每条贷款申请对应一个训练样本。使用 6 个特征：

1. `credit_score`：信用分；
2. `kyc_level`：身份核验等级；
3. `account_age_days`：申请时账户年龄；
4. `amount`：贷款金额；
5. `debt_ratio`：负债率；
6. `income_multiple`：贷款金额与月收入之比。

### 11.2 标签构造

当样本满足以下任一条件时标记为风险样本 `1`，否则为正常样本 `0`：

```text
信用分 < 560
或负债率 > 0.68
或贷款金额/月收入 > 13
```

这是教学项目使用的规则弱标签，目的是在缺少真实银行违约标签时跑通训练链路。生产项目应替换为真实的欺诈确认、逾期或坏账标签，并严格控制时间穿越和标签泄漏。

### 11.3 数据集与模型参数

使用 `train_test_split` 按 75% 训练、25% 验证拆分；`random_state=42` 保证结果可重复，`stratify=y` 保持两部分的正负样本比例一致。

XGBoost 使用 100 棵树、最大深度 3、学习率 0.08，并对样本和字段各采样 85%，在小型教学数据上控制过拟合。

### 11.4 评估指标

- `val_auc`：衡量模型把高风险样本排在正常样本前面的能力，越接近 1 越好，验收要求不低于 0.7。
- `val_f1`：精确率和召回率的调和平均，适合风险样本比例不均衡的分类任务。

模型和特征名会一起保存为 `models/credit_risk_xgb.joblib`，避免预测时字段顺序不一致。

执行：

```powershell
python scripts/train_xgb_model.py
```

当前固定数据通常输出：

```text
val_auc=1.0000
val_f1=1.0000
```

分数很高是因为教学数据中的高低风险模式被刻意设计得清晰，不能直接代表真实生产效果。

## 12. SQL 文件

### `sql/init_business_tables.sql`

包含 8 张银行业务表的标准 SQL DDL，可用于查看表结构或迁移到其他关系数据库。实际 SQLite 建库默认由 ORM 完成。

### `sql/init_business_data.sql`

提供一个客户和一张银行卡的最小 SQL 示例。完整 100 条以上业务数据由 Python 造数脚本生成，因为 Python 更适合批量制造带风险模式、固定随机种子且具有关联关系的数据。

## 16. 项目边界和可扩展方向

当前版本已经满足课程验收和完整流程演示，但仍属于教学系统。可扩展方向包括：

- 将训练好的 XGBoost 模型加载到在线决策链路，与规则分加权融合；
- 增加信用卡申请独立业务表以及申请流水校验；
- 黑名单按身份证摘要、卡号摘要、IP、设备分别关联匹配，并校验有效期；
- 增加规则数据库、规则启停、优先级和版本管理；
- 使用真实时间切分、交叉验证、类别不平衡处理和模型解释 SHAP；
- 增加案件认领、审核、处置、操作日志和权限系统；
- 替换为 MySQL/PostgreSQL，并增加 Redis 特征缓存和消息队列；
- 对个人信息实施加密、脱敏、权限隔离、完整审计和数据保留策略。

这份代码的核心价值是展示了从银行业务数据到特征、规则、评分、决策、落库、案件和模型训练的端到端风控流程。
