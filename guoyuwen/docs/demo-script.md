# 银行风控演示脚本（5–8 分钟）

> 使用前提：已完成 `docs/recording-checklist.md` 的录屏前检查；服务运行在 `http://127.0.0.1:8000`，专用 MySQL 容器已启动，XGBoost 模型已加载。本脚本可照读，但建议把关键句改成自己的口吻。时间分配：业务 1 分钟 → 风险检查与案件/评估 2 分钟 → XGBoost 1 分钟 → 重点规则 2 分钟 → Vibe Coding 复盘 1 分钟。

## 第 1 分钟：业务说明

**打开：总览页 `http://127.0.0.1:8000/`**

> 这是一个面向教学的银行风控演示系统。它处理四类银行事件：登录、转账、贷款申请和绑卡。我们围绕这四类事件，复现了银行风控里最典型的几类欺诈：账户接管、异地大额转账、多卡归集、多头借贷、代理或 Tor 隐匿位置，以及黑卡关联。页面上所有数据都是虚构的，卡号、身份证号只保存不可逆摘要，不涉及真实客户信息。

**停顿 3 秒，让镜头扫过指标卡与趋势图。**

> 页面上方是今天的评估量、高风险量、待审案件和通过率；下面是近 7 天评估趋势和规则命中 TOP 5。这些数据全部来自真实的风险评估流水，不是前端写死的数值。

**备用演示点**：若总览数据为空，先回到录屏清单确认造数与训练已完成。

## 第 2–3 分钟：完整风险检查与案件/评估

**打开：风险检查页 `http://127.0.0.1:8000/risk-check`**

> 风险检查是最核心的入口。调用方只需要四个字段：事件类型、银行用户 ID、事件来源 ID，以及可选的补充上下文。来源 ID 必须是业务表的真实主键，系统会校验记录归属，防止借用他人记录。

**演示一：正常登录（约 20 秒）**

> 先看一个正常登录。选择「登录」，用户填 `DEMO_USR_006`，来源填 `DEMO_LOGIN_006`，点击执行。

**点击「执行风险检查」，等待结果。**

> 结果是「通过」，0 分，低风险，没有命中规则。下方列出了 25 项银行特征的完整快照。

**演示二：异地大额转账（约 30 秒）**

> 再看一个高风险转账。选择「转账」，用户 `DEMO_USR_002`，来源 `DEMO_TXN_001`，执行。

**点击执行，等结果。**

> 这次是「拒绝」，98 分，极高风险，命中了四条规则：异地大额转账、新设备大额、代理或 Tor IP，还有设备多人共用。规则分和 XGBoost 的拒绝概率一起决定最终决策；因为命中了「极高」规则，走一票否决直接拒绝。

**演示三：黑卡短路（约 20 秒）**

> 第三个是黑名单场景。用户 `DEMO_USR_009`，转账来源 `DEMO_TXN_017`，执行。

**点击执行，等结果。**

> 结果还是拒绝，100 分，但是注意：这里命中 0 条规则，因为它是黑卡前置拦截。收款卡号哈希命中了核心黑名单，在计算特征和调用模型之前就短路拒绝，界面上明确标出「黑名单短路，未调用模型」。

**第 3 分钟：案件与评估流水（约 30 秒）**

**打开：风险案件页 `http://127.0.0.1:8000/cases`**

> 人工审核和拒绝的事件会生成风险案件。这是待办工作台，可以点「详情」看命中规则和银行画像，也可以点「重做检查」回到风险检查页复核。

**打开：评估流水页 `http://127.0.0.1:8000/assessments`**

> 评估流水是全量审计视图，按事件、等级、决策、用户筛选，可以看到规则命中数、模型拒绝概率和 sigmoid 校准后的风险分。

**备用样例**：转账 `DEMO_TXN_008`（用户 `DEMO_USR_010`）可替代 `DEMO_TXN_001` 作为第二条拒绝样例；贷款 `DEMO_LOAN_003`（用户 `DEMO_USR_010`）命中「信贷申请突击」，作为第四类事件补充样例。

## 第 4 分钟：XGBoost 数据与指标

**打开：`docs/model-evaluation.md` 或终端展示 `docs/model-metrics.json`**

> 训练脚本从真实的风险评估流水读取样本：1998 条、508 个唯一用户、25 维特征完整率 100%。标签由规则决策产生：通过和标记是 0，人工审核和拒绝是 1，正例占比约 22%。切分用的是按用户分组，同一用户的事件不会同时落在训练和验证两侧，避免用户级泄漏。

> 验证集上 AUC 1.0、F1 1.0，超过我们设定的 0.70 和 0.50 门槛。但我要强调：这是教学数据的干净结果，因为标签本身就是规则产生的，规则信号同时又是模型输入，所以决策边界非常清晰。它证明的是流水线、特征 ABI 和训练脚本可重复运行，不代表真实场景的泛化能力。

**备用演示点**：若浏览器不方便展示 JSON，改在终端执行 `Get-Content docs/model-metrics.json`。

## 第 5–6 分钟：重点规则

**打开：规则管理页 `http://127.0.0.1:8000/rules`**

> 规则管理页维护 7 条银行规则和 1 个黑名单前置控制。规则只引用 25 维特征，用通用 JSON 条件表达。

**依次点开几条规则（用「编辑」或直接在列表中说明）**

> 第一条「异地大额转账」：当前城市偏离常用城市，且金额大于 5 万，极高风险，直接拒绝。第二条「多卡归集」：一小时内至少 3 张付款卡转入同一收款卡，极高，拒绝。第三条「信贷申请突击」：近 30 天向至少 3 家机构申请贷款，高风险，人工审核。黑卡是我们保留在核心黑名单里的第八个控制场景，所以文档里它的规则数是 0，但拦截语义和规则拒绝明确区分。

**打开：黑名单页 `http://127.0.0.1:8000/blacklist`（约 20 秒）**

> 黑名单支持用户、设备指纹、IP、银行卡号、身份证号五类实体，列表值会自动脱敏。刚才演示的黑卡就属于「银行卡号」这一类。

**备用演示点**：演示「新建规则」时用可视化条件构建器选择特征 `order_event_amount` + `>` + 数值，保存后立即生效（教学环境演示即可，不要为了演示删除正式规则）。

## 第 7–8 分钟：Vibe Coding 与 `/goal` 复盘

**打开：`agent_design.md` 与 `PROMPTS_README.md`**

> 最后讲一下这个项目是怎么做出来的。我们用四份 `/goal` 提示词把一个电商风控基线重构成银行风控系统：Goal 1 定契约、Goal 2 建数据层、Goal 3 做流水线和全新前端、Goal 4 做文档和验收。每阶段独立验收、独立提交，推送到私有仓库。核心的 9 张表、四步和七步流水线从头到尾没有变过，变的是业务语义和前端。

> 这种方式的收益是节奏可控、证据可查；局限是模型指标的高分不代表真实能力，跨阶段的决定需要靠文档和 Git 交接，真正的业务判断和最终录屏还是要人工把关。

**收尾**

> 以上就是完整演示。所有数据均为虚构，本项目仅用于教学，不用于真实授信或反洗钱决策。谢谢。
