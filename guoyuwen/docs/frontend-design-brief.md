# 银行风控前端设计简报

> 目标：把现有电商展示层规划为“专业银行风险运营工作台”。本阶段只定义可实施的信息架构、视觉/交互原则及 API 依赖，不修改模板、CSS 或 JavaScript。

## 1. 基线盘点与复用判断

基线采用 FastAPI + Jinja2 + Bootstrap 5 + 原生 JavaScript，`templates/base.html` 提供固定侧栏和公共布局，`static/app.js` 提供 API 请求、分页、风险等级、ML 分数和规则条件构建器。现有页面与后端能力如下：

| 页面 | 现有路由/模板 | 主要 API | 复用与改造判断 |
|---|---|---|---|
| 总览 | `/` / `dashboard.html` | `GET /api/dashboard/overview` | 趋势图和统计交互可复用；电商指标、配色和文案必须重做 |
| 规则管理 | `/rules` / `rules.html` | `/api/rules` CRUD、toggle | 分页、条件构建器、启停和详情可复用；类别、事件、特征标签必须同步银行化 |
| 案件管理 | `/cases` / `cases.html` | `/api/cases`、`/statistics`、`/{id}/review` | 列表、状态机、审核表单可复用；业务回溯字段和画像文案必须重做 |
| 评估历史 | `/assessments` / `assessments.html` | `GET /api/assessments`、`/{id}` | 四维筛选、分页、详情抽屉/弹窗可复用；事件与字段标签必须重做 |
| 风险检查 | `/risk-check` / `risk_check.html` | `POST /api/risk/check` | 请求/结果交互可复用；固定改为四类银行事件和 `source_id` 语义 |
| 黑名单 | `/blacklist` / `blacklist.html` | `GET/POST/DELETE /api/blacklist` | 列表和增删交互可复用；“用户/地址/手机号”类型与提示必须银行化 |
| AI 助手 | `/chat` / `chat.html` | `/api/agent/chat`、`/clear` | 基线已有但非本简报核心页面；保留为辅助能力，不虚构新能力 |

基线还有 `/api/alerts` 和 `/api/profile/{user_id}`，但没有独立告警页或模型指标页。设计不得新增“模型监控/指标页”承诺；告警可在总览中作为已有 API 的辅助区，是否纳入 Goal 3 由范围和数据质量决定。

## 2. 信息架构与页面地图

主导航按运营任务排序：

1. **总览仪表盘**：今日评估量、高风险量、待审核案件、黑名单拦截、风险趋势、事件分布、待办摘要。
2. **风险检查**：选择 `登录/转账/贷款申请/绑卡`，输入 `source_id`、`user_id` 和可选 `event_data`；展示决策、风险分、命中规则、特征摘要及黑名单原因。
3. **规则管理**：列表、筛选、启停、创建/编辑、JSON 条件预览、命中详情入口。
4. **黑名单**：银行维度的名单浏览、添加、到期时间和移除；值默认掩码展示。
5. **案件管理**：待审核优先，支持状态/类别筛选、案件详情、人工复核、备注和可选加入黑名单。
6. **评估历史**：全量审计视图，按决策、风险等级、事件、用户和时间筛选，查看事件快照与规则命中。

辅助入口：AI 助手和系统告警不占用六个核心信息架构位置；帮助、环境标识和当前用户位于全局区域。

## 3. 页面与数据依赖

| 页面 | 必需数据/API | 当前缺口或同步要求 |
|---|---|---|
| 总览 | `GET /api/dashboard/overview`；可选 `GET /api/alerts` | 指标字段需从电商事件调整为四类银行事件；不虚构模型指标 |
| 风险检查 | `POST /api/risk/check`，请求只要求 `event_type/source_id/user_id/event_data` | Schema、validator、事件标签在 Goal 2/3 同步；内部 `order_id/receive_id` 不暴露为必填 |
| 规则管理 | `GET/POST/PUT/DELETE /api/rules`、`PUT /{id}/toggle` | 规则类别、事件枚举、25 维特征标签与 `sql/init_risk_data.sql` 同步 |
| 黑名单 | `GET/POST/DELETE /api/blacklist` | 黑名单类型需在 Goal 2 定义；列表值要掩码，不显示真实卡号/证件/IP |
| 案件管理 | `GET /api/cases`、`/statistics`、`/{id}`、`POST /{id}/review` | `source_id/event_type` 改银行语义；画像字段需与银行数据层同步 |
| 评估历史 | `GET /api/assessments`、`/{id}` | 筛选事件改为四类银行事件；详情复用 `triggered_rules`、`ml_score`、`event_data` |

所有列表继续采用 `{items,total,page,page_size}`，所有详情使用稳定 ID 加载；错误响应统一读取后端 `detail`。页面不得直接依赖未定义的业务表查询。

## 4. 视觉方向与设计 token

品牌仅使用中性项目名“银行风险运营工作台”，不使用任何真实银行名称、Logo、商标或完整视觉系统。

## 5. 组件与交互原则

- **导航**：桌面侧栏显示图标+文字并保持当前页状态；移动端改顶部栏与抽屉，关闭后焦点返回触发按钮。
- **卡片**：只放一个主指标和必要趋势；标题、统计周期、单位和数据状态清晰，不使用装饰性渐变制造“金融感”。
- **表格**：表头固定、数字右对齐、ID 等宽字体、状态列文字化；行点击与操作按钮分离，批量操作需二次确认。
- **筛选器**：高频筛选常驻，低频项折叠；提供“清除筛选”和结果总数，按 Enter 可提交。
- **表单**：必填项明确；`source_id` 随事件显示对应示例；提交前客户端只做格式提示，业务校验以后端为准。
- **状态徽标**：固定语义与颜色；`高/极高` 风险同时显示分数与等级。
- **风险分数**：0–100 数字为主，不使用只有颜色的仪表盘；标明规则分、ML 分是否可用以及最终决策来源。
- **规则命中详情**：展示规则 ID、名称、类别、触发字段、实际值、阈值、风险等级和动作；原始 JSON 作为次级展开项。
- **图表**：趋势图必须有轴、单位、时间范围和可访问数据摘要；颜色与状态 token 一致。
- **反馈**：提交按钮进入 loading 并防重复；成功提示说明结果，错误提示保留恢复路径；危险操作说明影响对象。

## 6. 响应式与可访问性验收

### 1440×900

- 约 240px 固定侧栏，内容区最大宽度 1200–1280px；首屏看到关键指标、风险趋势和待办。
- 列表页筛选与主操作同一视觉层级，表格主体可独立滚动，分页始终可见。

### 390×844

- 导航折叠为抽屉；关键操作采用单列布局，触控目标至少 44×44px。
- 表格优先转换为“主字段 + 状态 + 展开详情”的卡片行；确需横向滚动时固定首列并显示滚动提示。
- 弹层改近全屏抽屉，底部主操作保持可见；不把完整桌面表格缩小塞入窄屏。

### 通用验收

- 键盘可到达导航、筛选、表格操作、弹层和关闭按钮；焦点顺序符合视觉顺序。
- 正文与背景目标对比度至少 4.5:1，大号文字至少 3:1。
- 明确定义 `loading`、`empty`、`error`、`success`、`高风险`、`黑名单` 六类状态；空状态提供下一步，错误状态支持重试。
- loading 使用骨架或进度文本；高风险与黑名单状态不自动消失，并给出审计/人工复核入口。

## 7. 实施边界

- Goal 1：仅交付本简报和依赖清单。
- Goal 2：稳定业务表、事件 Schema、validator 与演示数据，不进行视觉改造。
- Goal 3：实现银行 pipeline、规则、训练和完整前端改造，并按两个视口验收。
- Goal 4：统一视觉、可访问性、演示脚本与最终打磨。
