## 问题 1：`撞黑名单: type=银行卡号, user_id=DEMO_USR_010` 是什么？为什么会弹出来？

### 结论
这是**预期行为**，不是报错。它是一条 WARNING 日志，表示“某条事件的付款/收款卡命中了教学黑卡，在黑名单前置拦截阶段被直接拒绝”。

### 原因（代码级）

1. **黑名单前置拦截**：`app/service/event.py` 的 `process_event()` 是事件统一入口，分 4 步：
   业务校验 → 补全内部字段 → **黑名单前置检查** → 7 步决策引擎。
   第 48-55 行：
   ```python
   blocked = await _check_all_blacklists(db, request)
   if blocked is not None:
       logger.warning("撞黑名单: type=%s, user_id=%s", blocked, request.user_id)
       return _blacklist_reject(request, blocked)
   ```
   命中后走 `_blacklist_reject()`：`decision="拒绝"`、`final_score=100`、`assessment_id="blacklist_reject"`，**故意不写库**（不产生审计噪音）。

2. **黑卡从哪里来**：
   - `sql/init_risk_data.sql`（第 51-57 行）插入了教学黑卡 `SHA2('DEMO_CARD_NO_020')`，即黑名单前置演示用的卡。
   - `sql/init_business_data.sql` 第 80 行：`DEMO_CARD_020` 属于 `DEMO_USR_010`；第 196 行又插了一条同样的黑卡（候选）。
   - 因此 `DEMO_USR_010` 名下的这张卡，在**任何交易里作为付款卡或收款卡**都会触发拦截。

3. **为什么生成数据时会“弹”出来**：`gen_train_dataset` / `gen_risk_data_with_dates` 会遍历库里的**所有**银行 source（转账/绑卡/贷款/登录），逐条走完整 `process_event`。凡是涉及这张黑卡的转账，就会在终端打印这条 warning。日志级别是 `logger.warning`，根 logger 默认打到 stdout，所以直接显示在终端（同时写入 `logs/app.log`）。

4. **你这次日志里 DEMO_USR_009 也出现**，是因为黑卡 `DEMO_CARD_NO_020` 同时被当作**收款卡**使用，从 `DEMO_USR_009` 的卡转入 → 也触发拦截（转账同时检查付款卡与收款卡）。

5. **附带影响（数据口径）**：撞黑样本会进入生成统计的 `拒绝/positive`（`decisions` 计数），但**不写库**。所以你这次 `--count 2000` 里 3 条撞黑 → 训练脚本显示“可训练评估 **1997** 条”，与 2000 - 3 完全吻合。

### 解决方案（三选一）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 批量生成脚本里把单条 `logger.warning` 静音，改为**聚合统计**：结束时打印一行“教学黑卡拦截 N 条（黑名单前置，不入库）”。黑卡教学演示功能保留 | 教学上有价值，终端干净，训练口径也清晰 |
| B | 生成训练数据时临时禁用黑名单检查 | 会让训练集少了“黑名单”这一真实拦截来源，不推荐 |
| C | 把该日志级别从 warning 降到 info | 只是不再显眼，警告语义丢失，不推荐 |

## 问题 2：`--days 7 --per-day 100 --live` 为什么浏览器只有一天的数据？

### 结论
根因是**“日期跨度功能根本没实现”**，不是浏览器或仪表盘的问题。生成的 700 条评估 `create_time` 全是“当前时间”，仪表盘按 `create_time` 分组，自然只有今天一个点。

### 原因（代码级，4 处叠加）

1. **`--days`/`--per-day` 只影响数量，不产生日期**：
   `scripts/gen_risk_data_with_dates.py` 第 21-30 行：
   ```python
   async def generate_risk_data_with_dates(days, per_day, *, clean=False, seed=20260812):
       return await gen_train_dataset(count=days * per_day, seed=seed, clean=clean)
   ```
   它只是把 `7 × 100 = 700` 传给 `gen_train_dataset`。脚本头注释“日期取各银行 source 的真实业务时间”**名不副实**。

2. **`--live` 是死参数**：第 41 行定义了 `--live`，但 `generate_risk_data_with_dates()` 根本没接收它；`--start`/`--end` 同理（第 38-39 行，注释写“兼容展示参数”，实际没用）。

3. **评估 `create_time` 恒为“当前时间”**：`RiskAssessment.create_time` 默认 `datetime.now()` / `server_default=func.now()`（`app/models_risk.py` 第 151-153 行）；`decision.py` 写库时（`_persist_assessment`）不传 create_time。所以无论 source 的业务时间在哪天，落库时间都是“生成那一刻”——你这次 700 条全部落在今天。

4. **仪表盘按 `create_time` 分组**：`app/agent/tools.py` `_stats_trend_7d()` 用 `func.date(RiskAssessment.create_time)` GROUP BY 近 7 天，全部同一天 → 折线图只有一个点，摘要显示“近 **1** 日”。训练脚本的告警“评估 create_time 跨度不足 1 天：0:02:19”也是同一根因。

### 解决方案

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐，语义最对）** | 按 source 业务时间回填 create_time：生成时读每条 source 的 `txn_at` / `login_at` / `apply_at` / `bind_at`，写 `risk_assessment` / `risk_event` / `risk_case` 时显式传 create_time。`--days 7` 的数据自然分布在最近 7 天，仪表盘 7 天曲线完整，训练数据时间跨度也真实；`--live` 保留“全部为当前时间”（供 one_command 第 6 步“造今日数据”演示） | 需改核心引擎写入路径，工作量中等 |
| **B（最小改动）** | 生成后做一次 UPDATE 回填：按 seed 伪随机把新生成评估的 create_time 均匀铺到最近 N 天（如 `now - randint(0, N-1)天 + 随机时:分`）。不动核心引擎，只改脚本 | 改动最小，但 create_time 与 source 业务时间不完全对应（教学系统够用） |
| C | 不动代码：`--live` 语义本就是“全部今日”；想要 7 天曲线就分 7 次跑 `--days 1 --per-day 100`，或手改 SQL | 治标不治本，不推荐 |

**建议**：选 A 或 B，同时把 `--live` / `--start` / `--end` 这三个死参数真正生效（或直接删掉避免误导）。

## 问题 3：有些指令的终端反馈太单调

### 原因
`init_db.py` 用了手写的“步骤横幅 + 每步说明 + 汇总”，观感好；而其它脚本基本都是 `print(result)` 打一个 dict（`gen_train_dataset` / `gen_risk_data_with_dates` / `gen_risky_users` / `backfill_ml_score`），或只有零散日志（`train_xgb_model`），没有统一的进度与总结。

### 解决方案（统一控制台输出层）

1. **抽一个共享工具** `scripts/_console.py`（不引入第三方依赖）：
   - `banner(title)`：`====` 标题横幅（与 init_db.py 同风格）
   - `step(i, n, desc)`：`[步骤 i/n] 描述`
   - `kv(key, value)`：对齐的 `键: 值` 行
   - `ok(msg)` / `warn(msg)` / `error(msg)`：状态提示
   - `summary(dict)`：把 decisions / events 等统计整理成对齐表格
   - 轻量进度（用 `\r` 覆写，每 100 条打一行，兼容 Windows GBK）
   - ANSI 颜色自动探测（仅 TTY 着色，管道/日志文件关闭）

2. **逐个脚本接入**，风格与 `init_db.py` 统一：
   - `gen_train_dataset.py`：横幅 + 阶段（加载 source → 逐条评估进度 → 完成），结尾对齐输出决策分布 / 事件分布 / 正例比例 / 失败样例；撞黑聚合为一行提示（配合问题 1 的方案 A）。
   - `gen_risk_data_with_dates.py`：同上 + 显示本次实际覆盖的日期范围。
   - `gen_risky_users.py`：横幅 + 风险模式表（`build_business_data` 里已有 `_print_summary`，只是没被调用）。
   - `backfill_ml_score.py` / `train_xgb_model.py`：步骤化输出。

3. **一致性**：所有脚本共用同一套 helper，保持与 `init_db.py` 完全一致的观感。

## 已实施变更（2026-08-12，用户确认后完成）

### 问题 1：撞黑日志 → 聚合提示
- `scripts/gen_train_dataset.py`：批量生成时用 `silence_loggers(["app.service.event"])` 静音单条 warning，循环内统计撞黑条数，结尾统一打印一行提示：
  `教学黑卡前置拦截 N 条（黑名单前置、不入库，符合教学演示预期）`。
- 结果 dict 新增 `blacklist_hits` / `time_min` / `time_max` 字段。
- 实时 Web 风控的 `撞黑名单` warning 保留不变。

### 问题 2：`--days 7` 只显示一天 → 修复
- **新增能力**：`gen_train_dataset(..., spread_days=N, live=bool)`。
  - `spread_days=N`：生成的评估 create_time 确定性铺到最近 N 天（含今天，seed 固定可复现）。
  - `live=True`：create_time 一律当前时间（今日数据）。
  - 两者都不设置：create_time 取 source 业务时间（真实时间跨度，供训练）。
- **引擎贯通**：`app/schemas.py` 给 `RiskCheckRequest` 加可选 `create_time`；`app/engine/decision.py` 通过 `ctx.as_of` 把该时间写入 `risk_event` / `risk_feature(compute_time)` / `risk_assessment` / `risk_case` / `risk_user_profile.last_assessment_time` / 响应 `create_time`。黑名单短路的响应也尊重 `create_time`（`app/service/event.py`）。
- **用法**：
  - `python scripts/gen_risk_data_with_dates.py --days 7 --per-day 100` → 最近 7 天 × 100 条，仪表盘 7 天曲线完整。
  - `python scripts/gen_risk_data_with_dates.py --days 1 --per-day 50 --live` → 今日数据（one_command 第 6 步不变）。
  - **`--live` 语义 = 全部按当前时间入库**；若与 `--days>1` 一起用，脚本会打印提示：去掉 `--live` 才能得到最近多天曲线。
- **注意（重要发现）**：`gen_risky_users.py`（seed 20260812）的业务 source 锚定在 `2026-01-13`（`gen_business_data.py` 的 `anchor = 2026-01-01 + seed%180 天`），而 `init_business_data.sql` 的 109 条在 2026-08 前后。因此：
  - 直接跑 `gen_train_dataset --count 2000` 训练数据时，create_time 会落在各自 source 的真实日期（跨度真实，训练告警“跨度不足 1 天”消失）。
  - 要看“最近 7 天”仪表盘曲线，必须用 `gen_risk_data_with_dates.py --days 7`（它把 create_time 铺到最近 7 天，与 source 日期无关）。
