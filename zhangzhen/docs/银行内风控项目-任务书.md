## 1. 项目背景与任务目标

### 1.1 为什么做这个任务

课堂参考项目 `AI_Risk` 已经实现了一套完整的电商风控闭环：

```text
业务事件
→ 参数与业务归属校验
→ 黑名单前置拦截
→ 特征计算与快照
→ JSON 业务规则匹配
→ XGBoost 风险概率
→ 规则/模型双轨融合
→ 风险决策
→ 评估、案件、画像、审计与告警
```

这套架构具有行业复用价值，但订单、物流、售后、收货地址等业务模型不能直接套到银行业。银行版项目需要证明：开发者能够识别“风控平台能力”和“行业业务能力”的边界，并将同一套风控主干迁移到登录、转账、信用卡交易和贷款申请四个银行场景。

### 1.2 项目目标

在参考项目基础上完成一个可独立启动、可浏览器演示、可接口调用、可规则配置、可模型降级、可审计回溯的银行智能风控原型。

项目必须实现：

- 4 类实时风险事件：登录、转账、信用卡交易、贷款申请；
- 8 张银行业务表和 9 张风控核心表；
- 固定 25 维银行风险特征；
- 不少于 20 条预置银行规则，其中至少 4 条组合规则、3 条一票否决规则；
- 规则引擎 + XGBoost 双轨决策，模型缺失时自动降级为纯规则；
- 黑名单、案件审核、评估历史、用户画像、审计日志和告警闭环；
- 7 个管理页面和一组 REST API；
- AI 风控助手，但默认只读，涉及变更的操作必须由人工确认；
- 本地 Python 与 Docker Compose 两种启动方式；
- 自动化测试、演示数据脚本和项目 README。

### 1.3 非目标

本项目不实现以下生产级能力：

- 不连接真实银行核心系统、征信系统或真实支付通道；
- 不保存真实姓名、身份证号、银行卡号、手机号等明文敏感信息；
- 不以演示模型代替真实反欺诈模型或授信模型；
- 不实现真实资金冻结、扣款、贷款审批或账户封禁；
- 不承诺生产级高可用、分布式计算、亿级实时流处理；
- 不让大模型单独作出放款、拒贷或资金拦截等最终决定。

## 2. 参考项目通读结论

### 2.1 参考项目现状

老师的电商参考项目采用五层结构：

| 层次 | 目录 | 职责 |
|---|---|---|
| 页面层 | `templates/`、`static/` | Jinja2 页面、表格、弹窗、可视化规则构建器 |
| 路由层 | `app/routers/` | 接收 HTTP 请求、Pydantic 校验、依赖注入、返回响应 |
| 服务层 | `app/service/` | 业务校验、事件编排、黑名单、案件、审计、告警 |
| 引擎层 | `app/engine/` | 25 维特征、JSON 规则、评分决策、XGBoost |
| 数据层 | `app/models_*.py`、`app/database.py`、`sql/` | ORM、异步 MySQL、初始化与迁移 |

参考项目包含：

- 17 张电商业务表；
- 9 张风控核心表；
- 4 种电商事件；
- 25 维电商特征；
- 30 条预置规则；
- 4 步 `process_event` 业务编排；
- 7 步 `run_risk_check` 决策流水线；
- 7 个页面、30 个左右的 HTTP 路由；
- 8 个 AI Agent 工具；
- 37 个测试文件、416 个测试函数；
- MySQL + FastAPI + Nginx 三容器部署。

### 2.2 可以复用的核心思想

以下能力应保持同样的架构和调用方向：

- `RiskCheckRequest → process_event → run_risk_check → RiskCheckResponse` 主契约；
- 事件、特征快照、评估、案件之间的审计链路；
- JSON 条件表达式和 `and/or` 递归求值；
- 规则分 `max(命中规则分) + 多规则加分` 的基础公式；
- 极高风险规则一票否决，不允许被模型低分推翻；
- XGBoost 未加载时自动使用纯规则；
- 人工审核/拒绝时建案，通过/标记只留评估记录；
- 案件状态机、黑名单软删除、操作审计和定时告警；
- FastAPI 路由拆分、异步 SQLAlchemy、Jinja2 管理后台；
- 数据生成、模型训练、Docker 和自动化测试框架。

### 2.3 必须重写的行业内容

- 电商业务 ORM 和 SQL；
- 事件类型与 `source_id` 映射；
- 25 维特征及其 SQL 计算；
- 规则类别、规则条件、阈值和描述；
- 黑名单对象及其检查顺序；
- 用户画像业务摘要；
- 演示数据与高风险用户生成逻辑；
- AI Agent 的银行查询工具与系统提示词；
- 页面中的订单、售后、地址等电商文案和字段。

### 2.4 对原任务书“完全不改 schema”的修订

原任务书要求“风控 9 张表完全复用，不许改 schema”，但参考代码的核心表仍含电商行业枚举和字段：

- `risk_rule.rule_category` 是订单欺诈、售后滥用等电商类别；
- `risk_rule/risk_event/risk_case.event_type` 是下单、支付、售后申请、物流投诉；
- `risk_feature.entity_type` 是用户、订单、地址；
- `risk_blacklist.blacklist_type` 是用户、地址、手机号；
- `risk_user_profile` 直接包含订单数、退款率、地址数、投诉数。

因此银行版采用“稳定骨架 + 受控适配”原则：

**不得改变：**

- 9 张核心表的数量和职责；
- 主键含义和 `event → feature/assessment → case` 审计链路；
- 软删除、状态机、操作日志、告警等机制；
- `final_score`、`risk_level`、`decision` 的总体语义；
- 规则 JSON 表达式格式。

**允许且必须改变：**

- 行业相关 ENUM 值；
- `risk_user_profile` 中电商摘要字段，或将银行摘要统一放入 `profile_data`；
- 与银行特征实体对应的 `entity_type` 值；
- 索引和注释，但不得破坏核心关联。

默认采用专业实现：保留 9 表职责和关联，受控修改行业枚举与画像摘要。若课程评分严格要求列级 schema 不变，则银行画像字段全部写入 `profile_data` JSON；这种模式仅用于满足作业约束，不作为推荐设计。

## 3. 总体业务范围

### 3.1 四类事件

| 事件类型 | `source_id` 指向 | 主要风险 | 正常决策时机 |
|---|---|---|---|
| 登录 | `login_log.login_id` | 撞库、异地登录、新设备、代理/Tor、短时地理跳跃 | 登录认证阶段 |
| 转账 | `bank_transaction.txn_id`，且 `txn_type=TRANSFER` | 盗号转账、异地大额、夜间密集、跑分归集、陌生收款人 | 转账提交前 |
| 信用卡交易 | `bank_transaction.txn_id`，且 `txn_type=CARD_PAYMENT` | 盗刷、额度异常、新设备大额、异常频次 | 支付授权阶段 |
| 贷款申请 | `loan_application.loan_id` | 多头借贷、收入负债不匹配、低信用高额度、身份风险 | 申请预审阶段 |

规则还可使用 `通用` 事件类型，表示对四类事件均生效。

### 3.2 六类规则类别

- 账户安全；
- 转账欺诈；
- 信用卡风险；
- 信贷风险；
- 设备风险；
- IP 与地域风险。

### 3.3 四档风险输出

| 分数 | 风险等级 | 默认决策 | 含义 |
|---:|---|---|---|
| 0–29 | 低 | 通过 | 未发现明显风险 |
| 30–59 | 中 | 标记 | 允许继续，但留下风险标记 |
| 60–84 | 高 | 人工审核 | 暂缓处理，进入案件工作台 |
| 85–100 | 极高 | 拒绝 | 直接阻断并自动形成已拒绝案件 |

第一版统一使用以上阈值，避免“规则等级区间”和“事件决策阈值”出现两套互相矛盾的口径。不同事件的严格程度通过规则条件和规则分值表达。一票否决优先级最高。

## 4. 总体技术架构

```text
浏览器 / 外部调用方
        │
        ▼
Nginx :80（Docker 模式，可选）
        │
        ▼
FastAPI Router
  ├─ Pydantic 请求校验
  └─ AsyncSession 依赖注入
        │
        ▼
Service.process_event（4 步）
  1. 银行业务实体与归属校验
  2. 补全交易/设备/IP/账户上下文
  3. 黑名单前置短路
  4. 调用决策引擎
        │
        ▼
Engine.run_risk_check（7 步）
  1. 构造上下文
  2. 写 risk_event
  3. 计算 25 维特征
  4. 写 risk_feature 快照
  5. 匹配 JSON 规则
  6. 规则 + XGBoost + 一票否决
  7. 写 assessment/case/profile 并返回
        │
        ▼
MySQL 8.0（8 张业务表 + 9 张风控表）
```

## 5. 核心请求与响应契约

### 5.1 风险检查请求

核心契约保持四个字段：

```json
{
  "event_type": "转账",
  "source_id": "TXN202608120001",
  "user_id": "U10001",
  "event_data": {
    "request_id": "REQ202608120001",
    "client_time": "2026-08-12T09:30:00+08:00"
  }
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `event_type` | 是 | 登录/转账/信用卡交易/贷款申请 |
| `source_id` | 是 | 对应业务表中的真实主键 |
| `user_id` | 是 | 发起事件的银行客户 ID |
| `event_data` | 否 | 补充快照，不能代替数据库中的权威业务数据 |

`event_data` 可以存请求编号、客户端时间等补充字段，但交易金额、设备、IP、用户归属等必须根据 `source_id` 查询业务表并核验，不能完全相信调用方传入值。

### 5.2 风险检查响应

```json
{
  "assessment_id": "ast...",
  "event_id": "evt...",
  "user_id": "U10001",
  "final_score": 92,
  "risk_level": "极高",
  "decision": "拒绝",
  "rule_count": 2,
  "triggered_rules": [],
  "features": {},
  "ml_score": 0.81,
  "ml_decision": "拒绝",
  "message": null,
  "blocked_by": null,
  "create_time": "2026-08-12T09:30:01+08:00"
}
```

### 5.3 错误响应约定

| 状态码 | 场景 |
|---:|---|
| 400 | `source_id` 与事件类型不匹配、字段业务值错误 |
| 403 | 交易、银行卡、账户或贷款申请不属于请求用户 |
| 404 | 用户或业务实体不存在 |
| 409 | 相同 `request_id` 重复提交且结果冲突 |
| 422 | Pydantic 字段类型或枚举校验失败 |
| 500 | 系统内部异常，日志记录 `error_id`，响应不得暴露堆栈和密钥 |
| 504 | AI 助手调用模型超时；风控主流程不依赖 AI 助手 |

## 6. 数据模型

#### 6.1.7 `device_fingerprint`：设备与用户绑定

为支持“同一设备关联多个用户”的规则，不能把 `device_id` 单独设为唯一主键。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `binding_id` | BIGINT PK AUTO | 绑定记录 ID |
| `device_id` | VARCHAR(100) INDEX | 设备 ID |
| `user_id` | VARCHAR(50) INDEX | 关联用户 |
| `fingerprint_hash` | VARCHAR(128) | 指纹哈希 |
| `first_seen` | DATETIME | 首次出现 |
| `last_seen` | DATETIME | 最近出现 |
| `os` | VARCHAR(50) | 操作系统 |
| `browser` | VARCHAR(50) | 浏览器/客户端 |
| `is_rooted` | TINYINT | 是否 Root/越狱 |
| `is_emulator` | TINYINT | 是否模拟器 |

#### 6.1.8 `ip_geo_location`：IP 地理与风险信息

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `ip` | VARCHAR(64) PK | 演示 IP |
| `country` | VARCHAR(50) | 国家 |
| `province` | VARCHAR(50) | 省份 |
| `city` | VARCHAR(50) | 城市 |
| `isp` | VARCHAR(100) | 运营商 |
| `is_proxy` | TINYINT | 是否代理 |
| `is_tor` | TINYINT | 是否 Tor 出口 |
| `risk_score` | INT | IP 风险分 |
| `updated_at` | DATETIME | 数据更新时间 |

### 6.2 表关系

```text
customer_info(user_id)
  ├─ 1:N bank_account
  ├─ 1:N bank_card ── N:1 bank_account
  ├─ 1:N bank_transaction
  ├─ 1:N loan_application
  ├─ 1:N login_log
  └─ 1:N device_fingerprint

ip_geo_location(ip)
  ├─ 被 bank_transaction.ip 引用
  ├─ 被 loan_application.ip 引用
  └─ 被 login_log.ip 引用
```

### 6.3 九张风控核心表

| 表 | 银行版职责 | 复用策略 |
|---|---|---|
| `risk_rule` | 保存银行 JSON 规则 | 保留结构，适配规则类别和事件枚举 |
| `risk_event` | 保存四类银行事件及原始快照 | 保留链路，适配事件枚举 |
| `risk_feature` | 保存每次检查的 25 维特征快照 | 保留结构，实体类型适配为用户/交易/设备/信贷 |
| `risk_assessment` | 保存规则、模型、最终分数和决策 | 完全复用 |
| `risk_case` | 保存人工审核或系统拒绝案件 | 保留状态机，适配事件枚举 |
| `risk_blacklist` | 统一管理银行黑名单 | 保留软删，扩展类型 |
| `risk_user_profile` | 保存客户风险画像 | 推荐适配摘要字段；严格模式放 `profile_data` |
| `risk_action_log` | 记录规则、案件、黑名单变更 | 完全复用并扩大审计范围 |
| `risk_alert` | 保存业务/模型/系统/安全告警 | 完全复用 |

不再创建 `BlacklistExtra`。否则会出现两套黑名单、两套软删除和两套审计口径。

### 6.4 银行黑名单类型

`risk_blacklist.blacklist_type` 支持：

- 用户；
- 身份证；
- 银行账户；
- 银行卡；
- 收款账户；
- 设备指纹；
- IP；
- 手机号。

`blacklist_value` 只存 ID、哈希值或脱敏值，不存真实敏感信息。

### 6.5 数据库约束

- 业务金额必须非负，交易金额必须大于 0；
- `credit_score` 范围 300–850；
- `debt_ratio`、`card_utilization_rate` 等比例范围 0–1，异常值需校验；
- 所有业务归属字段建立索引；
- 时间窗口特征涉及的时间字段必须建索引；
- 黑名单唯一约束为 `(blacklist_type, blacklist_value)`；
- 规则与黑名单使用软删除；
- 不依赖数据库物理外键也可以，但 Service 层必须做存在性与归属校验；
- SQL DDL、SQLAlchemy ORM 和 Pydantic Schema 必须保持同步，并有自动测试。

## 7. 事件处理主链路

### 7.1 `process_event` 四步业务流

```text
1. validate_risk_check_request
2. enrich_request_context
3. check_all_blacklists
4. run_risk_check
```

#### 步骤 1：业务校验

- 用户必须存在且状态允许发起业务；
- `source_id` 必须存在于对应业务表；
- 登录日志、交易、卡、账户、贷款申请必须属于 `user_id`；
- 转账事件必须对应 `txn_type=TRANSFER`；
- 信用卡交易必须对应 `txn_type=CARD_PAYMENT`；
- 交易金额、贷款金额等关键字段必须合法；
- 禁止用他人的真实交易 ID 配合自己的用户 ID 绕过风控。

#### 步骤 2：上下文补全

根据事件补全：

- `account_id`、`card_id`；
- `device_id`、`ip`、`geo`；
- 收款账户哈希；
- 用户常驻城市、信用分、KYC 等级；
- 本次事件时间。

#### 步骤 3：黑名单前置拦截

默认优先级：

```text
用户/身份证
→ 付款账户/银行卡
→ 收款账户
→ 设备指纹
→ IP
→ 手机号
```

命中即短路返回：

```text
final_score = 100
risk_level = 极高
decision = 拒绝
message = 撞黑名单: <类型>
```

与参考项目一致，第一版黑名单短路不写 `risk_event/risk_assessment`，避免污染模型训练数据；但必须通过结构化日志或专门指标统计命中次数。若后续要求完整审计，可增加“黑名单拦截事件是否落库”的配置开关。

#### 步骤 4：进入决策引擎

未命中黑名单才进入 `run_risk_check`。

### 7.2 `run_risk_check` 七步流水线

1. 构造上下文；
2. 创建 `risk_event`；
3. 计算 25 维银行特征；
4. 将每个特征写入 `risk_feature`；
5. 加载当前事件规则和通用规则并匹配；
6. 计算规则分、ML 分、一票否决和最终决策；
7. 同一事务写入 `risk_assessment`、可选 `risk_case`、`risk_user_profile`，提交后返回响应。

任一步失败必须整体回滚，不允许只写事件、不写评估的半成品。

## 8. 固定 25 维银行特征

> 特征名是规则引擎、XGBoost、前端构建器和测试之间的硬契约。修改特征名必须同时修改计算函数、`FEATURE_COLUMNS`、规则 SQL、训练脚本、前端标签和测试。

### 8.1 客户画像特征（7 维）

| 序号 | 特征名 | 含义 | 计算口径 |
|---:|---|---|---|
| 1 | `user_account_age_days` | 注册天数 | 当前时间－注册时间 |
| 2 | `user_credit_score` | 信用分 | `customer_info.credit_score` |
| 3 | `user_kyc_level` | KYC 数值 | L1=1，L2=2，L3=3 |
| 4 | `user_txn_count_30d` | 近 30 天交易笔数 | 成功/待处理交易数 |
| 5 | `user_txn_amount_30d` | 近 30 天交易总金额 | 对交易金额求和 |
| 6 | `user_avg_txn_amount_30d` | 近 30 天平均交易额 | 总金额/交易笔数，分母为 0 时返回 0 |
| 7 | `user_failed_login_count_24h` | 近 24 小时失败登录数 | `success=0` 的登录数 |

### 8.2 交易行为特征（8 维）

| 序号 | 特征名 | 含义 | 计算口径 |
|---:|---|---|---|
| 8 | `txn_amount` | 本次交易金额 | 非交易事件为 0 |
| 9 | `txn_amount_vs_avg_ratio` | 本次金额/近 30 天平均金额 | 平均金额为 0 时按约定返回 0 |
| 10 | `txn_count_1h` | 近 1 小时交易笔数 | 包含本次事件 |
| 11 | `txn_amount_24h` | 近 24 小时累计交易金额 | 按用户聚合 |
| 12 | `txn_is_night` | 是否 0–5 点交易 | 是 1，否 0 |
| 13 | `txn_is_new_beneficiary` | 是否首次向该收款账户转账 | 是 1，否 0 |
| 14 | `txn_cross_city` | 事件城市是否不同于常驻城市 | 是 1，否 0 |
| 15 | `txn_beneficiary_payer_count_1h` | 1 小时内向同一收款账户付款的不同账户数 | 多卡/多账户归集信号 |

### 8.3 设备、登录与 IP 特征（6 维）

| 序号 | 特征名 | 含义 | 计算口径 |
|---:|---|---|---|
| 16 | `device_age_days` | 设备首次出现距今天数 | 未知设备为 0 |
| 17 | `device_user_count_30d` | 30 天内设备关联的不同用户数 | `COUNT(DISTINCT user_id)` |
| 18 | `device_is_new` | 设备出现是否不足 7 天 | 是 1，否 0 |
| 19 | `ip_is_proxy` | IP 是否代理 | 是 1，否 0 |
| 20 | `ip_is_tor` | IP 是否 Tor | 是 1，否 0 |
| 21 | `login_geo_jump_km` | 与上次成功登录地点的距离 | 无历史或无法计算时为 0 |

### 8.4 信贷与信用卡特征（4 维）

| 序号 | 特征名 | 含义 | 计算口径 |
|---:|---|---|---|
| 22 | `loan_amount` | 本次贷款申请金额 | 非贷款事件为 0 |
| 23 | `loan_debt_ratio` | 申请时负债收入比 | 非贷款事件为 0 |
| 24 | `loan_institution_count_30d` | 30 天内申请的不同机构数 | `COUNT(DISTINCT institution_code)` |
| 25 | `card_utilization_rate` | 信用卡已用额度/总额度 | 非信用卡或额度为 0 时返回 0 |

### 8.5 缺失值约定

- 某事件不适用的特征填 0；
- “数据未知”和“业务值等于 0”在生产中应区分，教学版暂统一为 0；
- 原始特征字典必须固定包含全部 25 个键，避免 XGBoost 因字段缺失静默补 0；
- 金额和比率统一转为 `float` 供模型使用，但落库金额仍使用 `DECIMAL`；
- 特征只能使用决策时刻已经存在的信息，禁止使用交易最终拒绝状态、人工审核结果等未来信息。

## 9. 规则引擎

### 9.1 JSON 表达式

单条件：

```json
{
  "field": "txn_amount",
  "op": ">=",
  "value": 50000
}
```

组合条件：

```json
{
  "and": [
    {"field": "txn_cross_city", "op": "==", "value": 1},
    {"field": "txn_amount", "op": ">=", "value": 50000}
  ]
}
```

支持运算符：

```text
>  >=  <  <=  ==  !=  in  not_in  between  and  or
```

特征不存在、条件 JSON 损坏或运算符未知时，该规则按“未命中”处理并记录告警日志，不能中断其他规则。

### 9.2 预置规则清单（第一版 20 条）

| 编号 | 事件/分类 | 规则名 | 条件摘要 | 等级/分值 | 动作 |
|---|---|---|---|---|---|
| B001 | 登录/账户安全 | 24 小时失败登录过多 | `user_failed_login_count_24h >= 5` | 高/65 | 人工审核 |
| B002 | 登录/设备风险 | 新设备且代理 IP | `device_is_new=1 AND ip_is_proxy=1` | 高/75 | 人工审核 |
| B003 | 登录/IP地域 | 短时超远距离登录 | `login_geo_jump_km >= 1000` | 极高/90 | 拒绝 |
| B004 | 转账/转账欺诈 | 异地大额转账 | `txn_cross_city=1 AND txn_amount>=50000` | 极高/90 | 拒绝 |
| B005 | 转账/转账欺诈 | 凌晨密集交易 | `txn_is_night=1 AND txn_count_1h>=3` | 高/70 | 人工审核 |
| B006 | 转账/设备风险 | 新设备大额转账 | `device_is_new=1 AND txn_amount>=30000` | 高/75 | 人工审核 |
| B007 | 转账/转账欺诈 | 金额远超个人均值 | `txn_amount_vs_avg_ratio>=5` | 高/70 | 人工审核 |
| B008 | 转账/转账欺诈 | 陌生收款人大额转账 | `txn_is_new_beneficiary=1 AND txn_amount>=20000` | 高/70 | 人工审核 |
| B009 | 转账/转账欺诈 | 多账户向单一账户归集 | `txn_beneficiary_payer_count_1h>=5` | 极高/95 | 拒绝 |
| B010 | 转账/转账欺诈 | 24 小时累计超大额 | `txn_amount_24h>=200000` | 极高/90 | 拒绝 |
| B011 | 信用卡/信用卡风险 | 高额度使用率大额消费 | `card_utilization_rate>=0.95 AND txn_amount>=10000` | 高/75 | 人工审核 |
| B012 | 信用卡/信用卡风险 | 凌晨连续刷卡 | `txn_is_night=1 AND txn_count_1h>=4` | 高/70 | 人工审核 |
| B013 | 信用卡/设备风险 | 新设备信用卡大额交易 | `device_is_new=1 AND txn_amount>=10000` | 高/70 | 人工审核 |
| B014 | 信用卡/信用卡风险 | 消费金额显著偏离均值 | `txn_amount_vs_avg_ratio>=8` | 高/75 | 人工审核 |
| B015 | 贷款/信贷风险 | 高负债率申请 | `loan_debt_ratio>=0.70` | 极高/90 | 拒绝 |
| B016 | 贷款/信贷风险 | 低信用分申请 | `user_credit_score<550` | 高/70 | 人工审核 |
| B017 | 贷款/信贷风险 | 低 KYC 大额申请 | `user_kyc_level<=1 AND loan_amount>=50000` | 高/75 | 人工审核 |
| B018 | 贷款/信贷风险 | 30 天多头借贷 | `loan_institution_count_30d>=3` | 高/80 | 人工审核 |
| B019 | 通用/设备风险 | 同一设备多人共用 | `device_user_count_30d>=5` | 中/50 | 标记 |
| B020 | 通用/IP地域 | 代理或 Tor 访问 | `ip_is_proxy=1 OR ip_is_tor=1` | 中/50 | 标记 |

规则阈值是教学初值，不代表真实银行策略。后续评审可调整，但调整必须同步测试用例和演示数据。

### 9.3 黑名单硬策略

以下策略不依赖普通规则分，命中即拒绝：

- 用户或身份证命中黑名单；
- 付款账户、付款卡命中黑名单；
- 收款账户命中黑名单；
- 设备指纹命中黑名单；
- IP 命中黑名单。

### 9.4 规则评分

```text
rule_score = min(max(命中规则分) + 3 × (额外命中规则数), 100)
```

只要任意命中规则为“极高”，就触发一票否决：

```text
final_score 至少为 90
risk_level 强制为 极高
decision 强制为 拒绝
```

## 10. XGBoost 与双轨融合

### 10.1 模型定位

XGBoost 是规则之外的补充信号，不是规则替代品。模型输入固定为 25 维特征，输出：

```text
P(y=1) = 需要人工审核或拒绝的概率
```

模型未训练、文件缺失或推理失败时：

```text
is_loaded = false
ml_score = 0
系统继续走纯规则，不得导致核心风控接口不可用
```

### 10.2 演示标签

教学阶段可使用弱标签：

```text
y=0：通过、标记
y=1：人工审核、拒绝
```

必须在 README 中注明：这种标签来自规则或合成风险模式，模型主要学习规则，不代表真实欺诈识别效果。真实项目应使用人工审核结论、欺诈确认、拒付、逾期等事后标签。

### 10.3 防止数据泄漏

- 不使用 `decision`、`final_score`、`rule_count`、`ml_score` 作为模型特征；
- 不使用事件发生之后才产生的状态字段；
- 训练样本仅使用决策时点的特征快照；
- 训练集与验证集优先按时间切分，不能只随机切分；
- 同一用户的强相关重复样本应尽量避免同时落入训练与验证集；
- 合成数据 AUC=1.0 只能证明数据容易，不代表模型优秀。

### 10.4 双轨融合

保留参考项目思路：

```text
ml_risk_score = 100 × (1 - exp(-3 × ml_probability))
final_score = α × rule_score + β × ml_risk_score
默认 α=0.5，β=0.5
```

融合后再次执行一票否决，确保极高规则不会被模型低分拉低。

### 10.5 模型验收

| 项目 | 教学原型要求 |
|---|---|
| 特征数 | 严格等于 25 |
| 最小训练样本 | 可配置，建议不少于 1250 |
| 正例比例 | 建议 15%–60% |
| 验证方式 | 时间切分优先，输出 AUC/F1/Precision/Recall |
| 最低参考指标 | 真实风格合成集 `val_auc>=0.70`、`val_f1>=0.50` |
| 模型文件 | `app/engine/xgb_model.json`，不提交真实敏感模型 |
| 降级 | 删除模型文件后核心流程仍全部可用 |

## 11. 案件、画像、审计和告警

### 11.1 建案规则

- 通过：只写事件、特征、评估和画像；
- 标记：只写事件、特征、评估和画像；
- 人工审核：创建“待审核”案件；
- 拒绝：创建“已拒绝”案件，审核人记为 `system`；
- 相同 `(source_id, event_type)` 已有未结案件时不重复建案。

### 11.2 案件状态机

```text
待审核 → 审核中 / 已通过 / 已拒绝 / 已关闭
审核中 → 已通过 / 已拒绝 / 已关闭
已通过 / 已拒绝 / 已关闭 → 终态
```

非法回退必须返回 400。人工拒绝时可选择加入黑名单，案件变更、加黑和审计应在同一事务提交。

### 11.3 银行用户画像

推荐摘要字段：

- 综合风险分和风险等级；
- 近 30 天交易笔数与金额；
- 失败登录次数；
- 设备数和高风险 IP 次数；
- 贷款申请次数和负债率；
- 评估次数、最近评估时间；
- 其余扩展内容写入 `profile_data` JSON。

### 11.4 审计日志

必须记录：

- 规则创建、修改、启停、删除；
- 案件人工审核、系统拒绝、超时关闭；
- 黑名单新增和移除；
- 告警处理；
- AI 助手触发的任何写操作。

日志应包含操作人、动作类型、目标对象、变更前后 JSON、备注和时间。API Key、身份证、银行卡号、密码等不得写入日志。

### 11.5 告警场景

第一版至少实现：

| 告警 | 类型/等级 | 示例阈值 |
|---|---|---|
| 待审核案件积压 | BUSINESS/P1 | 待审核案件 > 50 |
| 规则命中率突降 | MODEL/P2 | 1 小时命中率 < 5% |
| 拒绝率异常升高 | BUSINESS/P2 | 1 小时拒绝率 > 30% |
| 模型未加载 | MODEL/P2 | 启动时 XGBoost 不存在 |
| 高风险 IP 激增 | SECURITY/P1 | 窗口内代理/Tor 事件超过阈值 |

定时器默认每 15 分钟执行一次，设置为 0 时关闭自动调度，仍保留手动检查 API。

## 13. 页面需求

### 13.1 仪表盘

- 今日评估数、高风险数、拒绝数、待审案件数；
- 近 7/30 天风险趋势；
- 四类事件分布；
- 风险等级和决策分布；
- 命中规则 TOP5；
- 高风险 IP、设备和收款账户摘要。

### 13.2 规则管理

- 按类别、事件、启停状态筛选；
- JSON 条件树可视化构建器；
- 字段下拉必须展示 25 个银行特征中文名；
- 支持单条件、AND/OR 分组和原始 JSON 查看；
- 保存前校验风险等级与分值区间；
- 删除采用软删除。

### 13.3 案件管理

- 默认只显示待审核/审核中案件；
- 展示用户、事件、来源、规则分、ML 分、最终分；
- 显示命中规则和关键特征；
- 支持通过、拒绝、关闭和拒绝时加入黑名单；
- 支持按原始 `source_id` 重做检查。

### 13.4 评估历史

- 按用户、事件类型、风险等级、决策和时间筛选；
- 详情展示事件快照、25 维特征、命中规则、ML 分和最终结果；
- 明确区分规则决策、模型决策和融合决策。

### 13.5 实时风险检查

- 动态选择四类事件；
- 选择或输入 `user_id`、`source_id`；
- 可选展示业务数据预览；
- 提交后展示完整请求链路结果；
- 黑名单短路时只显示拦截原因，不显示虚假的 ML 结果。

### 13.6 AI 助手

- 支持查询今日统计、待审案件、用户画像、规则效果、趋势和银行业务数据；
- 默认只读；
- 涉及黑名单新增/移除、案件审核、规则变更时必须提示人工去对应页面确认；
- LLM 不可用时不影响其他页面；
- 前端先判断 `res.ok` 和 `Content-Type`，不能把 `Internal Server Error` 强制当 JSON 解析。

### 13.7 黑名单

- 支持八类银行黑名单；
- 只展示脱敏值；
- 支持有效期、原因和软删除；
- 新增和移除必须写操作审计。

### 15.2 风险人物画像

至少生成以下高风险模式：

1. 异地大额转账用户；
2. 凌晨密集操作用户；
3. 新设备大额转账用户；
4. 多账户向单卡归集；
5. 多头借贷用户；
6. 同一设备关联多人；
7. 代理/Tor IP 登录用户；
8. 正常对照用户。

### 15.3 数据生成原则

- 固定随机种子，保证测试可复现；
- 数据生成器直接写业务表，评估数据必须调用真实 `process_event` 生成；
- 正例比例可配置，默认建议 20%–35%；
- 高风险模式要由多个原始字段共同形成，不能直接生成一个“是否欺诈”特征；
- 时间窗口数据必须先生成历史，再生成当前事件；
- 训练前校验样本数量、正例比例、日期跨度、25 维完整性和标签纯度。
