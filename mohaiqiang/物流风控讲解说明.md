# 物流风控系统讲解说明

## 1. 业务说明

### 1.1 系统定位

面向快递/快运/跨境物流企业，围绕“寄件 → 揽收 → 中转 → 派送 → 签收 → 投诉/理赔 → 代收货款 → 跨境报关”全链路做风险识别与处置。核心风险主体包括：寄件人、收件人、运单、地址、网点/快递员、结算账户。

### 1.2 业务边界

- 寄递实名：寄件人/收件人实名核验与面单隐私保护
- 危险品：电池、化学品等禁限物品瞒报识别
- 跨境物流：报关清关、三单对碰、海外仓、结汇退税
- 代收货款：COD 下单、收款、结算与拒收风险

### 1.3 关键风控场景

- 寄件人/收件人实名信息异常
- 危险品（电池/化学品）瞒报
- 跨境包裹重量/申报价值异常
- 代收货款（COD）拒收率异常
- 收件地址偏远/临时/多人共用
- 高频寄件、凌晨寄件、批量寄件

### 1.4 监管合规

- 实名收寄、收寄验视、过机安检三项制度
- 《邮件快件实名收寄管理办法》
- 《个人信息保护法》《数据安全法》《网络安全法》（隐私面单、数据最小化）
- 《禁止寄递物品管理规定》
- 《快递市场管理办法》
- 海关监管、外汇结算、反电信网络诈骗协同

## 3. XGBoost 评估

### 3.1 标签

- 0：通过 / 标记
- 1：人工审核 / 拒绝

### 3.2 训练数据

来源：`risk_assessment`（`ml_score IS NULL`） JOIN `risk_feature` 宽表，拼成 30 维特征矩阵。

### 3.3 30 维特征清单

### 3.4 训练配置

- 80/20 stratify 拆分
- 早停：AUC 连续 10 轮不升停止
- warmup 50 轮防假收敛
- `scale_pos_weight` 上限 10
- 最佳 F1 阈值扫描

### 3.7 概率校准与融合

```text
ml_risk_score = 100 × (1 - exp(-3 × P(拒绝)))
final_score = 0.5 × rule_score + 0.5 × ml_risk_score
```

## 4. 业务规则讲解

### 4.1 核心机制总览

本项目主要面向快递/快运/跨境物流企业，定位为守护物流全链路的安全检查系统，采用“规则 + AI”双保险。核心内容聚焦风险控制，分为三大点：

1. 风险识别
2. 风险等级划分
3. 决策（评分）

通过规则引擎和决策引擎两大引擎实现上述内容。

**规则引擎**

业务人员根据实际业务场景整理可能发生的风险，制定一系列规则。每条规则表现为“特征 + 条件 + 决策”，即发生风险的情况、什么条件下会发生、条件的标准，并将其量化。

**决策引擎**

设定风险等级和对应决策：按命中规则的分数设定低、中、高、极高四个等级（实际情况更复杂），并映射对应决策行动。

**执行主逻辑**

根据实际业务及已知信息计算得到一系列特征值，再与规则引擎创建的规则列表对比，得到命中的规则及规则打分。项目沿用电商系统框架（实际按物流业务重新设定），采用双轨融合：

- 仅有规则时：命中单条取该规则分数；命中多条为 `max(规则列表) + 额外条数分数 × (命中规则数 - 1)`
- 加上 ML 模型（XGBoost）：训练 30 维特征，学习各特征之间的非线性关系，召回“表面正常、统计上高风险”的事件
- 一票否决：上述任意一条达到极高风险，直接系统拒绝

总结：规则保精度和可解释性，ML 保召回和组合风险发现；一票否决兜底，防止模型把确定的高风险放走。

最后做好风险记录：事件记录、评估结果记录、案件记录，并更新用户风险画像。

### 4.2 规则条件

```json
{"field": "sender_waybills_30d", "op": ">=", "value": 50}
```

支持：`> >= < <= == != in not_in between`，以及 `and/or` 嵌套。

### 4.3 评分与决策

```text
rule_score = max(命中规则分) + 3 × (额外命中数)
评分 < 30 通过
评分 < 60 标记
评分 < 80 人工审核
评分 >= 80 拒绝
```

### 4.4 一票否决

极高规则命中后强制拒绝并抬到 90 分，XGBoost 低分不能推翻。

示例：

- R008 危险品件数 >= 10 → 拒绝
- R013 COD 拒收率 >= 60% → 拒绝
- R024 危险品 + 跨境组合 → 拒绝

| 类别 | 规则 |
|---|---|
| 实名风险 | R001, R002 |
| 寄件行为风险 | R003, R004, R005, R006, R017, R018, R019, R022 |

## 5. Vibe Coding 复盘

### 5.1 过程回顾

1. 从电商风控系统出发，梳理物流业务说明
2. 设计 12 张物流业务表 + DDL + SQLAlchemy 模型
3. 编写造数脚本（业务数据、高风险寄件人、评估数据、训练集）
4. 重构 30 维物流特征（寄件人/运单/地址三大族）
5. 将决策引擎、规则引擎、Agent、页面全部物流化
6. 训练 XGBoost 并完成验收

### 5.2 遇到的问题与修复

| 问题 | 原因 | 修复 |
|---|---|---|
| `logistics_complaint` 表名冲突 | 与旧电商表重名 | 改为 `logistics_complaint_record` |
| `_gen_multi_addr` 参数不统一 | 模式函数签名不一致 | 统一为 `(conn, sid, rid, aid)` |
| `--reset` 报 sender_id 不存在 | 部分表没有 sender_id 列 | 拆分 DELETE 条件 |
| 旧模型 feature mismatch | 25 维电商模型仍在 | 删除旧模型并重训 30 维模型 |
| 前端图表重叠 | 全局 `.row` 覆盖 margin | 增加 dashboard 专属行距与固定图表容器 |
| 文件命名不统一 | 三个脚本命名风格不一致 | 统一为 `gen_logistics_*` |

### 5.3 经验

- 表名、字段、枚举要先核对，避免和旧库冲突
- 特征列名必须与模型 `FEATURE_COLUMNS` 严格对齐
- 训练数据要保证 `ml_score IS NULL`，避免混入“未训练模型垃圾值”
- 高风险样本用 `--balance-pos` 控制正例比例
- 大规模改造后要跑“造数 → 训练 → 预测 → 页面”全链路验证

## 6. 可能存在的问题及解答

### Q1：`risk_assessment` 有数据但训练集为 0？

训练脚本只取 `ml_score IS NULL`。造评估数据时加 `--clean-ml`，或手动执行：

```sql
UPDATE risk_assessment SET ml_score = NULL, ml_decision = NULL;
```

### Q2：规则不命中，正例比例低？

- 检查事件类型是否匹配（R003 是“寄件下单”，R009 是“报关清关”）
- 使用 `--balance-pos` 优先挑 RISK 高风险寄件人
- 用 `gen_logistics_train_dataset.py` 造严格训练集

### Q3：模型加载报 feature mismatch？

旧模型是 25 维电商模型。删除 `app/engine/xgb_model.json` 后重训。

### Q4：`logistics_complaint` 表结构不对？

新系统使用 `logistics_complaint_record`，不要复用旧电商的 `logistics_complaint`。

### Q5：前端图表重叠？

刷新页面；若仍重叠，检查浏览器缓存，或清缓存后重新打开 `/`。

### Q6：AI Agent 无法回复？

检查 `.env` 的 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL_NAME`，并确认网络可访问。

### Q7：数据库中文乱码？

确认 MySQL 使用 `utf8mb4`，`init_db.py` 建库时已指定。

### Q8：`run_risk_check` 校验失败？

`source_id` 必须与事件类型匹配：

- 运单类事件：传运单号
- 投诉：传投诉 ID
- 理赔申请：传理赔 ID
- COD结算：传 COD 单号
- 实名认证：传寄件人 ID
