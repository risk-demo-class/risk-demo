# Vibe Coding 协作复盘（agent_design.md）

> 交付物：任务 4 | 说明我是怎么用 AI 协作完成"物流风控"的

## 1. 整体策略

基线 `AI_Risk` 是已完成的电商风控系统，任务不是重写，而是**业务层平移**。
所以整个过程中 AI 协作围绕一张"复用边界表"展开：

1. **先让 AI 读透基线**：把 `app/engine`、`app/service`、`sql/`、`scripts/` 通读一遍，
   搞清 7 步流水线、25 维特征、规则 JSON 格式、造数脚本模式。
2. **让 AI 按复用边界出设计**：5 张业务表、4 种事件类型、25 维物流特征、9 条规则，
   全部由 AI 先出方案，人工确认业务合理性。
3. **代码改造走"最小改动"路线**：能复用就不重写——决策引擎只改上下文字段名与
   画像映射；规则引擎一行没动；ML 训练脚本一行没动，只换了 `FEATURE_COLUMNS`。

## 2. AI 参与的具体环节

| 环节 | AI 做了什么 | 人工确认了什么 |
|---|---|---|
| 行业调研 | 列出物流欺诈场景、字段、事件类型 | 确认 4 个事件类型和 5 个画像符合实际 |
| 建表 | 生成 `models_business.py` + DDL | 确认枚举（电池/液体/化学品）与索引 |
| 特征 | 生成 25 维特征函数 | 确认"瞒报/拒收/虚报"能由字段算出来 |
| 规则 | 生成 9 条规则 JSON | 确认一票否决（R001）不能误伤 |
| 造数 | 生成业务数据脚本 + 静态 SQL | 确认 RISK 画像覆盖 5 种欺诈 |
| 训练 | 复用基线训练脚本 | 用 `val_auc/val_f1` 验收模型质量 |
| 文档 | 生成 README / 业务说明 | 人工补充术语与业务背景 |

## 3. 踩过的坑

- **枚举要改两处**：ORM 和 SQL DDL 都要改，否则建表与模型不一致。
- **特征顺序必须同步**：`FEATURE_COLUMNS` 与 `feature.py` 不一致 = 模型白训。
- **量纲问题**：ML 输出的是概率（0-1），不是风险分（0-100），融合前要 sigmoid 校准。
- **正例比例**：不控制正例，模型学不到欺诈模式；用 `--balance-pos` 抽 RISK 用户把
  正例拉到 30%+。

## 4. 一句话总结

**Vibe Coding 的正确姿势 = 让 AI 吃透基线架构 + 严守复用边界 + 把行业知识翻译成
特征与规则，而不是让 AI 从零重写一套风控引擎。**
