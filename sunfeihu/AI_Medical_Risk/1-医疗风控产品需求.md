# 医疗风控系统产品需求文档（PRD）

> 项目名称：Medical Risk AI（医疗智能风控系统）  
> 项目类型：本地运行的教学型行业风控实战项目  
> 技术基线：复用 `AI_Risk` 的风控核心架构，使用 Python 3.11、uv、FastAPI、SQLAlchemy Async、MySQL、Jinja2 和 XGBoost  
> 文档状态：V1.0（需求基线）  
> 重要声明：本系统仅用于教学、演示和风控辅助，不提供诊断或治疗建议，不直接替代医生、药师或医保审核人员作出最终决定。

---

## 1. 产品概述

### 1.1 产品定位

建设一个面向医疗机构、医保审核人员和运营风控人员的医疗风控演示平台，对挂号、处方和医保结算事件进行实时或准实时风险评估，识别疑似医保卡滥用、重复开方、超量用药、挂号黄牛、医生大处方和异常异地就医等行为。

平台使用“黑名单前置拦截 + 规则引擎 + XGBoost 模型 + 人工案件审核”的方式输出可解释的风险评分、命中规则和处置建议，并保留完整审计记录。

### 1.2 建设目标

1. 支持至少 4 类医疗业务事件的统一风控检查。
2. 建立患者、医生、医院、挂号、处方、处方明细、医保结算等医疗业务数据模型。
3. 建立不少于 25 个可解释特征和 12 条医疗风控规则。
4. 对高风险事件自动生成案件，支持人工审核和状态流转。
5. 使用合成数据完成 XGBoost 训练，验证集 AUC 不低于 0.70、F1 不低于 0.50。
6. 提供仪表盘、风险检查、规则管理、案件管理、评估历史、黑名单和 AI 助手页面。
7. 全项目通过 uv 管理依赖和执行命令，可在本地一键初始化和启动。

### 1.3 成功指标

| 指标 | 目标值 |
|---|---:|
| 支持的医疗事件类型 | >= 4 |
| 医疗业务表 | >= 8 张 |
| 医疗特征 | >= 25 个 |
| 医疗规则 | >= 12 条 |
| 可命中样例规则 | >= 6 条 |
| 合成业务数据 | >= 1,000 条，演示版可扩展至 10 万条 |
| XGBoost 验证集 AUC | >= 0.70 |
| XGBoost 验证集 F1 | >= 0.50 |
| 核心纯计算单元测试覆盖 | 评分、规则、状态机、特征映射均有测试 |

## 2. 产品边界

### 2.1 本期范围（MVP）

- 医保结算异常识别。
- 处方合规与用药行为异常识别。
- 挂号黄牛及高频退号识别。
- 跨医院、跨地区的患者行为关联分析。
- 医生处方行为异常识别。
- 黑名单管理、规则管理、案件审核、评估历史和统计看板。
- 基于平台数据的只读型 AI 风控助手。
- 完整合成数据、模型训练和本地演示流程。

### 2.2 本期不做

- 不连接真实医院 HIS、EMR、医保局或药店系统。
- 不保存真实姓名、身份证号、医保卡号、病历或诊断详情。
- 不进行疾病诊断、药物疗效判断和临床决策。
- 不自动执行真实医保拒付、冻结医保卡、停诊或处罚医生。
- 不实现电子病历全文分析、医学影像识别和真实支付结算。
- 不建设生产级多租户、统一身份认证、CA 签名或等保全套能力。

### 2.3 核心复用约束

以下内容沿用参考项目的契约与思路：

- 复用 9 张风控核心表：`risk_rule`、`risk_event`、`risk_feature`、`risk_assessment`、`risk_case`、`risk_blacklist`、`risk_user_profile`、`risk_action_log`、`risk_alert`。
- 保持请求核心契约：`RiskCheckRequest(event_type, source_id, user_id, event_data)`。
- 保持响应核心契约：风险评分、风险等级、决策、命中规则、特征快照、评估 ID 和事件 ID。
- 保持 `process_event` 前置处理和 `run_risk_check` 七步决策流水线的总体结构。
- 复用规则加载、评分融合、一票否决、案件生成、审计和告警机制。
- 医疗业务模型、医疗校验、特征计算、规则、合成数据及页面文案必须重新设计。

## 3. 用户与权限

| 角色 | 主要诉求 | MVP 权限 |
|---|---|---|
| 风控运营人员 | 查看风险趋势、维护规则和黑名单 | 看板、评估、规则和黑名单管理 |
| 医保审核员 | 审核异常结算与证据链 | 查询评估、处理案件、填写审核意见 |
| 药师/处方审核员 | 审核重复、超量及异常处方 | 查看处方风险详情、处理相关案件 |
| 系统管理员 | 初始化、配置和审计 | 全部功能、日志和系统配置 |
| 演示人员 | 完成课堂演示 | 使用预置数据运行检查和查看结果 |

MVP 不实现完整 RBAC 登录体系，但代码和页面应避免把“所有用户均为管理员”写死，为后续权限控制预留边界。

## 4. 业务术语

| 术语 | 说明 |
|---|---|
| 医保结算 | 医疗费用向医保基金申报并结算的业务行为 |
| 处方 | 医生针对患者开具的药品使用凭证 |
| 重复开方 | 患者在药品覆盖周期内重复获取相同或同类药物 |
| 超量用药 | 单次或累计处方数量超过配置的合理阈值 |
| 大处方 | 金额、药品数量或高价药占比显著异常的处方 |
| 异地就医 | 参保地之外发生的医疗服务和医保结算 |
| 挂号黄牛 | 通过批量、高频挂号和退号占用稀缺号源并转售的行为 |
| 医保卡滥用 | 医保凭证被多人、跨地或异常高频使用的行为 |
| 一票否决 | 命中极高风险规则后强制拒绝或冻结审核，不被模型低分覆盖 |
| 人工审核 | 系统不能直接判定时，由授权人员结合证据作最终判断 |

## 5. 核心业务流程

### 5.1 通用风控流程

1. 外部业务或演示页面提交医疗事件。
2. 系统校验患者和业务单据是否存在、是否归属正确。
3. 系统检查患者、证件摘要、医保卡摘要、手机号、医生和设备等黑名单。
4. 系统记录风险事件并计算患者、业务单据、机构/医生三类特征。
5. 规则引擎加载与事件类型匹配的启用规则。
6. XGBoost 对特征进行预测，与规则评分进行融合。
7. 系统输出通过、标记、人工审核或拒绝四档决策。
8. 人工审核或拒绝事件生成风险案件；所有结果形成特征快照和审计记录。

### 5.2 决策定义

| 决策 | 含义 | 后续动作 |
|---|---|---|
| 通过 | 未发现明显风险 | 业务继续 |
| 标记 | 有弱风险信号 | 业务继续，保留观察记录 |
| 人工审核 | 风险较高但证据不足 | 暂缓或进入审核队列 |
| 拒绝 | 命中严重风险或评分极高 | 演示环境中标记为拒绝并自动关案 |

医疗场景中的“拒绝”是风控建议。真实环境必须根据机构制度和监管要求由有权人员确认。

## 6. 业务事件

| event_type | source_id 对应对象 | 触发时机 | 主要风险 |
|---|---|---|---|
| `挂号申请` | registration_id | 提交挂号时 | 黄牛、高频挂号、多账号占号 |
| `挂号退号` | registration_id | 申请退号时 | 高频退号、临近就诊退号 |
| `处方开立` | prescription_id | 医生提交处方时 | 重复、超量、高价、大处方 |
| `医保结算` | claim_id | 医保费用申报时 | 多院高频、异地异常、金额异常 |
| `药品购药`（P1） | purchase_id | 药房购药时 | 代购、短期重复购药 |

MVP 必须实现前 4 类，第 5 类作为扩展项。

## 7. 医疗业务数据模型

所有敏感标识只保存不可逆摘要或合成值。时间字段统一保存到秒；金额使用 `DECIMAL`，禁止使用浮点数。

### 7.1 必须实现的业务表

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `medical_patient` | 患者主档 | `patient_id`、`name_masked`、`id_card_hash`、`insurance_card_hash`、`phone_hash`、`gender`、`birth_year`、`insured_province`、`account_created_at`、`real_name_status` |
| `medical_doctor` | 医生档案 | `doctor_id`、`doctor_name_masked`、`hospital_id`、`department`、`professional_title`、`license_status`、`practice_start_date`、`status` |
| `medical_hospital` | 医疗机构档案 | `hospital_id`、`hospital_name`、`province`、`city`、`hospital_level`、`hospital_type`、`insurance_designated`、`status` |
| `medical_registration` | 挂号记录 | `registration_id`、`patient_id`、`hospital_id`、`doctor_id`、`department`、`visit_date`、`register_channel`、`device_id_hash`、`status`、`register_at`、`cancel_at` |
| `medical_prescription` | 处方主表 | `prescription_id`、`patient_id`、`doctor_id`、`hospital_id`、`registration_id`、`prescription_type`、`total_amount`、`drug_count`、`issued_at`、`status` |
| `medical_prescription_item` | 处方药品明细 | `item_id`、`prescription_id`、`drug_code`、`drug_name`、`drug_category`、`unit_price`、`quantity`、`days_supply`、`is_controlled`、`is_high_value` |
| `medical_insurance_claim` | 医保结算记录 | `claim_id`、`patient_id`、`hospital_id`、`prescription_id`、`total_amount`、`insurance_amount`、`self_pay_amount`、`claim_type`、`visit_province`、`claim_at`、`status` |
| `medical_patient_device` | 患者设备关联 | `relation_id`、`patient_id`、`device_id_hash`、`first_seen_at`、`last_seen_at`、`use_count` |

### 7.2 可选扩展表

| 表名 | 用途 |
|---|---|
| `medical_drug_catalog` | 药品分类、限量和价格参考 |
| `medical_diagnosis_record` | 只保存合成诊断分类编码，不保存真实病历文本 |
| `medical_pharmacy_purchase` | 药房购药及代购风险 |
| `medical_region_policy` | 不同地区的医保限额和规则配置 |

### 7.3 核心关联约束

- 一个患者可有多条挂号、处方、医保结算和设备关联。
- 一个医生归属一个医院；一个医院拥有多名医生。
- 一张处方归属一个患者、医生和医院，可关联一次挂号。
- 一张处方有一条或多条药品明细。
- 一次医保结算归属一个患者和医院，可关联一张处方。
- `source_id` 必须与 `event_type` 对应表中的主键一致，并校验记录属于请求中的 `user_id`（患者 ID）。

### 7.4 索引要求

- 所有外键字段建立普通索引。
- 高频统计使用组合索引，例如 `(patient_id, issued_at)`、`(patient_id, claim_at)`、`(doctor_id, issued_at)`、`(hospital_id, claim_at)`。
- 黑名单 `(blacklist_type, blacklist_value, status)` 建立组合索引。
- 业务 ID、哈希化证件和医保卡字段建立唯一索引或按业务要求建立普通索引。

## 8. 风控特征需求

特征保持数值型、可解释和可审计。每次评估必须保存当时的特征快照。建议固定 25 个基础特征，避免训练与推理列顺序不一致。

### 8.1 患者行为特征（10 个）

| 特征名 | 含义 |
|---|---|
| `patient_registration_count_7d` | 7 天挂号次数 |
| `patient_cancel_count_30d` | 30 天退号次数 |
| `patient_cancel_rate_30d` | 30 天退号率 |
| `patient_hospital_count_7d` | 7 天就诊医院数 |
| `patient_claim_count_24h` | 24 小时医保结算次数 |
| `patient_claim_amount_30d` | 30 天医保申报总额 |
| `patient_cross_province_count_30d` | 30 天跨省就医次数 |
| `patient_same_drug_count_30d` | 30 天同类药品获取次数 |
| `patient_device_count_30d` | 30 天关联设备数 |
| `patient_account_age_days` | 患者平台账户存续天数 |

### 8.2 单据/处方/结算特征（9 个）

| 特征名 | 含义 |
|---|---|
| `event_total_amount` | 当前事件金额 |
| `prescription_drug_count` | 当前处方药品种数 |
| `prescription_total_quantity` | 当前处方药品总数量 |
| `prescription_max_days_supply` | 最大供药天数 |
| `prescription_controlled_drug_count` | 特殊管理药品种数 |
| `prescription_high_value_ratio` | 高价药金额占比 |
| `claim_insurance_ratio` | 医保支付金额占总额比例 |
| `event_is_night` | 是否为夜间异常时段 |
| `event_is_cross_province` | 是否跨省就医 |

### 8.3 医生/机构/设备特征（6 个）

| 特征名 | 含义 |
|---|---|
| `doctor_prescription_count_1d` | 医生当日处方数 |
| `doctor_prescription_amount_1d` | 医生当日处方总额 |
| `doctor_avg_prescription_amount_30d` | 医生 30 天平均处方金额 |
| `hospital_claim_amount_1d` | 医院当日医保申报总额 |
| `device_patient_count_7d` | 同设备 7 天关联患者数 |
| `doctor_license_abnormal` | 医生执业状态是否异常 |

无适用数据的特征必须返回 `0`，不得返回 `None`；训练和推理必须使用同一份特征列常量。

## 9. 业务规则需求

规则阈值为教学演示初始值，必须可在规则管理页面启停和调整，不作为真实医疗审核标准。

| 编号 | 规则名称 | 适用事件 | 初始触发条件 | 风险 | 建议决策 |
|---|---|---|---|---|---|
| MR001 | 医保卡多院高频使用 | 医保结算 | 24 小时内在 >= 3 家医院结算 | 极高 | 拒绝 |
| MR002 | 短期跨省高频就医 | 医保结算 | 30 天跨省结算 >= 3 次 | 高 | 人工审核 |
| MR003 | 单次医保结算金额异常 | 医保结算 | 单次总额 >= 20,000 元 | 高 | 人工审核 |
| MR004 | 医保支付占比异常 | 医保结算 | 医保支付占比 >= 98% 且总额 >= 5,000 元 | 中 | 标记 |
| MR005 | 同类药品重复开方 | 处方开立 | 30 天内同类药品获取 >= 3 次 | 极高 | 拒绝 |
| MR006 | 单次超长供药 | 处方开立 | 任一药品供药天数 > 90 天 | 高 | 人工审核 |
| MR007 | 特殊管理药品异常 | 处方开立 | 特殊管理药品 >= 2 种或数量超阈值 | 极高 | 拒绝 |
| MR008 | 医生单日大处方 | 处方开立 | 医生当日处方总额 >= 100,000 元 | 高 | 人工审核 |
| MR009 | 高价药占比异常 | 处方开立 | 高价药金额占比 >= 80% 且处方 >= 5,000 元 | 中 | 标记 |
| MR010 | 高频挂号疑似黄牛 | 挂号申请 | 同患者 7 天挂号 >= 8 次 | 高 | 人工审核 |
| MR011 | 高频退号疑似占号 | 挂号退号 | 30 天退号 >= 5 次且退号率 >= 70% | 高 | 人工审核 |
| MR012 | 设备关联多患者 | 挂号申请 | 同一设备 7 天关联 >= 5 名患者 | 极高 | 拒绝 |
| MR013 | 新账号高额结算 | 医保结算 | 账户 < 7 天且结算 >= 10,000 元 | 中 | 标记 |
| MR014 | 医生执业状态异常 | 处方开立 | 医生执业状态非有效 | 极高 | 拒绝 |
| MR015 | 夜间异常密集业务 | 通用 | 夜间且患者 24 小时业务次数 >= 3 | 中 | 标记 |
| MR016 | 黑名单主体拦截 | 通用 | 患者/证件/医保卡/手机/医生/设备命中黑名单 | 极高 | 拒绝 |

至少 MR001、MR005、MR008、MR010、MR012 和 MR014 必须能够由预置高风险样例稳定触发。

## 10. 黑名单需求

MVP 支持以下 `blacklist_type`：

- `PATIENT_ID`：患者业务 ID。
- `ID_CARD_HASH`：身份证摘要。
- `INSURANCE_CARD_HASH`：医保卡摘要。
- `PHONE_HASH`：手机号摘要。
- `DOCTOR_ID`：医生 ID。
- `DEVICE_ID_HASH`：设备指纹摘要。
- `HOSPITAL_ID`：医疗机构 ID（仅教学演示）。

黑名单需支持添加、查询、软删除/失效、原因、来源、创建时间和有效期。任何日志和页面都不得还原或展示完整身份证号、医保卡号、手机号。

## 11. 功能需求

### 11.1 仪表盘

- 展示今日评估量、风险事件数、待审核案件数、拒绝数和风险率。
- 展示近 7/30 天风险趋势。
- 展示事件类型分布、风险等级分布和命中规则 TOP 10。
- 展示医生异常处方排行和医院异常结算排行（仅合成数据）。
- 支持按日期、事件类型和医院筛选。

### 11.2 风险检查

- 用户先选择事件类型，再从对应业务记录中选择 `source_id`。
- 系统自动带出患者、医院、医生、金额等非敏感摘要信息。
- 提交后展示评分、等级、决策、命中规则、模型概率和主要特征。
- 支持一键加载正常、可疑、极高风险三类演示样例。
- 防止事件类型与业务单据类型不匹配，防止单据归属患者不一致。

### 11.3 规则管理

- 规则列表、详情、新建、编辑、启停和软删除。
- 条件使用结构化 JSON 保存，页面提供字段、运算符和值的基础编辑能力。
- 修改规则必须写入操作审计日志。
- 极高风险规则需明确标注“一票否决”。

### 11.4 案件管理

- 支持待审核、审核中、已通过、已拒绝、已关闭状态。
- 案件详情展示事件摘要、命中规则、特征证据和评估结果。
- 审核员可填写结论、意见和处理人。
- 终态案件不得再次流转；超时待审核案件可由调度器自动关闭。
- 相同业务源和事件类型存在未结案件时，不重复建案。

### 11.5 评估历史

- 支持按患者、事件类型、风险等级、决策和时间范围查询。
- 详情展示评估时的规则结果与特征快照，保证结果可回溯。
- 分页查询，避免 N+1 数据库访问。

### 11.6 黑名单管理

- 支持 7 类医疗黑名单。
- 展示值时进行掩码处理。
- 添加和移除均写入审计日志。

### 11.7 AI 风控助手

- 可回答“当前待审核案件数量”“某患者近期风险摘要”“某规则为何命中”等问题。
- 工具只允许读取脱敏后的业务和风控数据，不允许修改病例、处方、结算、规则或案件。
- 回答必须注明“仅供风控辅助”，不得输出诊断、用药或治疗建议。
- LLM 不可用时不影响规则和模型主流程。

### 11.8 告警与调度

- 待审核案件积压告警。
- 某时段风险命中率突增告警。
- 单医生处方金额突增告警。
- 单医院医保申报金额突增告警。
- 告警支持查看和处理，调度间隔通过 `.env` 配置。

## 13. 数据生成与模型训练

### 13.1 合成数据要求

- 所有姓名、证件、医保卡、手机号、医院和业务记录均为合成数据。
- 固定随机种子时结果可复现。
- 脚本支持正常数据、高风险数据、日期范围、数据量和清空重建参数。
- 默认至少生成：200 名患者、20 名医生、5 家医院、500 条挂号、500 张处方、1,000 条处方明细和 500 条医保结算。
- 构造不少于 6 种明确高风险模式，并保留正常对照组。
- 数据生成脚本可重复执行，不因主键冲突而产生不可理解的失败。

### 13.2 高风险样本模式

1. 同一患者 24 小时跨 3 家医院医保结算。
2. 同一患者短期重复获取同类药品。
3. 单医生单日集中开具高额处方。
4. 同设备关联多名患者并高频挂号。
5. 高频挂号后大量退号。
6. 执业状态异常医生继续开方。
7. 正常低频挂号、合理处方与常规结算作为负样本。

### 13.3 模型训练要求

- 特征必须来自数据库真实计算结果，不得把最终标签或规则结果作为输入特征。
- 标签来源和生成逻辑必须在 README 中说明。
- 按训练集/验证集分层拆分，避免同一事件同时进入两边。
- 输出 AUC、F1、最佳阈值、正负样本比例和特征重要性 TOP 10。
- 模型文件保存到固定位置并由服务启动时加载；加载失败时自动降级为纯规则模式。
- 训练数据不足、标签单一或正负比例异常时给出明确提示。

## 14. 非功能需求

### 14.1 安全与隐私

- 遵循数据最小化、目的限定和可审计原则。
- 证件、医保卡、手机号和设备指纹仅保存合成摘要。
- `.env`、数据库密码和 LLM Key 不进入 Git。
- API 和日志不得输出敏感字段原文。
- SQL 使用 ORM 或参数化查询，禁止拼接用户输入。
- AI 助手仅可读取允许字段，防止提示词注入诱导泄露配置或隐私。
- 文档注明与《个人信息保护法》《数据安全法》《网络安全法》及医疗数据管理要求对齐；教学项目不声称已完成正式合规认证。

### 14.2 性能

- 本地演示数据量下，普通列表接口 P95 目标小于 500ms。
- 单次风险检查（不含外部 LLM）P95 目标小于 2 秒。
- 列表接口必须分页，默认每页 20 条，上限 100 条。
- 统计查询避免明显 N+1；高频过滤字段建立索引。

### 14.3 可靠性

- 单次风险检查涉及的事件、特征、评估、案件和画像写入使用同一事务。
- 失败时回滚，不留下半成品评估。
- XGBoost 或 LLM 故障不能导致规则主流程不可用。
- 启动脚本检查 `.env`、依赖、MySQL、数据库初始化、端口和模型文件。

### 14.4 可维护性

- Router 只处理 HTTP 输入输出，Service 负责业务编排，Engine 负责特征/规则/模型，Model 负责数据映射。
- 配置集中于 `app/config.py` 和 `.env`。
- 核心纯计算逻辑具有单元测试；外部依赖可 mock。
- 业务字段、事件、规则和特征命名统一，禁止保留电商语义名称。

## 17. 总体验收标准

## 18. 风险与待确认事项

### 18.1 已识别风险

- 医疗规则高度依赖地区政策和医院制度，本项目阈值只能作为教学样例。
- 合成数据过于规则化可能导致 AUC 虚高，应在训练脚本中加入噪声并说明局限。
- 规则与模型同时参与评分可能产生冲突，必须保留一票否决和可解释证据。
- 处方合规涉及诊断、剂量和药物相互作用，本期刻意不进入临床判断范围。
- 参考项目存在少量历史实现和测试问题，迁移时应建立本项目自己的干净测试基线。

### 18.2 开发前默认决策

- 数据库继续使用 MySQL 8.x。
- 前端继续使用 Jinja2 + 原生 JavaScript/CSS，不引入独立前端工程。
- 医疗机构视角为主，不建设面向患者的客户端。
- 所有数据均为合成数据，默认中文界面。
- 第一阶段先保证规则链路可用，再训练模型，最后接入 AI 助手。

如后续产品方向发生变化，应优先更新本 PRD 的范围、事件、数据模型和验收标准，再进入实现。
