# 银行风控项目修改任务书意见书

> **基线项目**：`AI_Risk` 电商风控系统  
> **改造方向**：银行业务风控  
> **适用范围**：信用卡申请、贷款申请、大额转账、异常登录  
> **核心原则**：保留“事件驱动 + 风控核心 9 张表 + 25 维特征 + 业务规则 + XGBoost 双轨融合”的平台内核，重写电商业务层。

---

## 一、总体修改意见

本项目不建议从零重写，也不建议将“订单、收货地址、售后”简单改名为“贷款、银行卡、交易”。正确的改造方式是：保留通用风控平台内核，替换行业业务对象、事件、特征、规则、数据生成和前端文案。

```text
保留平台内核
  ├── 风控核心 9 张表
  ├── 统一决策流水线
  ├── 规则匹配框架
  ├── XGBoost 训练、推理与融合
  ├── 案件、画像、审计、告警
  ↓
重写银行业务层
  ├── 客户、银行卡、交易、贷款、登录
  ├── 设备指纹和 IP 地理位置
  ├── 银行事件和黑名单扩展
  ├── 银行特征和业务规则
  └── 银行测试、训练和演示数据
```

银行风控需要重点识别：身份冒用、KYC 不完整、新设备大额操作、异地登录/异地转账、账户—设备—银行卡团伙关联、多头借贷、代理 IP/Tor 和黑卡/黑设备风险。

---

## 二、不可修改的基线契约

### 2.1 风控核心 9 张表保持不变

以下 9 张表不得修改表名、主键和核心字段结构：

```text
risk_rule
risk_event
risk_feature
risk_assessment
risk_case
risk_blacklist
risk_user_profile
risk_action_log
risk_alert
```

职责不变：规则配置、事件审计、特征快照、评估结果、人工案件、公共黑名单、用户画像、操作审计、运营告警。

### 2.2 统一请求/响应契约保持不变

`RiskCheckRequest` 继续使用：

```text
event_type
source_id
user_id
event_data
```

银行业务编号均使用 `source_id` 传入，具体对象由 `event_type` 路由查询。不得因为银行业务新增 `loan_id`、`txn_id`、`login_id` 而破坏公共接口。

### 2.3 决策顺序保持不变

```text
业务校验 → 事件处理 → 特征计算 → 特征快照
        → 规则匹配 → XGBoost 推理 → 双轨决策与持久化
```

黑名单仍为前置短路：命中后直接拒绝，不进入普通评估流水线。

---

## 三、银行业务表设计

建议将电商业务表整体替换为以下 8 张表；允许重写业务表，禁止修改风控核心 9 张表。

| 表名 | 核心字段 | 主要用途 |
|---|---|---|
| `bank_user_info` | `user_id, name, id_card_hash, credit_score, register_at, kyc_level, account_status, usual_city` | 客户身份、KYC、信用和常用城市 |
| `bank_card` | `card_id, user_id, card_no_hash, bank_code, card_type, credit_limit, card_status, open_at` | 客户—银行卡关联，多卡与黑卡识别 |
| `bank_transaction` | `txn_id, from_card, to_card, user_id, amount, channel, device_id, ip, geo, txn_status, txn_time` | 转账/支付资金流水 |
| `loan_application` | `loan_id, user_id, amount, term_months, purpose, monthly_income, debt_ratio, application_channel, application_at, application_status` | 贷款准入、多头借贷和负债率风险 |
| `login_log` | `login_id, user_id, device_id, ip, geo, success, login_at, login_channel` | 异地登录、失败爆发和账户接管 |
| `device_fingerprint` | `device_id, user_id, fingerprint_hash, first_seen, last_seen, os, browser, is_emulator` | 多人共用设备、模拟器、新设备风险 |
| `ip_geo_location` | `ip, country, province, city, isp, is_proxy, is_tor` | IP 地理位置、代理和 Tor 判断 |
| `bank_blacklist_extra` | `entry_id, blacklist_type, blacklist_value, reason, expire_at` | 设备、IP、银行卡、身份证扩展黑名单 |

设计约束：身份证和银行卡号必须使用哈希或虚拟数据；不得使用真实敏感信息。

### 黑名单意见

不建议直接扩展 `risk_blacklist` 的枚举。原表继续承担公共黑名单能力；银行专属的设备指纹、IP 地址、银行卡号、身份证号放入 `bank_blacklist_extra`，并由银行版校验器统一查询，以免破坏通用风控表契约。

## 四、银行事件类型设计

| 事件类型 | `source_id` | 主要查询表 | 风控目标 |
|---|---|---|---|
| `信用卡申请` | 申请编号 | `bank_user_info`、`bank_card` | 新卡申请、额度风险、KYC 风险 |
| `贷款申请` | `loan_id` | `loan_application` | 贷款准入、多头借贷、负债率风险 |
| `大额转账` | `txn_id` | `bank_transaction`、`login_log` | 实时交易反欺诈 |
| `异常登录` | `login_id` | `login_log`、`device_fingerprint`、`ip_geo_location` | 账户接管和环境风险 |

每种事件必须：

1. 校验 `source_id` 归属于 `user_id`。
2. 查询对应业务对象及关联上下文。
3. 返回完整的 25 维特征字典。
4. 以统一引擎输出规则结果、ML 分数、最终决策和审计记录。

建议将银行路由、ID 补全、扩展黑名单查询集中在 `app/service/event.py` 与 `app/service/validator.py` 中，不要把银行 SQL 硬编码进 `decision.py`。

## 五、25 维银行特征改造方案

`FEATURE_COLUMNS` 的字段数量、字段名和顺序保持不变，避免训练/推理不一致；但计算逻辑从“用户—订单—地址”转换为“客户—交易/申请—设备/IP”。

### 5.1 客户行为特征（14 个）

| 原特征名 | 银行版语义 |
|---|---|
| `user_total_orders` | 历史交易总笔数 |
| `user_orders_30d` | 近 30 天交易总笔数 |
| `user_orders_7d` | 近 7 天交易总笔数 |
| `user_total_amount` | 历史交易总金额 |
| `user_avg_order_amount` | 平均交易金额 |
| `user_max_order_amount` | 历史最大单笔交易金额 |
| `user_refund_count` | 历史撤销/冲正次数 |
| `user_postsale_count` | 历史争议/投诉次数 |
| `user_refund_rate` | 撤销或冲正率 |
| `user_postsale_rate` | 争议交易率 |
| `user_refund_amount` | 历史撤销/争议金额 |
| `user_cancel_count` | 交易失败、取消或拒绝次数 |
| `user_complaint_count` | 客户投诉次数 |
| `user_address_count` | 常用登录地/交易地数量 |

### 5.2 当前业务行为特征（8 个）

| 原特征名 | 银行版语义 |
|---|---|
| `order_total_amount` | 当前转账金额或贷款申请金额 |
| `order_item_count` | 关联银行卡数量或申请资料项数量 |
| `order_sku_count` | 当前交易涉及账户/资金节点数量 |
| `order_discount_amount` | 额度优惠、手续费减免或营销优惠金额 |
| `order_discount_rate` | 优惠金额占当前金额比例 |
| `order_pay_interval_sec` | 登录/申请到当前操作的时间间隔 |
| `order_is_night` | 是否凌晨高风险时段操作 |
| `order_category_count` | 交易渠道、用途或关联业务类别数量 |

### 5.3 设备与地理特征（3 个）

| 原特征名 | 银行版语义 |
|---|---|
| `addr_total_count` | 用户历史使用过的设备数量 |
| `addr_province_count` | 历史登录/交易涉及省份数量 |
| `addr_is_new` | 当前设备或 IP 是否首次出现 |

验收要求：返回字典键必须与 `FEATURE_COLUMNS` 完全一致；不能计算时返回 `0.0`；禁止使用随机数填充；必须新增 `docs/银行特征字典.md` 说明每个特征的来源表、SQL 口径和事件差异。

## 六、银行业务规则建议

至少实现以下 8 条，建议扩展至 12-16 条：

| 编号 | 规则 | 触发条件 | 风险等级 | 决策 |
|---|---|---|---|---|
| R001 | 异地大额转账 | 当前登录城市与常用城市不同，且转账金额大于 50000 | 极高 | 拒绝 |
| R002 | 凌晨密集操作 | 0-5 点内 1 小时交易不少于 3 笔 | 高 | 人工审核 |
| R005 | 新设备大额交易 | 设备首次出现不超过 7 天，且单笔交易大于 30000 | 高 | 人工审核 |
| R008 | 多卡归集 | 1 小时内多张银行卡转入同一张卡 | 极高 | 拒绝 |
| R012 | 信贷申请突击 | 当月向不少于 3 家机构申请贷款 | 高 | 人工审核 |
| R018 | 设备多人共用 | 同一设备关联不少于 5 个用户 | 中 | 标记 |
| R025 | 代理 IP/Tor | 当前登录 IP 命中代理、Tor 或高风险 IP 库 | 中 | 标记 |
| R030 | 黑卡拦截 | 收款卡号命中银行黑名单 | 极高 | 拒绝 |

建议新增：KYC 不足申请高额度、收入与贷款金额不匹配、连续失败后换设备登录、同一身份证关联多个高风险账户、短时间跨省登录并转账、模拟器设备申请贷款、沉默账户突然大额交易。

每条规则必须给出：触发条件、风险等级、决策动作、业务原因和测试样例。

## 八、实施顺序与验收任务

### 任务 1：银行业务理解和设计

交付：

- `docs/银行行业分析.md`
- `docs/银行业务表设计.md`
- `docs/银行事件字典.md`
- `docs/银行特征字典.md`
- `docs/银行规则设计.md`

验收：能够说明四类事件、八张业务表、八条核心规则，以及它们和电商项目的差异。

### 任务 2：数据层和规则层改造

```powershell
python scripts/init_db.py --reset --yes
python scripts/gen_risky_users.py
python scripts/gen_risk_data.py
```

验收：业务表可创建；每类事件有正常与高风险样本；正例比例不少于 15%；至少 8 条规则可命中；核心 9 张表未被破坏。

### 任务 3：端到端与 XGBoost

必须演示：

1. 正常信用卡申请：通过。
2. 新设备大额转账：人工审核或拒绝。
3. 异地大额转账：命中 veto，拒绝。
4. 代理 IP 异常登录：标记或人工审核。

模型验收：训练样本不少于 500 条；正例比例不少于 15%；`val_auc >= 0.70`；`val_f1 >= 0.50`；不触发假收敛；前端显示 ML 拒绝概率；模型失效时降级到纯规则。

### 任务 4：演示与交付

最终提交：可运行 Git 仓库、业务表设计、事件/特征/规则字典、训练指标截图、四类事件演示截图、5-8 分钟讲解材料、至少 30 个银行场景测试用例。

## 九、测试要求

至少覆盖：

- 四类事件的 `source_id` 与 `user_id` 归属校验。
- 信用卡申请正常、高额度、KYC 不足。
- 贷款申请正常、多头申请、高负债率。
- 大额转账正常、异地、凌晨、新设备。
- 异常登录正常、代理 IP、Tor、多人共用设备。
- 用户、设备、IP、银行卡、身份证黑名单。
- veto 规则不能被低 ML 分数推翻。
- 模型未加载时纯规则降级。
- 25 个特征字段完整且顺序一致。
- `risk_event`、`risk_feature`、`risk_assessment` 可以完整回溯。
- 人工审核自动创建 `risk_case`，操作写入 `risk_action_log`。

关键断言：

```text
规则命中 → rule_score 正确
模型输出 → ml_score 正确
融合结果 → final_score 正确
极高规则 → 最终一定拒绝
```

## 十、风险与边界意见

1. 本项目是银行风控迁移原型，不是完整征信、授信和放款系统；不得接入真实征信或真实放款。
2. 身份证、银行卡、手机号、IP、设备指纹必须使用脱敏、哈希或虚拟数据；禁止写入真实数据、日志和截图。
3. 训练标签来自模拟风险结果或人工标注，不能把规则命中字段原样作为模型输入后预测相同规则结果，防止标签泄漏。
4. `risk_rule` 规则分和 XGBoost 概率必须继续走统一双轨融合；极高风险规则必须保留一票否决。

## 十一、最终评价标准

| 等级 | 标准 |
|---|---|
| A | 四类银行事件跑通；核心 9 表复用；规则合理；`val_auc >= 0.80`；能讲清双轨融合和 veto |
| B | 端到端跑通；`val_auc >= 0.70`；至少 8 条规则生效；有案件和黑名单演示 |
| C | 能建表、造数据、完成检查；规则较粗糙；模型能训练但指标一般 |
| D | 只有页面或 SQL，无法完整跑通事件到决策链路 |
| 不合格 | 直接复制电商字段；修改核心 9 表；无银行规则；无模型训练或无法解释结果 |

---

## 十二、结论

建议按本意见书执行：**平台层不动，业务层重做；事件银行化，特征银行化，规则银行化，训练数据银行化。**

最终目标不是替换电商页面文案，而是证明可以把通用风控能力抽象出来，并将业务数据、风险特征、规则知识和模型训练完整迁移到银行场景。
