## 一、为什么是这个任务

`AI_Risk` 这套电商风控已经在课堂上讲完了——**事件驱动 + 25 维特征 + 业务规则 + XGBoost 双轨融合** (规则数量按行业复杂度自由定)这套架构是可复用的. 但**业务层** (订单 / 物流 / 售后) 每换一个行业就完全不一样.

让学生做这个任务, 本质是验证两件事:

1. **能不能把"风控核心 9 张表"识别出来, 跟"行业业务表"做解耦**
2. **能不能用 Vibe Coding 快速吃透陌生业务, 48 小时内出可演示原型**

## 二、基线项目: 复用边界 (能复用哪些 / 必须改哪些)

这是任务里**最重要的一张表**, 学生必须先看明白这个边界:

| 模块 | 学生能不能动 | 说明 |
|---|---|---|
| 风控核心 9 张表 | **完全复用, 不许改** | `risk_rule / risk_event / risk_feature / risk_assessment / risk_case / risk_blacklist / risk_user_profile / risk_action_log / risk_alert` |
| 风控引擎 4 个核心 | **完全复用** | `app/engine/{decision, feature, rule, ml_model}.py` 不许改 schema, 只改特征计算函数 |
| 决策流水线 | **完全复用** | `process_event` 4 步 + `run_risk_check` 7 步不许改流程 |
| 行业业务表 | **必须重写 80%** | `app/models_business.py` 跟业务强绑定, 每个行业重做 |
| 行业特征计算 | **必须重写** | `compute_user_features / compute_order_features / compute_address_features` 三大特征族 |
| 业务校验 | **必须重写** | `app/service/validator.py::ensure_source_matches_event_type` 派发表 |
| 业务黑名单类型 | **必须重写** | 比如"设备指纹"在银行业才有, "IP 地址"在所有行业都有 |
| 业务事件类型 | **必须重写** | 比如旅游有"签证欺诈", 教育有"虚假学历", 制造业有"串货举报" |
| 业务数据生成脚本 | **必须重写** | `gen_risky_users.py` / `gen_risk_data.py` 全部按行业重做 |
| 业务规则 | **必须全部重做** | 数量自由 (5 条起步). 这是行业 know-how 的核心, 规则内容 / 阈值 / 决策等级全部按行业重做 |
| 前端 / 文档 / Docker | **部分复用** | 框架能用, 业务字段要改 |

**核心契约**: `process_event` 接收 4 字段 `RiskCheckRequest(event_type, source_id, user_id, event_data)`, 返回 `RiskCheckResponse`——这层契约**不能改**, 是学生发挥的边界.

**推荐选择策略**:

- **小组做** (3 人): 选 B 银行 / F 医疗——业务复杂 / 规则多, 能体现分工价值
- **个人做**: 选 E 物流 / H 共享经济——业务边界清晰, 能当天跑通
- **展示效果最好**: A 旅游 / C 教育——数据可视化天然有故事感
- **避免选 D 制造业**——除非有设备/经销商业务背景, 否则不好讲

## 四、4 个深度场景包 (详细数据表设计)

下面挑 4 个最有代表性的行业, **给出必须有的业务表 schema 草图**. 学生即使选其他行业, 也按这个模板做.

### 场景 A: 旅游风控 (推荐小组)

**业务边界**: 用户在 OTA 平台预订机票 / 酒店 / 签证 / 跟团游, 触发风控

#### A.1 必须有的业务表 (7 张)

| 表名 | 核心字段 | 跟电商版的差异 |
|---|---|---|
| `UserInfo` | `user_id, name, real_name_status, vip_level, account_age_days` | 加"实名状态" (旅游必须) |
| `OrderInfo` | `order_id, user_id, order_type, total_amount, dest_country, depart_date, return_date, passenger_count` | 跟电商订单完全不同: 加"目的地国家 / 出行日期 / 乘客数" |
| `PassengerInfo` | `passenger_id, name, id_type, id_number, nationality, age` | 跟电商 `ReceiveInfo` 同级, 1 个订单 N 个乘客 |
| `VisaApplication` | `visa_id, user_id, dest_country, visa_type, reject_history, submit_time` | 全新表, 电商没有"签证"概念 |
| `BookingHotel` | `booking_id, order_id, hotel_id, check_in, check_out, room_count, is_refundable` | 全新表 |
| `BookingFlight` | `booking_id, order_id, flight_no, depart_airport, arrive_airport, cabin_class` | 全新表 |
| `BlacklistExtra` | `entry_id, type, value, reason, expire_at` | 跟电商 `RiskBlacklist` 一致, 但 `type` 加 `护照号 / 签证号 / 设备指纹` |

#### A.2 必有的业务规则 (举例 8 条, 行业专属部分)

| 编号 | 规则名 | 触发条件 | 风险等级 | 决策 |
|---|---|---|---|---|
| R001 | 拒签历史拦截 | 用户 90 天内签证被拒 ≥ 2 次 | 极高 | 拒绝 |
| R002 | 短期多国签证 | 30 天内申请 ≥ 3 个不同国家签证 | 高 | 人工审核 |
| R005 | 大额跨境游 | 单笔订单 > 50000 元 | 高 | 人工审核 |
| R008 | 黄牛囤票 | 同一支付账号 1 小时内预订 ≥ 5 张同航班 | 极高 | 拒绝 |
| R012 | 0 点突击下单 | 凌晨 1-5 点下单 + 行程 < 7 天 | 中 | 标记 |
| R018 | 乘客信息不一致 | 订单乘客 ID 号与历史乘客匹配 < 30% | 中 | 标记 |
| R025 | 新用户大单 | 注册 < 7 天 + 订单 > 10000 元 | 中 | 标记 |
| R030 | 黑护照拦截 | 乘客证件号在黑名单 | 极高 | 拒绝 |

#### B.2 必有的业务规则 (举例 8 条, 行业专属部分)

| 编号 | 规则名 | 触发条件 | 风险等级 | 决策 |

| R005 | 新设备大额 | 注册设备 < 7 天 + 单笔 > 3 万 | 高 | 人工审核 |
| R008 | 多卡归集 | 1 小时内 N 张卡转入同一卡 | 极高 | 拒绝 |
| R012 | 信贷申请突击 | 当月已申请 ≥ 3 家不同机构贷款 | 高 | 人工审核 |
| R018 | 设备多人共用 | 同一 device_id 关联 ≥ 5 个不同 user_id | 中 | 标记 |
| R025 | IP 代理/秒拨 | 登录 IP 命中代理库 / Tor 出口 | 中 | 标记 |
| R030 | 黑卡拦截 | 收款卡号在黑名单 | 极高 | 拒绝 |

### 场景 E: 物流风控 (推荐个人)

**业务边界**: 寄递实名 / 危险品申报 / 跨境包裹 / 代收货款 4 大场景

#### E.1 必须有的业务表 (6 张)

| 表名 | 核心字段 | 跟电商版的差异 |

#### E.2 必有的业务规则 (举例 8 条, 行业专属部分)

## 五、4 个递进任务 (vibe coding 节奏)

让学生**逐步**做出端到端可演示版本, 每个任务有明确产物和验收标准.

### 任务 1 (2 学时): 行业选型 + 业务理解文档

**输入**: 8 个行业方向二选一 (或抽签)

**产物**:

- `docs/行业分析.md`: 300-500 字, 说清"这个行业的核心业务是什么 / 风险点在哪里 / 跟电商比最大差异"
- `docs/业务表设计.md`: 列出 6-8 张业务表, 每张表 3-5 个核心字段 + 1 句话说明用途
- `docs/规则设计.md`: 列出 N 条规则 (每条 1 行: 编号/名称/触发条件/风险等级/决策), 数量自由, 5 条起步

**验收**:

- 行业分析说人话, 不是百度百科堆砌
- 业务表 / 规则能**讲出"为什么这么设计"** (不卡字段比例, 不卡规则数量, 不卡风险等级覆盖)
- 唯一硬底线: 跑通端到端 + 至少跑出 1 次"非通过"的决策

**Vibe Coding 关键**:

- 用 AI 调研行业 ("旅游业常见的欺诈场景有哪些")
- 用 AI 设计 schema ("基于这套字段生成 SQLAlchemy 模型")
- 业务规则必须**自己写**, AI 只能帮你查漏补缺

---

### 任务 2 (2 学时): 数据层 + 规则引擎改造

**输入**: 任务 1 的 schema 设计

**产物**:

- 改写 `app/models_business.py` (新 6-8 张表)
- 改写 `app/engine/feature.py::compute_*_features` (3 个特征族函数)
- 改写 `app/engine/rule.py` 注册新规则 (每条 1 个 match 函数 + 1 个 score 阈值), 数量自定

**验收**:

- `python -m app.service.validator` 能跑通 (demo 块不报错)
- `python scripts/init_db.py --reset --yes` 能建表
- `python scripts/gen_risky_users.py` + `gen_risk_data.py` 能造数据, **正例比例 ≥ 15%**

**坑预警** (必须告诉学生):

- 改 schema 要同步改 `app/schemas.py` 的 Pydantic 模型
- 改 feature 要保证返回字段名跟 `FEATURE_COLUMNS` 对齐 (25 维不能乱)
- 改 rule 要保证每条规则都有 `enabled=True` 才能进 `load_enabled_rules()`

### 任务 3 (2.5 学时): 端到端 pipeline + XGBoost 训练

**输入**: 任务 2 的代码

**产物**:

- 启动 `run_app.py` 一键启动, 跑通 6 步 preflight
- 在前端触发 5 个不同场景的检查 (如: 旅游的"签证申请"/"机票预订"), 每条都有合理决策
- 跑 `python scripts/train_xgb_model.py` 训练 XGBoost, 输出:
  - `val_auc ≥ 0.7`
  - `val_f1 ≥ 0.5`
  - **不触发假收敛** (`is_fake_convergence=False`)

> **训练数据最低门槛**: 至少 500 条评估 + 正例比例 ≥ 15%, 否则 XGBoost 必然假收敛. 不达标时先跑 `gen_risk_data.py --balance-pos` 补数据.
- 跑 `python scripts/backfill_ml_score.py` 回填 ml_score
- 训练数据**严格化**: `risk_assessment.ml_score IS NULL` 过滤

**验收**:

- 浏览器能打开前端 (`http://localhost:8000/`)
- 至少 1 条规则触发"拒绝"决策 (看 case 列表能看到)
- XGBoost 模型能成功加载 + 推理 (前端 ML 评分小节显示非 0)
- 测试用例不崩 (`pytest tests/ -k "not scheduler"` 通过 200+ 个)

**Vibe Coding 关键**:

- 训练数据 0 进展时直接问 AI: "为什么 val_auc 低? 是数据不平衡还是特征没区分度?"
- 让 AI 帮你 debug 假收敛 ("我的 XGBoost 早停在第 5 轮, val_auc 只有 0.6, 怎么调?")

## 九、附录: 5 个常见翻车点 (提前警告)

1. **改 schema 时漏改 Pydantic**: `app/schemas.py::RiskCheckRequest` 跟 `models_business.py` 是双胞胎, 漏一个就跑不起来
2. **特征函数返回字段名跟 FEATURE_COLUMNS 不一致**: 训练时是 25 维, 推理时字典 key 错位, ml_score 全是 0
3. **规则 enabled=False**: 加规则后忘了 `db.commit()` 或者忘了 `enabled=True`, 前端永远看不到
4. **训练数据全是 0 标签**: `gen_risk_data.py` 造了 1000 条全是通过, XGBoost 训练失败 (val_auc=0.5)
5. **XGBoost 模型没回填**: 训完忘了跑 `backfill_ml_score.py`, 前端 ML 评分永远是 0
