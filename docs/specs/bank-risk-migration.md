# Spec: 电商风控 → 银行信贷风控 全量领域迁移

> 状态：`done`（2026-08-12 T-01..T-10 全部落地，360 测试通过并合并 bank-migration → main）
> 说明：本项目无 issue tracker（非 git 仓库），本 spec 落地为文件，等同发布。

---

## Problem Statement

我拥有一套完整的电商风控系统（规则引擎 + XGBoost 双轨融合 + 黑名单 + 案件审核 + 告警调度 + AI Agent，315 个测试），但目标是**面试银行风控岗位**。现有系统从表结构、特征、规则到前端文案全是电商语义（订单/退款/物流），面试官深挖任何一层都会被认定为"电商项目"，无法证明银行风控能力。我需要把整个系统改造成**银行信贷风控**语义，让任何一层被追问时都是可信、自洽的银行风控。

## Solution

**全量替换领域层，原样保留引擎层**：

- **替换**：17 张业务表（DDL+数据）、25 维特征、30 条规则、4 个事件类型、请求/响应契约、前端文案、数据生成脚本、训练数据脚本、领域相关测试。
- **保留**：决策 7 步流水线、规则解析/匹配、XGBoost 双轨融合（sigmoid 校准 + 一票否决）、案件状态机、告警调度器、黑名单、审计日志、分页框架、日志体系。

改造后系统定位：**银行信贷风控**——以贷款申请审批为主线，覆盖欺诈风险、信用风险、反洗钱合规三个维度，贯穿进件 → 放款 → 贷后 → 服务全生命周期。

## User Stories

1. 作为**面试候选者**，我想在简历上写"银行信贷风控系统"，以便投递银行/消金/互金风控岗位不被领域不符刷掉。
2. 作为**面试候选者**，我想面试官追问任一表结构时得到自洽的银行语义，以便证明项目真实可信。
3. 作为**面试候选者**，我想讲清"电商→银行"的领域迁移方法论，以便展示跨领域建模能力。
4. 作为**风控运营**，我想收到一笔新的贷款申请时系统实时跑出风险等级与决策，以便决定自动通过/标记/人工审核/拒绝。
5. 作为**风控运营**，我想看到命中的具体规则（如多头借贷、负债率超标），以便人工复核有依据。
6. 作为**风控运营**，我想命中"极高"规则时被强制拒绝（一票否决），以便极端风险不被模型放行。
7. 作为**风控运营**，我想在放款环节复核风险，以便防操作风险与洗钱。
8. 作为**贷后专员**，我想在还款/逾期事件上触发贷后风险规则，以便及时发现逾期与违约苗头。
9. 作为**客服/合规**，我想客户投诉事件进风控，以便把纠纷信号纳入客户画像。
10. 作为**审核员**，我想在案件工作台处理"人工审核"案件，以便决定通过/拒绝/关闭并沉淀黑名单。
11. 作为**审核员**，我想查看案件关联的评估详情、命中的规则、ML 评分，以便复核有完整上下文。
12. 作为**模型工程师**，我想用银行语义的 25 维特征训练 XGBoost，以便规则+ML 双轨融合持续工作。
13. 作为**模型工程师**，我想训练数据正例来自高风险申请（会被拒绝/人工审核的），以便标签业务含义成立。
14. 作为**风控管理者**，我想在仪表盘看到申请量/风险分布/决策分布，以便汇报与监控。
15. 作为**风控管理者**，我想配置/软删规则（欺诈/信用/反洗钱/账户/贷后/合规六类），以便策略快速迭代。
16. 作为**风控管理者**，我想黑名单按客户/手机号/地址维度管理，以便快速封禁已知风险。
17. 作为**风控管理者**，我想告警调度器监控待审积压/规则命中率异常，以便及时干预。
18. 作为**审计人员**，我想所有自动拒绝/人工操作留审计日志，以便合规追溯。
19. 作为**面试候选者**，我想一切自动化命令（初始化/造数/训练/一键启动）仍然可用，以便现场演示零失误。
20. 作为**面试候选者**，我想保留引擎层测试（决策/规则/ML/案件/告警）证明工程质量，以便展示测试能力。

## Implementation Decisions

### D1. 领域定位与事件线
- 主线：信贷审批；副线：反欺诈、信用风险、反洗钱合规。
- 事件类型（4 枚举，与引擎对齐）：`贷款申请` / `放款` / `还款` / `客户投诉`。
- 生命周期：进件 → 放款 → 贷后 → 服务。

### D2. 实体模型（17 张业务表全量替换）
主实体：**customer（客户）**，非 borrower、非 user。映射清单（电商 → 银行）：

| 电商 | 银行 |
|---|---|
| user_info | customer_info 客户表 |
| order_info | loan_application 贷款申请表（时间线：申请/审批/放款/到期） |
| order_detail | loan_installment 分期明细表 |
| sku_info | loan_product 贷款产品表（利率/期限/额度上限） |
| product_category | loan_product_category 产品类别（信用贷/抵押贷/经营贷/消费贷/车贷/房贷） |
| order_status | loan_status 贷款状态（申请中/审批中/已放款/还款中/已结清/逾期/已拒绝） |
| receive_info | contact_info 联系信息表（手机/地址/紧急联系人） |
| postsale | overdue_record 逾期记录表 |
| postsale_status | repayment_status 还款状态表（正常/逾期/已结清） |
| postsale_reason | overdue_reason 逾期原因表 |
| logistics | repayment_record 还款记录表（应还日/实还日/还款方式） |
| order_logistics | loan_repayment_rel 申请↔还款关联 |
| postsale_logistics | overdue_repayment_rel 逾期↔还款关联 |
| logistics_company | bank_branch 银行网点表 |
| region | region 地区表（保留） |
| logistics_complaint | complaint_content 投诉内容对照 |
| logistics_complaints_record | complaint_record 投诉记录表 |

### D3. 特征域（25 维，3 类前缀，与引擎 FEATURE_COLUMNS 对齐）
- `cust_*` 客户维度 ×14：cust_total_loans、cust_loans_30d、cust_loans_7d、cust_total_credit、cust_avg_loan_amount、cust_max_loan_amount、cust_overdue_count、cust_overdue_rate、cust_overdue_amount、cust_repay_count、cust_repay_rate、cust_reject_count、cust_complaint_count、cust_contact_count。
- `loan_*` 申请维度 ×8：loan_amount、loan_term_month、loan_installment_count、loan_debt_ratio、loan_income_debt_ratio、apply_interval_sec、apply_is_night、apply_product_count。
- `dev_*` 设备/网络维度 ×3：dev_total_count、dev_ip_province_count、dev_is_new。
- 特征语义强调银行味：多头发起、负债率、收入负债比、逾期率、履约率、被拒史、设备/IP 稳定性。

### D4. 规则（30 条，6 大银行场景）
欺诈风险 ×6（多头借贷、团伙申请、极速申请、夜间申请、异地异常、资料矛盾）/ 信用风险 ×6（负债率、逾期率、收入负债比、被拒史、新客大额、呆账）/ 反洗钱 ×4（频繁大额、快进快出、拆分、无真实用途）/ 账户风险 ×5（异常登录、新设备、批量注册、信息频繁修改、密码尝试）/ 贷后风险 ×5（逾期、连续逾期、套现、提前还款异常、还款来源异常）/ 合规风险 ×4（黑名单、制裁名单、敏感行业、高风险地区）。

### D5. 契约变化（schema）
- `event_type` 字面量：`下单/支付/售后申请/物流投诉` → `贷款申请/放款/还款/客户投诉`。
- `rule_category` 字面量：`订单欺诈/支付风险/账户风险/售后滥用/地址风险/物流风险` → `欺诈风险/信用风险/反洗钱/账户风险/贷后风险/合规风险`。
- 请求字段：`source_id` 语义 = 申请ID/还款ID/投诉ID；`order_id` → `loan_id`（保留字段名兼容引擎，语义为贷款申请ID）；`receive_id` → `contact_id`（联系信息ID）。
- 用户画像响应字段：total_orders→total_loans、total_refunds→overdue_count、refund_rate→overdue_rate、avg_order_amount→avg_loan_amount、address_count→contact_count、complaint_count 保留。
- 决策动作、等级、黑名单类型、案件字段：**不变**（引擎层）。

### D6. 数据生成与训练
- 数据生成脚本换银行域：客户画像（含 5% 高风险客户）、贷款产品、申请数据（含欺诈/信用风险注入）、还款/逾期记录、投诉记录。
- 训练正例来源：高风险客户（高逾期率/多头借贷/被拒史）的申请被拒绝/人工审核 → 标签 1；正常客户 → 标签 0。
- 训练脚本特征名同步更新；标签语义保持引擎约定（0=通过/标记，1=人工审核/拒绝），业务含义由数据生成保证。

### D7. 前端与 Agent
- 前端文案全量替换：仪表盘指标（申请量/风险分布）、风险检查表单（贷款申请/放款/还款/投诉）、规则管理（六类银行场景）、案件工作台、黑名单、用户画像页。
- AI Agent 工具若引用电商实体则同步替换。

## Testing Decisions

- **好测试的标准**：只测外部行为（给定请求 → 决策/响应/落库），不测实现细节；引擎层测试保持"领域无关"（不断言电商词）。
- **保留（引擎层，不改）**：决策评分/一票否决/融合、规则解析与匹配、ML 校准、案件状态机/超时关闭、告警调度、审计日志、黑名单类型、分页、日志配置。
- **重写（领域层）**：DDL 同步（表结构→银行 17 表）、特征计算（25 维银行特征名与取值）、schema 契约（事件类型/规则分类字面量）、事件校验（客户/申请/还款归属）、数据生成脚本（客户画像/申请/还款/逾期）、训练数据校验（正例来自高风险客户）、一键启动/前端页面文案。
- **Prior art**：沿用现有 `test_ddl_sync`（SQLAlchemy 反射对比 ORM）、`test_feature_optimization`（特征名对齐 FEATURE_COLUMNS）、`test_gen_*`（脚本参数与输出断言）的测试模式，仅替换领域断言。

## Seams（测试/验证边界）

1. **最高 seam：HTTP API**——`/api/risk/check` 收到银行事件请求 → 返回银行语义决策；`/api/rules` 增删改查银行规则。验证端到端领域正确性。
2. **中间 seam：决策引擎纯函数**——现有 `test_risk_decision` 模式（不依赖 DB），保持。
3. **低 seam：DDL 反射对比**——`test_ddl_sync` 模式验证 17 张银行表与 ORM 一致。
4. **脚本 seam**——数据生成/训练脚本的参数化输出断言。

> 注：to-spec 流程要求与用户确认 seams；此处按用户指示不采访，交付时请复审本清单。

## Out of Scope

- 引擎层改动（评分公式、状态机、调度器、黑名单逻辑）。
- 真实征信对接（人行征信/百行征信 API）、OCR 影像件、电子签章。
- 生产级安全（等保、加密、权限矩阵）。
- 多银行/多租户、子账户体系。
- 移动端 App。
- 反洗钱大额交易报告（CTR/STR）报送系统（仅保留规则维度，不含报送链路）。
